# 06. 製品構想 v2（最終形）: リスク提案ナビ — 営業と商品部をつなぐ二方向ナレッジエンジン

**位置づけ**: docs/02（v1構想）を上書きする確定版。対話で確定した論点（更新案件が主戦場／切り口は多数／刺さった要因は言語化できない／型をガンガン生む工場がゴール／投稿ボックスは商品部の内輪の声であり、本当に要るのは営業が拾う顧客の形なき声）をすべて反映。仕様書 docs/spec/ は本書に対する差分（18_v1.1差分仕様.md）で追随する。

---

## 1. 一文で言うと

> **営業の「現場の声」と商品部の「商品・座組の知識」を、AIの上で毎日すれ違わせて、新しい提案（型）をガンガン生み出し、成功パターンを全員に横展開する装置。**

## 2. 二人の主人公と、欠けた半分

| | 持っているもの | 欠けているもの |
|---|---|---|
| **営業** | 顧客の形なき声・課題感・見えないリスク（毎日拾っている） | 商品知識（費用利益・工業中止…全種目は覚えられない）、座組・スキームの引き出し |
| **商品部** | 商品・約款・引受の知識、座組の部品（機構795件） | 現場のリアルな課題感・顧客の声（だからアイデアが凝り固まり、投稿もドロップする） |

投稿ボックス2年分の分析が示したのは「商品部内の発想は受け側の構造で8割落ちる」だったが、より根本の制約は**インプットが商品部の内輪の声しかない**こと。ヤモリ→じゃぱん21→WOTAのような横展開が生まれたのは、現場の課題（水道管・水処理）と座組の知識（検知×裏受け）が一人の頭の中で出会ったからで、この「出会い」を個人の偶然から**仕組みの必然**に変えるのが本製品である。

## 3. 核心の設計判断: 現場の声は「集めない」。副産物として貯まる

営業は商品部のためのデータ入力を絶対にしない。だから：

```
営業がやること: 自分の得のために道具を使うだけ
  更新診断・新規提案プレイ → 1日仕事が15分になり、提案が厚くなる
  その入力（営業メモ・付保状況・顧客の変化）と
  その出力への反応（商談事実・顧客の実際の発言）が
  ──── 構造化された「現場の声」として自動的に貯まる ────
商品部がやること: 貯まった声を編集長として裁くだけ
  月次: AIが受信箱＋案件ログから型候補・カタログ更新・判断基準の下書きを生成 → 採択/却下
  四半期: AIが全案件を横断して勝ち筋仮説 → 裁定 → 型ライブラリへ
  採択された型は翌月から全営業の提案生成に自動注入される
```

**営業は提案力を得て、商品部は現場の声を得る。** どちらも相手のために働かない。それでも回る。これがフライホイールの正体で、「刺さった要因の言語化ができない」問題も、人に解釈を書かせず事実（提案内容・商談の展開・顧客の発言・結果）だけ記録してAIが横断分析で仮説化する、という分業で解く。

## 4. 製品の構造: 共通シャーシ＋プレイ（作戦カード）

全プレイ共通の5段: **①状況の構造化 → ②ナレッジと突合 → ③選択肢の生成（根拠とトレードオフつき）→ ④成果物化 → ⑤結果の記録**。技術基盤は確定済み（Excel/VBA×社内AIリボン、詳細は docs/spec/12・14）。

| プレイ | 主な使い手 | 状態 |
|---|---|---|
| 新規提案（春華堂型） | 営業 | 設計済（spec 15章） |
| 更新診断・アップ/クロスセル | 営業 | v1.1差分で追加（現契約サマリ入力→ギャップ・提案） |
| 壁打ち・座組開発（三菱電機型・対話型） | 営業＋商品部 | **Phase 1**。リボンの会話継続機能で、案件ドシエ＋分析結果＋型・機構を注入した反復対話。ポン出しでなく研ぎ澄ます工程。気づきは受信箱へ |
| 投稿プリフライト診断 | 全員（受信箱の入口） | docs/05 §2 |
| 情報ウォッチ | 商品部（月次） | 新設。下記 §5 |
| 型生成（掛け合わせ） | 商品部（月次・四半期） | 第3弾分析の手順を製品化 |
| BID戦略・高ロス対応 | 商品部UW | Phase 2（案件判断台帳が貯まってから） |

## 4.5 入力ティア（「HPだけでは薄い」への答え）

入力は多いほど有利。ただし収集コストを人に載せない。3ティア構成:
- **T1クイック（15分・収集レシピ8項目）**: 量をこなす更新・新規。恥ずかしくない80点のフロア
- **T2フルドシエ（重要案件・13観点）**: ニュース・SNS評判・競合・業界市況・マクロ・財務・付保コンテキストまで。**収集はディープリサーチ社内アプリへの定型プロンプト集（docs/08）で自動化**し、人はコピペ運搬15分
- **T3壁打ち**: T1/T2の上で対話反復（PL-04）。仮説を研ぎ澄まし、セレンディピティを受信箱で捕獲

S1の入力充足度診断が「いまの入力で出せる水準」と「何を足せば上がるか」を毎回明示する（薄い入力には薄いと言い返す設計）。リスク仮説の生成ロジック（何を根拠にどう判断するか）は仕様書15章§0.5に明文化——保険数理的診断ではなく「根拠が追跡できる仮説の量産」であり、検証は壁打ちと訪問ヒアリング、定量接地はPhase 2（判断台帳×支払データ）。

## 4.6 既存ツールとのすみわけ（グループ長指摘への回答）

部内には既に「既顧客追販リスト」「リスクマップ（2020年7月以降）」がある。競合ではなく分業:

| ツール | 答える問い | 本製品との関係 |
|---|---|---|
| 既顧客追販リスト | **誰に**売るか（ターゲティング） | 更新・追販プレイの**案件選定の入口**。リストで選んだ先をナビで深掘る |
| リスクマップ | 業種×リスクの静的な地図 | **リスクライブラリのシード源**（2020年以降の蓄積をT-90で変換。整備工数を大幅削減） |
| リスク提案ナビ | **この1社に何をどう**提案するか＋学習ループ | 上記2つを入力・素材として使う案件単位の生成エンジン |

## 4.7 出力物の全体像（確定）

1案件から最大4つの成果物が出る: ①**リスク分析表**（S2シート: 仮説×根拠×未然防止策×付保ギャップ） ②**リスクレポート**（S1+S2を整形した文書型・A4数枚。社内検討/顧客提出用） ③**提案書PPT**（保険提案書 または 協業提案書=座組図・三方メリット・実証ステップの2バリアント） ④**ヒアリングシート**（データで取れないもの——他社付保状況・内部事情——を聞く質問リスト。他社付保は競争情報で取得不可と確定したため、定番質問として常設）。

## 5. 情報ウォッチプレイ（「しれっとリリース問題」への答え）

自社・グループのプレスリリース、他社・他業界の動き、法改正は、型ライブラリと適用先候補の最重要の更新源なのに、誰もキャッチアップできていない。月次でこう回す：

1. 巡回: 自社/グループPRページ・主要他社PR・法改正情報を、ブラウザ＋ディープリサーチ社内アプリで収集（公開情報のみ。当面は人が15分で収集し、AIが要約・構造化）
2. 変換: AIが各ニュースを「新アセット？型の実例？適用先候補？判断基準の変化（例: MS側商品との重複）？」に仕分けして受信箱へ
3. 採択: 月次編集会（30分）でナレッジブックに反映 → 翌月から全員の生成に効く

これにより「ヤモリの次の横展開先」をAIが毎月探している状態になる。

## 7. 成功指標（v2）

- 営業側: 提案準備時間の削減率／生成提案の商談投入率（作ったが使われない率の逆）
- 商品部側: 月次で型ライブラリに昇格した件数／受信箱投稿の「プリフライト後修正で生存」率（無駄打ち削減の直接指標）
- 橋そのもの: 案件ログ由来で生まれた型の数（=現場の声→型の変換が動いている証拠）。**これが本PJ固有のKPI**

## 8. これまでの構想からの変更点（差分の明示）

1. 主戦場を新規開拓から**更新案件＋多切り口のプレイブック**へ（v1は新規1プレイのみだった）
2. フィードバックを「刺さった/刺さらない」の主観記録から**事実記録＋AI仮説化**へ
3. ナレッジ源を商品部内（投稿ボックス・マニュアル）から**営業経由の顧客の声（利用の副産物）＋情報ウォッチ**へ拡張
4. ゴールを「素人でも80点」から「**型を生み続ける工場**」へ（80点はPhase 1の中間成果物）
5. 投稿ボックスは廃止せず、プリフライト診断つき受信箱として本製品に吸収
