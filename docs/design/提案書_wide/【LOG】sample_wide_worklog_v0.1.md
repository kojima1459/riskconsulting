## 0. フラグの凡例

| フラグ | 意味 | promptでの扱い |
|---|---|---|
| **F** | フォーマットデータ（テンプレートHTML/CSS）で担保 | 「フォーマット層を改変しない」「所定クラスを使う」の一言で足りる。個別指示は不要 |
| **R** | 参照資料で補足（プロンプト-デザイン.txt、入力レポート、用語対訳表など） | 資料を添付・参照させる。promptに転記しない |
| **P** | promptに明記が必要 | 生成AIが内容を判断するルール。外部情報からは導けない |
| **C** | 生成後チェック項目 | promptの最終チェック節、または別工程のQAで実施 |
| **N** | 今回の作業手順上の事項 | promptには不要 |

判断基準：フォーマットや参照資料から自然に定義が補足されるものは、promptに細かく書かない。promptには「内容の判断ルール」と「一貫性のルール」だけを残す。

## 6. 次段階への仕分け（案）

### 6.1 フォーマットデータに含めるもの（F）
- `#format-css`（原本値＋ヘッダータイトル補正1.5px）、`#viewer-css`、`#content-css`
- マスター4種のHTML断片（表紙／セクション扉／本文／裏表紙）と、本文コンポーネントの雛形＋クラス一覧（用途・想定行数）
- 改善候補：ページ番号の自動採番（JS化すればpromptから「ページ番号を振る」指示を外せる）。スライド種別ごとの骨組み（要旨・判断事項・リスク一覧など）を雛形として同梱すれば、promptの構成指示も短くできる
- 表示機能を原本と揃える場合は、フォーマットデータを「Marpテーマ CSS（`sample_wide/marp/shunkado-wide.css`）＋ Markdown 雛形」として持ち、生成AIには「1スライド＝HTML断片、`---` 区切り、ノートはHTMLコメント」で書かせて marp-cli でビルドする（第8章）

### 6.2 参照資料として渡すもの（R）
- `プロンプト-デザイン.txt`（設計原則・デザイン規律・出力前チェック）
- 用語対訳表（保険会社用語・略語 → 顧客向け表記）
- 入力レポート（生成対象）

### 6.3 promptに書くこと（P）
1. 読み手と立場：顧客の経営層向け。宛先「御中」、本文「貴社」、自社「当社」
2. 禁止パターン：否定構文による枠組み語り、社内ラベル（提案の核・対話の順序・攻めの・発散段階など）、顧客の認識を評価する表現、当社の作業を主語にした説明（方法論・判定・開発・組成）
3. 用語：対訳表に従う。略語は本文で日本語説明、用語集脚注に頼らない
4. 事実の扱い：入力の事実だけを使い、足さない。入力から導ける整理（比較表・対応表・参照）は可。契約未確認・仮評価の断り書きを保持。出典は本文で使ったものだけ
5. 一貫性：テーマ名と順序、評価ラベル、3分類ラベル、カテゴリー名を全頁で統一。IDを使う場合は一覧を必ず置く
6. 標準構成：表紙→要旨（3テーマ＋実数の指標帯＋前提＋構成）→各Section→提案テーマ→進め方（役割・費用の扱い）→本日ご判断いただきたいこと→ご共有いただきたい事項（優先印）→巻末リスク一覧→前提と出典→裏表紙
7. 1枚の設計：見出しは結論の一文（1行に収まる45文字程度、朱の強調は1箇所）、1枚1メッセージ、データ左・示唆右
8. 分量の上限：本文コンポーネントの想定行数を超えない（表は8行程度、カードは4〜6行）
9. 当社サービスの記載は入力に根拠がある場合のみ

### 6.4 生成後チェック（C）
- はみ出し・脚注との重なり・ラベル重なりがないか（PDF化して目視）
- 見出しが1行に収まっているか
- ID・テーマ名・ラベルの全頁一致、出典の本文照合
- 禁止パターン・保険会社用語の残存スキャン
- 読ませたい本文が14px相当を下回っていないか

| Marp既定テーマの干渉 | `@import 'default'` により表のゼブラ背景・格子罫線、定義リストの斜体・字下げ、`word-wrap:break-word` によるID折返し、段落余白が崩れた。テーマ末尾に打ち消しルール（[3]節）を追加して解消 | **F** | テーマCSSに固定済み。原本と同じ `default` 継承を保ったまま本文コンポーネントを守る |
| 発表者ノート | 各スライドのタイトル＋見出し文をHTMLコメントとして自動付与（21枚）。発表者ビューで現在／次スライド・ノート・タイマーを確認できることをスクリーンショットで検証 | **P**（任意） | ノート内容は生成AIが書く要素。「見出し文をノートにする」程度の一文で足りる |
| フォント | テーマ内で Google Fonts を `@import`（Marpitがそのまま通す）。フォールバックは原本の指定を維持 | **F** | テンプレートに固定 |
| 格納 | `【SAMPLE-Wide-Marp】…v0.1.html/.pdf` を別名で追加。単体表示版（`【SAMPLE-Wide】…`）は無変更 | **N** | 作業上の取り決め |

## 10. 検証：Marp形式のスライドを marp-cli なしで再現できるか（2026-09-03）

質問：Marp形式のスライドデータは、HTMLフォーマットとLLMへのpromptだけで、marp-cli を使わずに再現できるか。

**結論：可（条件付き）。** 固定のHTMLシェルに、スライド本体のHTMLと発表者ノートを差し込むだけで、marp-cli の出力と同一の文書になることを実データで確認した。

### 10.1 根拠（実測）

| 観点 | 確認結果 | フラグ |
|---|---|---|
| 出力の構造 | Marp出力は「固定部分」（表示機能CSS、テーマCSS、操作パネルの要素、スクリプト2本）と「内容依存部分」（各スライドを包む svg→foreignObject→section ラッパーの中身、ノート用 div、タイトル）に完全に分かれる | F |
| 変換の素通し | スライド本体をHTMLで書いているため、Marpの変換は事実上素通し。22枚中17枚は完全一致、残り5枚の差は自己終了タグ表記（`<col />`）のみで表示に影響なし | F |
| 組み立て検証 | シェル＋ソースのスライド＋トークスクリプトから組み立てたHTMLは、空白と自己終了タグを正規化すると marp-cli 出力と一致（503,556文字同士）。ページ移動・一覧・発表者ビュー・全画面は固定部分のスクリプトが担うためそのまま動く | F |
| Twemoji／自動縮小 | 出力マークアップ中に Twemoji 画像や自動縮小要素は0件（CSS・JS内の文字列のみ）。本フォーマットでは変換の影響がない | C |

| 部分 | サイズ |
|---|---|
| 文書全体 | 約500KB |
| 画像のdata URI（テーマCSS内） | 約300KB |
| テーマCSS（画像を除く） | 約80KB |
| 表示機能CSS | 約25KB |
| スクリプト2本 | 約34KB |

### 10.2 成り立つための条件

| 条件 | 内容 | フラグ |
|---|---|---|
| シェルはコンパイル済み産物 | 一度 marp-cli で生成したもの。テーマCSSはセレクタに接頭辞（`div#\:\$p > svg > foreignObject > section`）が付いた形に変換され、Marp既定テーマもインライン化済み。デザイン変更時は接頭辞付きで直接編集するか、marp-cli でシェルを再生成する | F / N |
| LLMの出力範囲 | シェル全体（圧縮JS・Base64画像を含む約500KB）をLLMに書かせるのは非現実的で、転記ミスで壊れる危険が高い。LLMの出力は「スライド本体のHTML＋ノート」に限定し、結合はテンプレートへの差し込み（数行のスクリプト、または手作業の貼り付け）で行う | **P** |
| 「フォーマット＋promptだけ」の解釈 | フォーマットを4断片（先頭部、スライドラッパー、ノートラッパー、末尾のスクリプト）として持ち、LLMには本体だけを書かせ、結合は機械的に行う形なら可能。結合までLLMにやらせることは原理上可能でも推奨しない | P / N |

### 10.3 marp-cli なしでは再現できないもの（本フォーマットでは未使用）

- Markdown記法からHTMLへの変換（LLMがHTMLで書く限り不要）
- 見出し・コードブロックの自動縮小要素の挿入、絵文字のTwemoji画像化、`paginate` 等のディレクティブ処理
- PPTX出力。PDFは bespoke 出力に印刷用CSSが含まれるため、ブラウザの印刷で代替可能

### 10.4 補足と次段階への含意

- 固定部分のスクリプトには MIT ライセンス表記が含まれており、そのまま保持すれば再利用に問題ない
- 次段階の分担：フォーマットデータ＝4断片＋クラス一覧（F）、prompt＝本体とノートの生成ルール（P）、結合＝marp不要の小さなスクリプト（N）、marp-cli＝デザイン変更時のシェル再生成のみ（N）
