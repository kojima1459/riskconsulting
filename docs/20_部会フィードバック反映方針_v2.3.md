## 1. FBの本質（何が言われたか）

### 内田部長（プロジェクトオーナー）
- **「一発完結」ではなく「対話による成長型」**: 公開情報から完璧な提案書を一発で出そうとするな。①初回=全体像・仮説＋ヒアリングシート → ②営業が対話で生データを獲得 → ③再入力で提案が深化、の3ステップ。AIは「自動帳票出力機」ではなく「営業の作戦参謀（壁打ち・ロープレ相手）」
- **ビジュアライズと強弱**: テキストの羅列では営業が説明できない。エグゼクティブサマリー＋2軸リスクマップ（頻度×損失規模）＋グラデーションで、経営層が一目で優先順位を掴める形に
- **ハザードマップ連携**: 企業情報だけでは自然災害リスクは出ない。拠点住所×公開ハザード情報で「貴社◯◯工場は浸水想定3m」という客観根拠を初回から出す
- **話法・タイミング・ロープレ**: 提案書だけでなく「どの切り口で・いつ・どう切り出すか」のアドバイスと壁打ちを
- **対象**: ホールだけでなく中堅・地域有力企業も。保険移転だけでなく回避・低減・保有を含む総合リスクコンサル

### 高橋PL（5点）
1. **MECE軸**: 「事業内容×既存保険」のリスクマップ＋定型商品でカバーされないニューリスク＋保険を使った本業拡大（三菱電機型）の3軸で。※参考資料: リスコンポータルのリスマネパンフ・業種別リスクマップチラシ・法人版リスクマップ／提案書サンプル（商C企）／提案書ライブラリ（企金営開）——散在情報の集約自体が価値
2. **シナリオベース・財務インパクト**: 決算公告の純資産を踏まえ「損害◯億円に対し保険料◯万円で備える」。保険ありきでない財務目線。VIEW情報の取込も
3. **フロー**: ①初期収集→②リボン分析→③**追加リサーチプロンプトをGPTに作らせる**→④統合分析→⑤レポート・提案書ドラフト
4. **アーキテクチャ**: UIは作り込まずモジュール開発＋最低限IO。「全体像立案AI→種目特化AI」の2層（データ相互共有）
5. **引受目線**: ニデックのD&Oは受けられる状況にない。網羅性のため分析には持ちつつ、**提案を控えるリスクを理由とともにレポートに明記**すべき
6. **出力**: 当面HTMLでよい（コードだけで見栄えが出る）。方針が固まったらデザインシステム化。Word/PPTは最後の最後

### 廣瀬さん
- フリート・労務等は**業種ごとの事故傾向・刺さる施策の「型」**が存在する（運送=バック事故×ドラレコ、建設=第三者賠償×下請管理…）。業種コード起点のナレッジレコメンドに組み込むべき

### 高橋プロトタイプから抽出した構造（初回レポートの標準型）
サマリー3テーマ(PROTECT/RESILIENCE/GROWTH) → 企業理解(事実/推定/要確認タグ) → リスクユニバース10分類(MECE) → 2軸マップ(Impact×Likelihood 5×5) → カバレッジ表(移転可能性3値: cover/partial/hard＋ギャップ＋管理策) → ニューリスク → 攻めの保険活用 → 提案ストーリー → ヒアリング14問 → 出典・免責。
**データ(JSON配列)とテンプレート(HTML/JS)が分離されており、そのままS2/S3のJSON→固定テンプレ流し込みに載る。**

### 出力デザインの制作方法（開発PM判断）

レポートのデザインは**コードファースト（このリポジトリのHTMLテンプレート）を正**とする。理由: 最終成果物はVBAが吐くHTMLテンプレートであり、デザインツール上の絵はテンプレートに翻訳し直す工数が二重にかかる。高橋プロトが既にコードで存在し、DADS版が示すとおり「テーマCSS差し替え」で見た目は切り替えられる。Claude Design等のビジュアル編集は、部長・高橋さんと**見た目の合意形成をする局面のオプション**として使う（確定後にテンプレへ反映）。
