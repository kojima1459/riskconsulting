# 製品構想書: リスク提案ナビ（仮称）

**版**: v0.1（構想・上流工程。実装前）
**対象読者**: 内田部長・AIリスクコンサルティングPJメンバー・営業企画
**位置づけ**: 内田部長のアイデア「企業名や業種を入力するだけで、事業内容・潜在リスク・提案すべきリスクコンサル施策を自動分析し、提案書の骨子まで短時間で生成する」を、当社の実環境（OpenAI API利用可・VBA開発可・Web検索不可）で具現化するための要件定義・基本設計。

---

## 1. コンセプト

> **「プロンプト配布」ではなく「ナレッジが増えるほど賢くなる提案生成マシン」。**

- 形態: **Excelマクロブック（.xlsm）1本**を製品として配布・版管理する。技術スタックは社内PoC中のVBA製NotebookLM風ツールと同一（VBA × OpenAI API）で、実証済み。
- 差別化の本体はプロンプトではなく**社内ナレッジとの結合**: 実在のリスクコンサルメニュー・保険種目・過去の勝ち提案にグラウンディングした出力だけを返す。
- 属人化解消は「ツール」ではなく「**ナレッジ・フライホイール**」（§5）で実現する。ツールはその器。

### 解決する課題（議事録との対応）
| 議事録上の課題 | 本製品での打ち手 |
|---|---|
| 営業の事前調査に膨大な時間（春華堂の例） | 入力15分 → 分析・骨子・ヒアリングシートまで自動生成 |
| 提案レベルの属人化 | 勝ち提案ライブラリを全員の生成に自動注入（§5） |
| メンバーのAIリテラシー・実装スキル育成 | プロンプト・ナレッジ整備・評価をPJメンバーが分担して「作る側」を経験 |

## 2. スコープ

### やること（Phase 1）
- 公開情報（企業HPテキスト・有価証券報告書の「事業等のリスク」章・営業の下調べメモ）を入力として、①企業プロファイル、②潜在リスク仮説、③実在メニューに紐づく提案、④提案書骨子＋PPT、⑤初回訪問ヒアリングシート、を生成する。

### やらないこと（明確に外す）
- Webの自動クロール（APIがWeb検索不可。人がブラウザで収集して貼り付ける。社外公開情報の下調べには既存のディープリサーチ社内アプリを補助的に使ってよい）
- 顧客の非公開情報・個人情報の投入（Phase 1では公開情報のみ。§8の確認事項が解決するまで拡大しない）
- 保険料試算・引受判断（UW判断は本製品の対象外。あくまで提案準備の高度化・効率化）

## 3. アーキテクチャ

```
┌─ リスク提案ナビ.xlsm ──────────────────────────────────────┐
│                                                            │
│ [入力シート]                「ナレッジブック(別ファイル)]   │
│  ・企業名 / 業種(選択式)      ・業種×リスクライブラリ       │
│  ・HPテキスト貼付欄           ・リスクコンサルメニュー一覧  │
│  ・有報リスク章貼付欄(任意)   ・保険種目マッピング          │
│  ・営業メモ欄(任意)           ・成功事例ライブラリ          │
│       │                              │                     │
│       ▼                              ▼                     │
│  Step1 企業プロファイル構造化 (JSON)                        │
│  Step2 リスク仮説生成 (頻度×強度×根拠×確認質問)  ←ナレッジ注入│
│  Step3 提案マッチング (実在メニュー・種目に限定)  ←ナレッジ注入│
│  Step4 骨子生成 (スライド構成JSON)                          │
│       │                                                    │
│       ├─→ 固定VBAがPPT自動生成（コード生成はしない）        │
│       └─→ 初回訪問ヒアリングシート出力                      │
│                                                            │
│ [フィードバックシート] 商談結果・刺さった/刺さらなかった     │
│        └──→ 成功事例ライブラリへ還流（月次レビューで昇格）  │
│                                                            │
│ [設定シート] APIキー参照先 / モデル名 / バージョン           │
└────────────────────────────────────────────────────────────┘
          │ HTTPS (MSXML2/WinHTTP)
          ▼
   OpenAI API (Chat Completions / Structured Outputs)
```

### 設計原則
1. **多段パイプライン・中間出力の可視化**: 各Stepの出力はJSONとしてシートに残す。人（特にベテラン）が中間結果を修正して次Stepを再実行できる。この「修正差分」こそ暗黙知の採取ポイント（§5）。
2. **グラウンディング必須**: Step3は「ナレッジブックのメニュー一覧に**実在するものからのみ**選定。適合なしなら『該当メニューなし・新サービス検討候補』と明示する」制約を課す。幻覚提案を構造的に防ぐ。
3. **PPT生成は事前ビルド済み固定VBA**: AIが返すのはスライド構成データ（JSON）のみ。コードを都度生成・実行させない（セキュリティ教育との整合・保守性）。
4. **APIキーの分離**: キーは本体に埋め込まず、設定シートが参照する外部ファイル（またはユーザー環境変数）から注入。当面の**中央処理型**（開発者が案件を回す）と、将来の**配布型**（各自がキー取得）を同一本体で両対応。
5. **「わからない」を価値にする**: 各Stepで確信が持てない項目は推測で埋めず「要確認」として出力し、Step4でヒアリングシート（初回訪問で聞くべき質問リスト）に変換する。AIの限界を商談の武器に変える。

## 4. パイプライン仕様（各Stepの入出力）

### Step 1: 企業プロファイル構造化
- **入力**: 企業名、業種、HPテキスト、有報リスク章（任意）、営業メモ（任意）
- **出力（JSON）**: 主力事業 / 製造・販売プロセス / 主要拠点と設備 / 原材料・サプライチェーン / 顧客層・販路 / 従業員構成の推定 / 経営上の特記事項 / **情報の欠落リスト**
- **品質規律**: 入力テキストに根拠のない事実は書かない。推定には `(推定)` タグを付す。

### Step 2: リスク仮説生成
- **入力**: Step1のJSON ＋ ナレッジブック「業種×リスクライブラリ」の該当業種行
- **出力（JSON）**: リスク項目ごとに { カテゴリ（財物・自然災害 / 製造・品質・賠償 / 労務・人為 / BCP・サプライチェーン / サイバー・情報 / 経営・戦略 ※Geminiの4分類にサイバーと経営を追加した6分類）, 発生シナリオ, 頻度(高中低), 強度(大中小), 根拠（入力のどの記述から導いたか）, 現地・ヒアリングで確認すべき点 }
- **品質規律**: この企業「特有」であること。業種一般論はライブラリ由来と明示し、企業固有の記述に紐づくものを優先表示。

### Step 3: 提案マッチング
- **入力**: Step2のJSON ＋ ナレッジブック「リスクコンサルメニュー一覧」「保険種目マッピング」「成功事例ライブラリ」の該当業種・類似規模の事例
- **出力（JSON）**: 提案ストーリー3本。各 { 刺さる理由（顧客の言葉で）, 対応リスク, 提案メニュー（実在IDで参照）, 関連保険種目, 類似成功事例の参照, 想定される反論と切り返し }
- **品質規律**: メニューIDの実在チェックをVBA側でも検証（AI出力の照合）。該当なしは「なし」と返させ、新サービス候補として別枠に記録（商品部にとっては**新商品開発のシーズ検知**にもなる）。

### Step 4: 骨子生成・出力
- **出力1**: スライド構成JSON → 固定VBAがPPT生成。構成は5枚: ①貴社の事業環境の理解（=「御社を調べてきた」の証明）②潜在リスクマップ（頻度×強度の2軸）③同業の事故・トラブル事例 ④当社のご支援メニュー（実在サービス）⑤次のステップ（ヒアリング項目の提示）
- **出力2**: 初回訪問ヒアリングシート（Step1の欠落リスト＋Step2の確認点を質問文に整形）

## 5. 属人化解消の本体: ナレッジ・フライホイール

「80点までは電子データにあるが、80→100点（提案のセンス・成功事例）は属人化して共有されていない」という現状認識に対する直接の打ち手。**ツール開発と同格のPJタスク**として扱う。

1. **エキスパートインタビュー（初期装填）**: ベテラン2〜3名に過去の勝ち提案・負け提案を語ってもらい、「業種 × 顧客状況 × 提示リスク × 提案 × 決め手（なぜ刺さったか）」の型に構造化して成功事例ライブラリへ登録する。内田部長の春華堂の経験そのものが第1号エントリになる。
2. **運用ログによる継続採取**: 全案件の生成結果と、営業からのフィードバック（刺さった/刺さらなかった/顧客の反応）をフィードバックシートに記録。月1定例で「今月の勝ちパターン」をレビューし、良いものをライブラリへ昇格させる。
3. **自動還流**: ライブラリに昇格した事例は、以後**全員**のStep2/Step3の生成に自動注入される。＝ ベテランの暗黙知が、翌月から若手の提案書に反映される。

この構造により「成功事例の共有がなされていない」問題を、研修や掛け声ではなく**日常業務の副産物として蓄積される仕組み**で解決する。

## 7. 品質評価（PoCの合否基準）

ベテランUW/リスコン担当が各出力を5段階で採点する3軸ルーブリック:
1. **網羅性**: この企業で見るべきリスクの見落としがないか
2. **具体性**: 業種一般論でなく、この企業固有の記述になっているか
3. **実売性**: 提案が実在メニュー・種目に正しく紐づき、そのまま商談に持ち込めるか

加えて所要時間（従来の事前準備時間との比較）を計測し、キックオフで約束する「準備時間の大幅短縮」を定量で示す。

## 8. 要確認事項（情シス・部内。Phase 1着手前に回答が必要）

1. **OpenAI APIの利用規約・社内ルール上、業務データ（公開情報の加工）の送信可否**。および将来的に顧客非公開情報を扱う場合の条件（Enterprise契約・オプトアウト設定の有無）
2. **APIキーの配布可否**: PJメンバー・営業への配布が可能か。不可なら中央処理型で運用継続
3. **マクロブックの配布ルール**: 署名の要否、配布経路（部内ポータル等）
4. **ディープリサーチ社内アプリの位置づけ**: 下調べ補助として公式に組み込んでよいか（入力制約の正確な範囲）

## 9. リスクと対策（本プロジェクト自体の）

| リスク | 対策 |
|---|---|
| 出力が一般論で現場が使わなくなる | ナレッジ注入を必須とし、Phase 1でベテラン採点をゲートにする |
| ナレッジ整備が続かない | 月1定例の議題に固定。フィードバック記入を「生成を使う条件」にする |
| APIキー配布が認められない | 中央処理型（依頼→翌日納品）で価値実証を先行。件数が捌けなくなった実績を持って情シスと交渉 |
| Excel/VBAの限界（同時利用・保守） | Phase 3の全社基盤移植を最初からロードマップに明記。Excel版は使い捨てにしない（動く仕様書） |
