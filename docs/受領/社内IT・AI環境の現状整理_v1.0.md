## 1. 要約

1. **利用できるAIツールは、持株ビジネス部が全社員向けに提供する4種（マルチモーダルChat、RAGアプリ、Deep Research、AIリボン）である。** いずれも単独では業務を完結できず、合算しても一般提供サービスの機能水準に届かない。ツール間のデータ受け渡し機能はない。
2. **内製は AIリボン（Office アドインが提供する専用VBA関数で Azure OpenAI API を呼び出す）＋VBA で行う。** 中核モデルは GPT-5.5、GPT-5.4 mini、GPT-5.4 nano で、トークン上限はモデル上限まで使える。AI へのアクセスはアドインの VBA 関数の呼び出しに限られ、Azure OpenAI API に直接リクエストを送ることはできない。そのため、関数が対応していない API 機能（Function Calling、JSON Schema による構造化出力等）は利用できない。レート制限は不明だが厳しくないと想定し、設計上は勘案しない。アドインは3か月程度で更新され、互換性は基本的に担保される。
3. **Web 情報の取得経路は Deep Research のみで、AIリボンからは使えない。** Deep Research は入力2,000文字・添付不可・顧客情報入力不可で、結果は人がコピーして Excel ツールに貼り付ける。内部方式は不明（入手不可）である。業務PCのブラウザ（Edge）から社外インターネットは検索できず、仮想ブラウザ経由の手作業に限られ、ブラウザ操作の自動化はできない。
4. **開発手段は VBA に限られる。** Power Platform（Power Automate、Power Apps 等）、Power Query、Office Scripts、Python・Node.js・Git・WSL・PowerShell・Copilot Studio・Microsoft 365 Copilot は不可（例外申請なし）、外部通信はプロキシで制限され任意の API は不可である。ソース管理・テスト環境はなく、業務環境で開発する。
5. **利用者環境は全部門共通（Windows 64bit、Office 32bit）で、自作アドイン・マクロ付きブックの配布が可能である。** 配布は SharePoint またはポータル、更新通知はポータルで行う。
6. **データ取扱は「Deep Research 以外にはあらゆる情報を投入可。Deep Research には顧客情報・センシティブ情報・機密情報を入力不可（企業名・公開情報は可）」である。** 持株提供ツールを基盤にする限り利用申請は不要である。

## 3. 開発環境・開発手段

### 3.1 開発手段の可否

| 手段 | 可否 | 備考 |
|---|---|---|
| Office VBA（AIリボンの関数を呼び出す） | 可 | 唯一の内製手段 |
| Power Platform（Power Automate、Power Apps 等） | 不可 | ― |
| Power Query、Office Scripts | 不可 | ― |
| Copilot Studio、Microsoft 365 Copilot | 不可 | ― |
| Python、Node.js、Git、WSL、エージェント型AI（Claude Code、Codex 等） | 不可 | 例外申請の制度もない |
| コマンドライン | cmd.exe は実行可能。PowerShell は不可 | ― |
| PDF処理用の補助部品 | MyBookshelf に同梱の Ghostscript を VBA から呼び出す実装がある | PDFの文字抽出・画像化に使用。必要部品と配置条件は第4.3節を参照 |
| VBA からの外部通信 | プロキシで制限 | AIリボンが接続する持株の Azure OpenAI・社内API 以外の任意の API（社内システム、SharePoint REST 等）は利用不可。社内ネットワーク内の端末間通信（P2P）は可能なことを確認済み。許可範囲の詳細は不明で、社内ネットワークは許可されているものと想定 |
| Azure OpenAI API への直接リクエスト | 不可 | AI へのアクセスはアドインの専用関数の呼び出しに限られる（第4.1節） |

任意の API が使えないため、ツール間のデータ連携は SharePoint 上のファイル（CSV 等）を介する方式か、社内ネットワーク内の端末間通信（P2P）に限られる。環境の拡張（AIリボンでの Webサーチ、統制下での内製開発環境または LLM アプリ開発基盤）は所管部門へ要望済みだが、実現時期は未定である。

### 3.2 ブラウザ環境と社外インターネット接続

| 項目 | 内容 |
|---|---|
| ブラウザ | Microsoft Edge。特段のアドインは導入されていない |
| 社外インターネットの検索 | 業務PCのブラウザからは不可。仮想ブラウザ経由でのみ検索・閲覧でき、認証等を挟むため自動化の余地はない |
| ブラウザ操作の自動化 | 不可。Edge は Internet Explorer のように VBA から直接操作（COM オートメーション、DOM 操作）できない |

したがって、Web 情報を AI 処理に取り込む経路は Deep Research（第2.3節）に限られる。人が仮想ブラウザで閲覧した情報をコピーして Excel ツールに貼り付けることは可能だが、VBA によるスクレイピングやブラウザ自動操作による収集はできない。

### 3.3 開発プロセスの前提

| 項目 | 内容 |
|---|---|
| 開発できる人員 | VBA＋AIリボンでの開発ができるのは2名 |
| ソースコードの管理 | 特段管理していない（管理不要と判断） |
| 開発・本番の切り分け | テスト用の環境・データはない。通常の業務環境で開発する |

版管理がなく本番と同じ環境で開発するため、次の3点を各ツールの運用ルールに含める。いずれも追加の仕組みを要しない。

- 配布したブックは版番号付きのファイル名で SharePoint に残し、直前の版に戻せるようにする。
- 開発中の動作確認では、AIリボンの呼び出しが持株側に記録されることを踏まえ、入力にダミーデータを使う。
- シート内のシステムプロンプトと参照データの更新手順を文書化し、開発者以外でも更新できるようにする。

## 4. AIリボン（Office アドイン）の仕様

### 4.1 提供形態と運用条件

| 項目 | 内容 |
|---|---|
| 提供元・利用範囲 | 持株ビジネス部が提供。全社員が利用可能 |
| 対応アプリケーション | Excel、Word、PowerPoint、Outlook。ソース上もアプリケーション名をツール名に付けてログ記録する作り |
| 呼び出し方法 | アドインが提供する専用VBA関数を、利用者側のブック（xlsm 等）から `Application.Run` 等で呼び出す。AI へのアクセス経路はこの関数呼び出しに限られ、自作の VBA から Azure OpenAI のエンドポイントへ直接 HTTP リクエストを送ることはできない。したがって、指定できるパラメータは関数の引数として公開されているものに限られる |
| 利用できない API 機能 | 関数が対応していない API 機能は利用できない。具体的には、OpenAI API の Function Calling（`tools`）、JSON Schema 出力（`response_format`）、ストリーミング出力。構造化出力はプロンプト指示＋VBA 検証で実現する |
| モデル更新 | 事前に通知される |
| 利用期限・更新 | アドインに利用期限日が設定されている（ver202606 は 2026-09-30）。期限後は「最新版をダウンロードして利用ください」と表示され利用できない。更新サイクルは3か月程度で、互換性は基本的に担保される前提。互換性がなくなる場合は内製ツール側を更新する |
| 利用同意 | 初回起動時に利用同意画面が表示され、同意状態は端末の一時フォルダに記録される |
| 既定モデルの保存先 | 利用者が選択したモデル名は端末の一時フォルダのテキストファイルに保存される。一覧にないモデルが指定されていると既定モデルに戻る |
| エラー時の対応 | レート制限は不明だが厳しくないと想定し、設計上は勘案しない。エラー時は再度リクエストを送信する（所管部の案内） |

### 4.2 主要関数

| 関数 | 内容 | 備考 |
|---|---|---|
| `ChatGPT(text, roleSystem, Temperature, MaxTokens, Wait, optModel, prevU, prevA, toolN, reasoning_effort, verbosity)` | テキスト生成の中核関数。システムプロンプト、モデル、過去のユーザー／アシスタント発話（`;;;` 区切りで新しい順）、応答待ち秒数、GPT-5 系の `reasoning_effort`（minimal／low／medium／high）と `verbosity`（low／medium／high）を指定できる | Temperature・top_p は GPT-5 系・o 系・codex 系には送信されない。会話履歴は呼び出し側が保持して渡す |
| `ChatGPTV(text, imageInputs, roleSystem, resolution, toolN)` | 画像入力（Base64 JPEG、カンマ区切りで複数可）付きの生成。解像度 low／high | モデルは GPT-5.5 固定 |
| `GetEmbeddings(text)` | Azure OpenAI Embeddings API（text-embedding-3-small、1,536次元）でベクトル化し、ベクトル値の文字列を返す | ― |
| `CosineSimilarity` 系 | ベクトル間のコサイン類似度を VBA で計算 | RAG の検索部分 |
| その他 | 音声文字起こし（Whisper）、音声合成（tts、tts-hd、gpt-4o-mini-tts、VOICEVOX）、画像生成（gpt-image 系、Stable Diffusion 系）、翻訳、表OCR、クラスタリング、汎用文書チェック、Word／HTML への出力補助 | リボンメニューから利用。内製ツールからは関数を直接呼ぶ |

### 4.3 入出力の条件

| 項目 | 内容 |
|---|---|
| トークン上限 | 1回の呼び出しに特段の制限なく、モデル上限まで使用できる。`MaxTokens` は出力上限として任意指定 |
| 画像・PDF・Excel の投入 | VBA で本文の抽出や画像化等の前処理を行い、テキストまたは画像として AIリボンの関数に渡す。画像は `ChatGPTV` で送信する。PDFの文字抽出・画像PDFの文字起こしは、下記の MyBookshelf の実装を参照 |
| 応答待ちと再送 | 既定120秒、モデルにより300〜1,200秒（pro 系は900秒）。待ち時間を超えると同じリクエストを自動で再送するため、長時間処理では二重実行に注意 |
| コンテンツフィルター | Azure OpenAI の責任あるAIポリシーに該当すると「content_filter に該当しました」を返す。事故・賠償・疾病等の記述が該当する可能性があり、検証項目に含める |
| API 方式 | 通常は Chat Completions API。pro 系・codex 系は Responses API（`store: false` で履歴を保存させない） |

**PDFの前処理（MyBookshelf の実装）**

`Final20260909MyBookshelf_配布` には、Excel VBA と同梱の Ghostscript を組み合わせたPDF読取処理がある。

| 項目 | 実装・利用条件 |
|---|---|
| 文字データのあるPDF | Ghostscript の `txtwrite` で本文を抽出する。抽出できない場合に Word／Acrobat 経由の抽出を試す実装もあるが、各アプリケーション経由の処理は利用端末の環境に依存する |
| 画像PDF（スキャン文書等） | Ghostscript でページごとに JPEG 化し、AIリボンの `Base64FromFile` で画像を文字列化してから `ChatGPTV` で1ページずつ文字起こしする。文字起こしには AIリボンへの接続が必要で、処理時間・AI呼出回数は対象ページ数に応じて増える |
| 必要な補助部品 | 配布版に Ghostscript 10.03.1（32bit）の `gswin32c.exe` と `gsdll32.dll` を同梱。`MyBookshelf.xlsm` と同じ階層に `Ghostscript` フォルダを置き、その中に両ファイルを配置する。配布物はフォルダ構成を保って展開する |
| 実行・配置条件 | VBA の `Shell` から Ghostscript の実行ファイルを起動する。PDF前処理に Python／PowerShell は使用しない。Ghostscript を実行でき、作業用の一時フォルダに書き込めることが必要。同梱配置で見つからない場合は、設定 `ghostscript_path` に実行ファイルのフルパスを指定できる |

確認対象は、指定配布版の `MyBookshelf.xlsm` のPDF関連VBA（`modExtractorPdf`、`optGsTxt`、`optVision`、`optOcrCore`、`optOcrPage`、`optGsProc`）、配布 `README.txt`、`Ghostscript/README.txt` である。本項は配布物・ソースの確認に基づく実装方式の整理であり、PDF処理やOCRの動作・品質の検証結果を示すものではない。

### 4.5 RAG の実装方式

- Azure OpenAI の Embeddings API を使用する。登録できる文書の形式は VBA で処理できる形式による。容量・件数に制限はない。
- 文書の登録先は社内サーバや SharePoint である。業務PCはシンクライアント環境であり、ローカル保存データは環境終了時に削除される前提である。一部にデータが保持されるフォルダはあるが、削除を回避してデータを残す目的での利用は社内ルール上できない。参照文書・ベクトル・会話履歴等の継続して保持するデータは、社内サーバや SharePoint 等への保存を前提とする。
- 登録文書は自動的には共有されず、共有するには SharePoint 等の共有フォルダに置くか、社内ポータルのアプリ基盤に登録して全社公開する。本社部門は専用の本社サーバを使用できるが、営業部門との共有や本社部門間の共有には使えない。
- SharePoint をエクスプローラーで表示し、そこから Excel ブックを開く方法で、VBA による当該ブックの読み書きが可能なことを確認済みである。この確認は SharePoint REST 等の API 利用とは別の、ファイルを開いて利用する経路に関するものである。外部 CSV の読み込み・更新方式は、下記のとおり先行ツールの設計時に定める。
- 実装は、`GetEmbeddings` でチャンク単位にベクトル化し、ベクトルを Excel のセルに文字列として保存、検索時に VBA でコサイン類似度を計算する方式である。ベクトルデータベースは使わない。文書量が増えると Excel のサイズ・メモリ（Office 32bit）と VBA の計算時間が制約になる。
- 既存ツール（第5.1節）は参照データをシート内に保持しているが、分量の増加に備えて実行ブック外の CSV 形式等の DB に移す方針である。外部 CSV に移す際の形式（列構成・文字コード）、置き場所、読み込み方式、文書更新時のベクトル再生成手順は、最初に移行するツールの設計時に決め、以降のツールでも同じ形式を用いる（第8章 #10）。

### 4.6 ログと接続先

- すべての生成呼び出しは、持株側のログ収集API（社内ホスト）に記録される。記録項目は、日時、利用者（Active Directory の氏名・役職・メール）、ツール名・版、システムプロンプト、質問、回答（各4,096文字まで）、エンドポイント、HTTP ステータス、エラー・コンテンツフィルター情報、入出力文字数、モデル名、トークン数である。ツール名の末尾を `_ss` にすると質問・回答は「出力不可」として記録される。
- 持株側のログは当部から確認できず、確認手段もない。効果測定・品質監視に必要な利用記録は各ツール側で VBA により実装する必要がある。
- 接続先は、Azure OpenAI の持株リソース（テキスト生成・Embeddings は米国 East US 2 リージョン、音声合成は Sweden Central、画像生成は West US 3）と、持株テックユニットの社内API（Whisper、VOICEVOX、Stable Diffusion）である。データの保存・学習利用・ログ保管は持株の管理下にあり、当部で管理する必要はない。

- 持株のAIガバナンス関連ガイドライン・規程は、本PJでは考慮不要。

### 7.3 AI生成物の表示と確認

| 提示先 | ルール |

| 顧客提示 | 全件、利用者による確認が必須。確認を経た成果物には AI生成の表示は不要 |

## 8. ツール設計時の環境チェックリスト

要件定義書作成ガイドライン v1.0 の共通項目と併せて、環境に依存する次の事項をツールごとに確認する。

| # | 確認事項 | 観点 |
|---|---|---|
| 1 | Web 情報への依存 | 公開情報の収集を AI に任せる工程があるか。Deep Research の手動実行（2,000文字以内、10〜15分／回、公開情報のみ）と人による貼り付けを前提とした手順・所要時間を定義しているか。ブラウザ操作の自動化やスクレイピングを前提にしていないか |
| 2 | 入力量と分割 | 投入する文書量がモデル上限に収まるか。Deep Research への指示は2,000文字以内に分割されているか |
| 3 | モデルの指定 | 中核3モデルのどれを工程ごとに使うか。`reasoning_effort`・`verbosity` の設定。Temperature が GPT-5 系では効かないことを踏まえた再現性の考え方 |
| 4 | 会話履歴・状態の保持 | 前段の結果を引き継ぐ必要があるか。履歴を VBA 側で保持して `prevU`／`prevA` に渡す設計か |
| 5 | 構造化出力 | JSON 等が必要か。Function Calling が使えない前提で、プロンプト指示＋VBA 検証の設計か |
| 6 | 再送・タイムアウト | 長時間処理での自動再送（二重実行）とエラー時の再送・スリープを設計しているか |
| 7 | コンテンツフィルター | 事故・賠償・疾病等の記述がフィルターに該当する可能性を検証項目に含めているか |
| 8 | 利用ログ・効果測定 | 利用者・件数・修正量をツール側で記録する設計か（持株ログは利用不可）。記録の保存先（シート内か SharePoint 上の CSV か）と収集方法 |
| 9 | データ取扱 | 投入情報の区分（第7.1節）に沿っているか。Deep Research への指示が企業名・公開情報のみで構成されているか |
| 10 | 参照データの置き場所と規模 | 構造化データ・ベクトルをシート内に持つか外部 CSV（SharePoint）に持つか。外部 CSV の場合は列構成・文字コード・置き場所・読み込み方式・更新手順を先行ツールと揃えているか。32bit Office のメモリ制約下で読み込み・類似度計算が実用範囲か。本社サーバは営業部門と共有不可 |
| 11 | ツール間連携 | 他ツールとの受け渡しをファイル経由の手順として業務フローに明示し、所要時間を効果測定の前提に含めているか |
| 12 | 配布・更新 | SharePoint またはポータルでの配布、ポータルでの更新通知、利用者のマクロ設定、アドインの3か月周期の更新への追従（互換性が失われた場合の再配布手順）、版番号付きファイル名による版管理 |
| 13 | 利用者確認とAI表示 | 顧客提示前の利用者確認を必須工程として置き、社内向け成果物に AI生成の表示を付けているか |
| 14 | 共通モジュールへの依存 | MyBookShelf 等から再利用するモジュールを列挙し、その変更がツールに与える影響を明示しているか |
| 15 | 環境拡張時の扱い | Webサーチ開放等が実現した場合に追加できる機能と、実現しない場合の到達点を分けて記載しているか |
| 16 | Outlook 連携 | メールを入力元にする場合、取得対象（フォルダ、件名条件）と添付の保存先を定めているか。AI が作成した回答は下書きに留め、送信を人が行う設計になっているか |
