## 0. 結論（3行）

1. **骨格は一致している。** 「レポートJSONを中心に、VBAが固定テンプレでHTMLを組む。AIはJSONを出すだけ。schema検証＋修正1回。版は全部残す。Excelは入力口でデータは外」──これは当方が W3〜W10 で実装済みの形そのものである（§1）。

## 2. 成り立たないもの（×）──会社PCの実測と当方の確定事実に照らして

### 2-1. 「Azure OpenAI API を VBA から直接呼ぶ」（§2 用語表・§9.1 全体）

- **事実**: 社内で全員のPCから通る経路は **AIリボン「リボンちゃん」**（`Application.Run "ChatGPT"`・11実引数）だけである。VBAからの直接HTTP（`MSXML2.ServerXMLHTTP`）は社内AVが重く見る書き方で、当方は W11-a で**配布ビルドから実体ごと外した**（`ship:false`・配布binに `ServerXMLHTTP` の文字列が無いことを出荷検査⑥で保証）。APIキーも全社共用のローテ不能な借り物1本で、利用者に配れない（docs/21・22）。
- **帰結**: 文書中の「Azure OpenAI API」は**すべて「AIリボン経由」に読み替える**。すると──
  - **D-4（APIキーの置き場所）は消える**。利用者側にキーの概念が無い。
  - **A-01 ステップ5・8・9 / A-02 / A-04 の「モデル系統の使い分け（フラッグシップ／mini／nano）」は、リボンが知っているモデル名の範囲でしかできない**（14章§2: リボンの `ChatGPT` はモデル名の `Select Case` に `Case Else` が無く、一覧に無い名前は実行時エラー）。mini／nano 系がリボンの一覧にあるかは**未確認**（→ Q-1）。無ければ全部フラッグシップ1系統になる（コスト最適化は後回しでよい。動くことが先）。
  - **§9.1「トークン数を記録」はできない**。リボンは応答テキストを素通しで返すだけで usage を返さない。記録できるのは入力・出力の**文字数**と**所要時間**（当方の run_log がそれ）。
  - **X-3（失敗時の再試行）はリボンの挙動が前提になる**: リボンは失敗時に空文字でなく**定型の日本語文字列**を返す（`(error:429` / `接続切れ` / `content_filterに該当しました` 等。16章 E-15・E-54〜E-57）。タイムアウト時は**リボン側が無限に再送する**。つまりツール側で指数バックオフを設計する余地は小さく、「定型文を先頭一致で分類して止める」のが正しい（当方 `modGatewayRPN.RibbonFailureCode`）。
  - **X-4（送ってよい情報の区分）は「リボンがプロンプト全文＋氏名等を社内ログサーバへ送る」事実を前提に置く**。ツール側のログで本文を伏せても、リボン側には全文が残る。当方は送信前の PII 検知（`modPii`・匿名化 `{{COMPANY}}` 置換）を入れている。

### 2-2. 起動 bat の骨子「配布フォルダの位置はどこでもよい」（§9.2.1）

- **事実**: 会社PCで**マクロが動く場所は D: だけ**（信頼できる場所。VBOM は免除されない）。OneDrive 配下から `.xlsm` を開くとマクロがブロックされる。D: と Documents は**シャットダウンで消える**。消えないのは OneDrive 同期フォルダと部門共有だけ。`%OneDrive%` は別利用者を指す端末があり環境変数は当てにできない（2026-09-05 実測・W11-b）。
- **帰結**: `start "" excel.exe /x "%~dp0<ツール名>.xlsm"` を OneDrive 上で叩いても動かない。当方の bat は **本体を D:\リスク提案ナビ へ複製してから起動し、保存先（OneDrive側の `データ\`）を `data_dir.txt` で渡す**。よって「実行ブックは自分と同じフォルダの `DB/` を見る（絶対パスを持たない）」は成り立たず、**D-5 は「両立させる（data だけ OneDrive）」で実測済みの決着**である。パス長 200 字目安も OneDrive の前置き（`C:\Users\…\OneDrive - <社名>\…`）を考えると企業フォルダ名は短く保つ必要がある（当方は `<会社名>_<8桁>_企業カルテ.xlsx` の1ファイル）。
- bat 自体もメールでは届かない（`.bat`/`.bat.txt` は受信時削除、zip は送信側で拒否）。配布は **SharePoint/Teams に zip** が唯一の経路（docs/24 §8.1c）。

### 2-3. A-04「AI が提案書 HTML 全文を生成し、HTML の schema 検証・修正をする」（§7）

- **成り立たない理由**: (a) Wide 形式の固定部分（フォーマットCSS＋画像 data URI 約300KB＋表示スクリプト）を AI に書かせるのは非現実的で転記ミスで壊れる──**髙橋さんの作業ログ §10.2 自身の結論**。(b) AI の HTML には script・外部参照・イベント属性が混入し得る（A04-5）。当方は 18章で「LLM出力は**データとしてのみ**ページに入る。`<` は全部 `\u003C` へ」を規約にしており、この防衛線を HTML 生成では張れない。(c) リボンの1呼び出しで 60〜90KB の HTML を安定して返させるのは時間もぶれも大きい。
- **裁定**: A04-5 の代替案（**本文構造を JSON で出させ、HTML化は VBA**）を採る。詳細は §5。これにより §7.5「HTML修正」ボタンと `proposal_html.schema.txt` は不要になり、検証は既存の JSON schema 検証1系統に統一できる。

### 2-4. B-01〜03「Outlook メールを自動作成し、ログ一式を zip で添付」（§8）

- **成り立たない理由**: (a) zip 化には `Shell.Application`（COM 経由のコード実行系＝AV が重く見る）か PowerShell（社内PC不可）が要る。(b) マクロから Outlook を起動してメールを組み立てる形（`CreateObject("Outlook.Application")`）は**マクロ型マルウェアの典型パターン**で、AMSI 検知の実績がある方式と同じ系統である。(c) 社内メールは zip 添付が通らない実績がある（B-2 は事実上「否」）。
- **代替（当方の方式に寄せる）**: 報告シート（不具合／要望／好事例の3種別）に入力 →[報告文をコピー]でクリップボードへ（Excel自身のコピー経路・W9 で AV 対応済み）→ 利用者が Teams かメールに貼る。ログは添付せず、**err_log.csv の末尾N行と `data_dir` のパス**を報告文に自動で含める。宛先は config の「報告先」を表示するだけ（B-1 の懸念どおり固定送信はしない）。既存の「回収フォーマット」と同じ回収先へ流す。

### 2-5. X-1「企業情報（詳細）＋全11種目の基本ナレッジ＋共通ナレッジを毎回1本に結合」

- **事実**: 上限はモデルのコンテキスト長だけ（リボンは制限なし。有報「事業等のリスク」章全文を1呼び出しで通した実績・14章§3）。ただし**リボン呼出は VBA を同期ブロックし画面が白くなる**ので、入力が増えるほど待ち時間の体感が悪化する（当方は「呼出前に確定表示」で受けている）。
- **当方の方式**: 注入は**業種コード一致の決定的フィルタ＋行数上限**（`kb_risk_rows=20` / `kb_menu_rows=60` / `kb_case_rows=5` / `kb_scheme_rows=10`）。全文投入はしない。
- **すり合わせ案**: 種目ナレッジは「**要約版（basic）は種目あたり数百字**」に保ち、全種目分を A-01 に入れてもよいのはその範囲。詳細（約款・引受GL）は A-03 の該当種目でだけ入れる。**11種目の区分そのものは採用する**（当方の種目マスタは現状シード1行〔L-03 PL〕しか無いので、髙橋さんの11種目を種目マスタの正にする。§7）。

### 2-6. A-03 の「RAG 抽出データ」（v2）

- 社内PCに埋め込み（ベクトル）API は無い（リボンには無い）。純VBA内積の RAG 資産（gemini-demo）はあるが埋め込み生成に外部APIが要るので**社内では動かない**。
- **現実解**: `rag/` の原本を「節見出し付きの txt」にしておき、種目×論点（`deep_dive_points`）で**節を決定的に引く**。装填は開発機で `structure_chunker.py`（docs/21）を使ってオフラインで行う。v2 の話なので今は方針だけ置く。

## 5. 裁定: 顧客向け提案書（A-04）の出力形式は Wide 22枚見本に合わせる

### 5.1 方式

- **AI は「提案書JSON」だけを出す。HTML は VBA が固定テンプレで組む**（HTMLレポートと同じ作法。18章の規約をそのまま適用: LLM出力はデータとしてのみ入る・`<` は `\u003C`・外部参照なし・自己完結1ファイル）。
- 見本 22 枚のうち、**機械的に導けるスライドは AI を呼ばない**: リスクマップ（S2 の impact×frequency）、3分類（`insurability.transferability`）、優先8件の表、巻末リスク一覧、出典と前提。**AI に頼むのは「顧客向けの言い換え」だけ**: 要旨の3テーマ文、各スライドのヘッドメッセージ（結論の一文・45字）、事業構造の5領域と5要因の敬体化、テーマ表、進め方4ステップの当社／貴社の役割、本日ご判断いただきたいこと3点、ご共有いただきたい事項の優先印、発表者ノート（読み上げ／問いかけ／更問／フォロー）。
- **呼び出しは1回（フラッグシップ）＋修復1回**。入力は S1+S2+S3（18章 DATA）＋髙橋さんの作業ログ §6.3 の「promptに書くこと」9項目（読み手と立場・禁止パターン・用語対訳・事実の扱い・一貫性・標準構成・1枚の設計・分量上限・当社サービスの記載条件）。用語対訳表は `docs/design/提案書_wide/` に R 資料として置く（**まだ無い → Q-3**）。
- 版番号は元ラウンド（`proposal_v00N.html`）。HTMLレポートの横に書き出す。

```
proposal: {

  stats: {risk_total, easy, design, non_ins, ideas, ideas_priority},  -- VBA が S2/S3 から数える（AIに書かせない）
```

## 8. 追記(2026-09-07 夜): リボンちゃんの応答抽出仕様が当方のJSON出力を途中で切る(髙橋 md-review-tool v1.2 の指摘を実ソースで確認)

**事実**(`リボンちゃん ver202606` の `log.bas` を当方の手元コピーで読んだ。`AI関連/Excelツール - AIリボン/excel-addin_module_リボンちゃん_ver202606/`):

1. `parseText` は API 応答本文(HTTPボディ全体)に対して先に **`": "` → `":"`**、`content_filter_results` → `content_filter_result`、`prompt_filter_results` → `prompt_filter_result` の3置換を掛ける。**モデルの本文にも効く**(本文中の「見出し: 値」の空白が消える)。
2. `ExtractText` は本文の始点を `content":"`(無ければ `text":"`)の**最初の出現**、終点を `","` / `"},` / `"`+LF の**最も早い出現**で決め、その間を `UnEscapeJSON` で戻して返す。**エスケープ済みの本文の中身を区別しない**。
3. 当方の S1〜S4 は JSON を返させる。本文の中に `"},`(文字列値で終わるオブジェクトの後にカンマ)があると、APIボディ上は `\"},\"` で **`"},` が部分一致し、そこで切られる**。`","` は本文中では `\",\"`(引用符の前に必ず `\`)になるので当たらない。LF は本文中では `\n` なので当たらない。**危ないのは `"},` だけ**。
4. 手元で模擬した結果: 1行に詰めた(minified)S1風JSON 123字 → **74字で切断**。整形(pretty-print・`}` の前に改行)した同じJSON → 切れない(`\"\n}` になり `"},` が現れないため)。
5. 2026-08-28 の実機 S1 完走は、モデルがたまたま整形JSONで返したから通った可能性が高い。**S2/S3/S4 は実リボンで一度も回していない**。当方の mock 応答(`modMockLlm*`)は `"},{` を26箇所含む=1行詰め形式で、ニセリボンちゃん(`wintest/mock_ribbon`)は `parseText` を模していない。**現行の検問ではこの切断を再現できない**。
