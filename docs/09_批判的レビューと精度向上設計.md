# 09. 批判的レビューと精度向上設計（コスト度外視版）

**前提の変更**: OpenAI APIコールは無制限（コスト一旦度外視）。ribbon経路も利用枠内で多呼び出し許容。これにより「1 step = 1呼び出し」の制約を外し、精度優先のアーキテクチャに改める。
**本書の構成**: §1 敵対的セルフレビューの指摘一覧（仕様反映の対応つき）／§2 現場メモ（自由入力）の設計／§3 データ拡張マップ／§4 精度アーキテクチャ（入念モード）／§5 プロンプトを進化させ続ける仕組み。

## 1. 敵対的セルフレビュー（v2.0仕様の欠陥と対応）

| ID | 指摘 | 深刻度 | 対応 |
|---|---|---|---|

## 2. 現場メモ（自由入力）の設計 — 蒸留しない伝搬経路

**思想**: 定型入力とドシエは「調べれば分かる情報」。現場メモは「営業しか知らない情報」——社長の性格、決裁の力学、工場で見た光景、競合の営業の動き、担当者がこぼした一言、噂、勘。**この価値は原文にあり、要約・構造化した瞬間に減価する**。だから他の入力と逆の設計にする:

- 案件入力に「**現場メモ（何でも欄）**」を新設。書式自由・箇条書き推奨・下書き不要。「きれいに書かない。思い出した順でいい」を欄の注記に明記
- S1は現場メモを**要約せず**、1ネタ=1件の field_insights に切り分けて**原文のまま**保持し、タグだけ付ける（risk_clue=リスクの手がかり／relationship=人間関係・決裁／competitor=競合・他社動向／constraint=制約・NG事項／opportunity=商機／other）
- field_insights は s1Json に含まれるため、S2/S3/S4・壁打ちに**原文のまま届く**。S2は risk_clue を根拠（source=memo）に使い、S3は relationship/constraint を hook_question・objection_response の調整に、S4は constraint をスライドのトーン調整に使う
- 個人名は書かない運用（E-05の走査対象。役職表記を推奨: 「社長が」「工場長が」）

## 4. 精度アーキテクチャ — 入念モード（quality_mode）

config `quality_mode`: standard（T1既定・従来の1呼び出し/step）／ **deep（T2既定・生成→批判→改訂）**。

```
deep時のS2:  S2生成 → S2C批判(別呼び出し・辛口審査員) → S2改訂(批判を添えて再生成) = 3呼び出し
deep時のS3:  S3生成 → S3C批判(顧客経営者ペルソナの反論+実売性審査) → S3改訂 = 3呼び出し
S1/S4はstandardのまま（構造化・整形は1発で十分。批判の価値が薄い）
1案件の呼び出し数: standard=4 / deep=8（+修復リトライ）。リボン枠が厳しければdeepのみdirect経路へ逃がす(config)
```

- **批判者は生成者と別呼び出し・別システムプロンプト**（自分の答案を自分で採点させない）
- S2C観点: ①6カテゴリの見落とし ②企業固有性（一般論度） ③根拠の質（引用が本当にそのリスクを支えるか） ④頻度×影響の整合 ⑤ギャップ分析の誤り。＋追加すべきリスクの提案
- S3C観点: ①経営者になりきった率直な反論（「それはウチには関係ない」と言われないか） ②実売性（メニュー・型が本当に応えられるか） ③3本の優先順位 ④hook_questionの刺さり ⑤幹事・BID文脈との整合
- 批判・改訂の全文も case_data に保存（監査＋プロンプト改善の教材）
- プロンプト全文とSchema-S2C/S3Cは15章§4.5/§4.6に定義（modPromptsOps・modSchemas実装対象）
- さらに上の「多視点アンサンブル」（S2を財物・オペ・戦略の3視点で並列生成→統合）はPhase 1.5の実験項目とする（direct経路で並列可・効果をゴールデンセットで検証してから採用）

## 5. プロンプトを進化させ続ける仕組み（「ラッパーのシステムプロンプトが大事」への答え）

プロンプトは書いて終わりではなく、**評価→改訂のループを製品の一部**にする:

1. **ゴールデンセット**: PoC対象5～10社の入力一式を保存（17章T-43）。うち1社は「正解」をベテランが作る（模範リスク仮説・模範提案）
2. **LLM審査員**: 3軸ルーブリック（網羅性/具体性/実売性）を審査プロンプト化し、direct経路で自動採点。初回はベテラン採点と突き合わせて審査員自体を較正
3. **改訂サイクル**: プロンプト変更→ゴールデンセット一括再実行（direct・並列・コスト度外視）→自動採点で劣化検知→良化のみ採用。15章§10の変更管理をこの自動評価つきに強化
4. **ディープリサーチプロンプト（docs/08）も同じ扱い**: 収集結果の質を「S1充足度診断の改善幅」で測り、D-1～D-6を版管理・改訂していく
5. **運用シグナル**: run_logのrepaired/failed率・警告率（inference過多等）・壁打ちでの手戻り箇所を月次でプロンプト改訂の優先度に変換

## 6. 「より精度の高いリスクコンサルエージェント」への道筋（総括）

精度は4つの掛け算で決まる。**①入力の解像度**（ティア制×ドシエ収集×現場メモ×ラウンド反復＝今回までで設計完了）×**②知識の質**（ナレッジ・フライホイール＝設計完了、装填はT-90）×**③推論の質**（入念モード・批判改訂・アンサンブル実験＝本書）×**④検証の速さ**（LLM審査員×ゴールデンセット＝本書）。この4つが揃うと、残るボトルネックは「支払データ・失注理由など社内の結果データへの接地」（§3のOQ待ち領域）になり、それがPhase 2（UW高度化）の入口になる——つまり**精度向上の道はデータガバナンスの交渉に収束する**。技術側で先にやれることは全部この設計に入れた。
