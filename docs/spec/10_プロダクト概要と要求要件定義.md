# 10. プロダクト概要と要求・要件定義

**製品名**: リスク提案ナビ（コード名: RPN）
**版**: v1.0（実装着手可能版）
**読者**: 実装担当（Opus/Sonnet エージェント）、レビュー担当、PJメンバー
**上位文書**: `docs/02_製品構想_リスク提案ナビ.md`（構想）。本書以降 `docs/spec/` が実装の正。矛盾時は spec が優先。

---

## 1. プロダクト概要

企業の公開情報（HPテキスト・有価証券報告書「事業等のリスク」章・営業メモ）を入力すると、
①企業プロファイル → ②潜在リスク仮説 → ③実在の自社コンサルメニューに紐づく提案 → ④提案書骨子（PowerPoint自動生成）＋初回訪問ヒアリングシート
を4段のAI処理で生成する **Excelマクロブック製品**。

- 配布物: `リスク提案ナビ.xlsm`（本体）＋ `ナレッジブック.xlsx`（知識データ・共有フォルダ配置）
- LLMは**社内AIリボン（「リボンちゃん」アドイン、Azure OpenAIラッパー、全社配布）経由**で呼び出す。ゆえに利用者へのAPIキー配布は不要
- 先行PoC「MyBookshelf」（github.com/kojima1459/notebook, branch `claude/internal-notebook-lm-chatbot-B6BE7`）で実証済みの基盤（LLMゲートウェイ・config・ログ・テスト方式）を移植・踏襲する

## 2. 背景・目的（要約）

- 営業のリスクコンサル提案の事前調査に膨大な時間がかかる（内田部長の春華堂での原体験）
- 提案の質が属人化している。80点までの素材（マニュアル・約款・過去提案書）は電子データであるが、80→100点（何が刺さったか）は共有されていない
- 目的: (a) 事前準備を1営業日→15分に短縮 (b) ナレッジ注入により提案レベルの底上げと属人化解消 (c) 成功事例が自動的に蓄積・全員に還流する仕組みの確立

## 3. ペルソナ

| ID | ペルソナ | 特徴 | 主要ニーズ |
|---|---|---|---|
| P1 | 営業企画・営業担当 | 非エンジニア。Excel/PPTは日常利用。マクロの中身は見ない | 訪問前日に15分で「恥ずかしくない」準備を終えたい |
| P2 | 商品部 UW/リスコン担当 | 種目・リスクの専門家。AIには半信半疑 | 生成結果を短時間でレビュー・修正したい。自分の知見が反映されてほしい |
| P3 | ナレッジ管理者（当面は開発者） | ナレッジブックの編集権限を持つ | 成功事例・メニューの登録が簡単であってほしい |
| P4 | 開発者（小島） | VBA・OpenAI APIを扱える唯一の要員 | 保守が1人で回る構造。PoCと同じ流儀 |

## 4. ユースケース

| ID | ユースケース | 主アクター | 流れ |
|---|---|---|---|
| UC1 | 新規訪問先の提案準備 | P1 | 案件作成→HPテキスト貼付→一括実行→PPT・ヒアリングシート取得（15分） |
| UC2 | 生成結果の専門レビュー | P2 | S2/S3シートの中間結果を修正→該当Step以降のみ再実行 |
| UC3 | 商談後のフィードバック登録 | P1 | フィードバックシートに商談結果を記入（3分） |
| UC4 | 成功事例の昇格 | P3 | 月次レビューでフィードバックから成功事例ライブラリへ登録 |
| UC5 | ナレッジ整備 | P3 | メニュー一覧・業種リスクライブラリの追加/修正 |
| UC6 | デモ実行（mock） | P4 | 社内ネットワーク外でmock経路により全画面フローを確認 |

## 5. 要求定義 → 要件定義トレーサビリティ

| 要求ID | 要求（誰が・何を） | 対応要件 |
|---|---|---|
| RQ1 | 営業は企業名とHPテキストだけで提案準備を完了したい | FR-01,02,03,04,05,06 |
| RQ2 | 部長は提案の質を底上げし属人化を解消したい | FR-07,08,09,10 |

## 6. 機能要件（FR）

| ID | 要件 | 優先度 | 備考 |
|---|---|---|---|
| FR-01 | 案件（企業）単位で入力・生成結果・状態を管理できる。案件ID採番 `C-YYYYMMDD-NNN` | Must | 13章 |
| FR-02 | 入力: 企業名(必須)/業種(業種マスタから選択・必須)/HPテキスト貼付(必須)/有報リスク章(任意)/営業メモ(任意) | Must | |
| FR-03 | Step1: 入力テキストから企業プロファイルをJSONで構造化し、S1シートに表形式で表示 | Must | 15章 Schema-S1 |
| FR-04 | Step2: プロファイル＋業種リスクライブラリから潜在リスク仮説（6カテゴリ・頻度×影響度×根拠×確認点）を生成、S2シートに表示 | Must | Schema-S2 |
| FR-05 | Step3: リスク仮説をナレッジブックの実在メニュー・種目にマッチングし提案ストーリー3本を生成、S3シートに表示。**メニューIDはナレッジに実在するもののみ**（VBA後検証） | Must | Schema-S3 |
| FR-06 | Step4: スライド構成JSONを生成し、固定VBAがPowerPoint(5枚)を自動生成・保存。同時に初回訪問ヒアリングシートを生成 | Must | Schema-S4 |
| FR-07 | Step2/3のプロンプトに、業種コードで決定的にフィルタしたナレッジ（リスクライブラリ・メニュー・成功事例）を自動注入する | Must | |
| FR-08 | 全生成結果と実行メタ（モデル・所要時間・注入ナレッジID）をrun_logに記録する | Must | |
| FR-09 | フィードバックシートに商談結果（刺さった/刺さらなかった/顧客の反応/自由記述）を案件に紐づけて記録できる | Must | |
| FR-10 | ナレッジ管理者が成功事例ライブラリに事例を登録すると、次回以降の該当業種の生成に自動注入される | Must | |
| FR-11 | 各Stepの中間結果（シート上のJSON由来データ）を人が編集し、そのStep以降だけを再実行できる | Must | |
| FR-12 | 「一括実行」（Step1→4連続）と「Step個別実行」の両方を提供する | Must | |
| FR-13 | LLM経路は config で `ribbon`(既定)/`direct`/`mock` を切替。ribbonはキー不要。directのみ外部ファイルからAPIキーを読む | Must | 14章 |
| FR-14 | Step2の「要確認」項目とStep1の「情報の欠落」を統合してヒアリングシート（質問10問以内）を出力する | Must | |
| FR-15 | S3で「該当メニューなし」となったリスクを新サービス候補として別枠記録する（商品部の新商品シーズ検知） | Should | |
| FR-16 | 有報PDFのテキストは利用者がコピペで貼る（PDF自動抽出はPhase 1対象外。PoCのmodExtractorPdf移植はPhase 2候補） | 対象外明記 | |

## 7. 非機能要件（NFR）

### 性能
| ID | 要件 |
|---|---|
| NFR-P1 | 一括実行の目標所要時間: 5分以内（LLM 4呼び出し＋PPT生成。リボン待機は最大 `llm_wait_sec`=1200秒/回を上限とする） |
| NFR-P2 | 実行中はExcelがフリーズしたと誤認されないよう、Step名と経過を常時ステータス表示する（PoCの SetStage 方式） |
| NFR-P3 | 入力テキストは最大40,000字（超過分は警告の上で打ち切り。PoC `max_context_chars` と同思想） |

### 可用性・信頼性
| ID | 要件 |
|---|---|
| NFR-R1 | LLM応答がJSONとして不正な場合、自動修復リトライを1回行い、それでも失敗なら案件状態を「エラー」にし人可読メッセージを表示（16章 E-06） |
| NFR-R2 | 全エラーは err_log シートに構造化記録（PoC modLog 方式・ローテーション付き） |
| NFR-R3 | 途中失敗時も完了済みStepの結果は保持され、失敗Stepから再開できる |

### 保守性
| ID | 要件 |
|---|---|
| NFR-M1 | PoCのコーディング規約を踏襲: 1モジュール30,000字以内 / R3（`Application.Run`はゲートウェイモジュール内のみ）/ R4（UI層以外のモジュールにExcelオブジェクトトークンを書かない）/ 外部ライブラリ（JsonConverter等）依存禁止 |
| NFR-M2 | 純ロジックは modTestsPure 方式でユニットテスト可能にし、mock_ribbon でLLMなしの結合確認ができる |
| NFR-M3 | モデル名・閾値・パス等は全て config シート駆動（ハードコード禁止） |

### ユーザビリティ
| ID | 要件 |
|---|---|
| NFR-U1 | 利用者の操作は「シートに貼る→ボタンを押す」のみ。設定作業ゼロ（ribbon経路） |
| NFR-U2 | エラーメッセージは非エンジニア向けの日本語（対処方法つき） |

### コスト
| ID | 要件 |
|---|---|
| NFR-C1 | ribbon経路は社内リボンの利用枠内（LimitCheck準拠）。direct経路のコスト試算は14章に記載 |

### セキュリティ
NFR-S1〜S5 は `16_エッジケースとセキュリティ設計.md` に定義。

## 8. スコープ外（Phase 1でやらないこと）

- Webの自動取得・クローリング（人がブラウザでコピペする）
- 顧客の非公開情報・個人情報の投入（公開情報のみ。16章のデータ分類マトリクス参照）
- 保険料試算・引受判断
- PDF/Word自動テキスト抽出（Phase 2でPoCのmodExtractor群を移植候補）
- ベクトル検索（業種コードによる決定的フィルタで代替。Phase 2で必要になればPoCのembed基盤を移植）

## 9. 成功指標（PoC評価）

- ベテラン採点ルーブリック3軸（網羅性/具体性/実売性）で 実在5〜10社の平均 **3.5/5.0 以上**
- 事前準備所要時間: 従来比 **80%削減**（自己申告計測）
- Step3のメニューID後検証エラー率（幻覚率）: **0%**（検証で全件ブロックできること）
