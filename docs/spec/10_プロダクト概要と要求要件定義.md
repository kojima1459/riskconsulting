## 1. プロダクト概要

**営業の「現場の声」と商品部の「商品・座組の知識」をAIの上で毎日すれ違わせ、新しい提案（型）を生み出し、成功パターンを全員に横展開する二方向ナレッジエンジン。**

- 形態: `リスク提案ナビ.xlsm`（本体・利用者ローカル実行）＋ `ナレッジブック.xlsx`（共有・管理者編集）
- LLM: 社内AIリボン「リボンちゃん」経由（全社配布・キー不要）。開発用にdirect（OpenAI API）・mock経路を併設（14章）
- 構造: 共通シャーシ（構造化→突合→選択肢→成果物→記録）の上に**プレイ（作戦カード）**を載せる。Phase 1はPL-01〜03、Phase 1.5でPL-04〜06、Phase 2でPL-07/08（§5）
- 基盤实証: PoC「MyBookshelf」（github.com/kojima1459/notebook, branch `claude/internal-notebook-lm-chatbot-B6BE7`）のLLMゲートウェイ・config・ログ・テスト方式を移植（12章）

### 二方向エンジン（製品の心臓部）

```
【使うエンジン】営業・商品部が案件ごとに使う
  案件入力 → S1構造化 → S2リスク/ギャップ → S3提案 → S4骨子・PPT・ヒアリング
【生むエンジン】商品部が月次・四半期で回す
  受信箱(投稿・現場の声・ウォッチ) ＋ 案件事実ログ
    → PL-03プリフライト(入口診断) / PL-06型生成(掛け合わせ)
    → 編集会で採択 → 型ライブラリ → 翌月から全員の使うエンジンに注入
```

**設計原則: 現場の声は「集めない」。** 営業は自分の得（準備が15分・提案が厚い）のために使うだけで、入力と商談事実が副産物として構造化されて貯まる。営業向けに入力専用の作業を課す機能を作ってはならない。

## 2. 背景・目的

1. 提案準備の時間（1日→15分）と質の底上げ（内田部長の春華堂原体験）
2. 属人化の解消: 80点までの素材は電子データにあるが、80→100点（勝ち筋・座組の引き出し・判断の理由）は共有されていない
3. 商品部と営業の知識非対称の解消: 商品部は現場を知らず（アイデアが机上化・投稿ボックス2年分1,680件の8割が受け側構造でドロップ）、営業は商品・座組を知らない（提案が定番化）
4. 型の量産: ヤモリ→じゃぱん21→WOTAのような横展開を、個人の偶然から仕組みの必然へ（商品×CSV×DXの実装）

### 入力ティア（ドシエ・ティア。案件属性 dossier_tier）

| ティア | 対象 | 収集 | 所要 | 期待水準 |
|---|---|---|---|---|
| **T1 クイック** | 量をこなす更新・新規 | 収集レシピ8項目（15章§2.0） | 15分 | 恥ずかしくない80点の初回準備（フロア） |
| **T2 フルドシエ** | 重要案件・戦略先 | 13観点（8項目＋SNS評判・競合・業界市況・マクロ・財務/付保コンテキスト）。収集はディープリサーチ社内アプリへの定型プロンプト（docs/08）で自動化し人はコピペ運搬 | 1〜2時間（放置込み・人の作業15分） | 仮説を持って訪問する水準 |
| **T3 壁打ち** | 提案を研ぎ澄ます局面 | T1/T2のドシエ＋S1〜S3結果を初期コンテキストにPL-04で反復 | 可変 | 三菱電機型（付加価値の天井） |

思想: **フロア（T1）は量と底上げとデータ収集のため、天井（T2×T3）が付加価値のため**。入力は多いほど有利（充足度診断が誘導）だが、収集コストをAI（ディープリサーチ）に転嫁することで「多く集める」を現実にする。
