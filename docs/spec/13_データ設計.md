# 13. データ設計（シート＝テーブル定義）

原則: 1シート=1テーブル。1行目=ヘッダ（物理名）。2行目以降=データ。物理名は英小文字snake_case。日本語表示名はヘッダセルのコメントに保持。VBAからのアクセスは列名ベース（列番号ハードコード禁止。ヘッダ探索ユーティリティを modUtil に置く）。

## 1. ID採番規則

| 対象 | 形式 | 例 | 採番 |
|---|---|---|---|
| 案件 | `C-YYYYMMDD-NNN` | C-20260901-001 | 作成日+当日連番。modCaseStore が案件一覧の最大値+1 |
| リスク行 | `R-<案件ID>-NN` | R-C-20260901-001-03 | Step2出力順 |
| 提案ストーリー | `P-<案件ID>-N` | P-C-20260901-001-2 | Step3出力順(1..3) |
| メニュー | `M-NNNN` | M-0012 | ナレッジ管理者が手動採番（欠番可・再利用禁止） |
| 種目 | `L-NN` | L-03 | 同上 |
| 成功事例 | `K-NNNN` | K-0003 | 同上 |
| 業種 | 総務省 日本標準産業分類 中分類コード | `09`(食料品製造業) | マスタ固定 |

## 2. 本体ブック `リスク提案ナビ.xlsm`

### 2.2 `case_data`（案件の実データ。key-value縦持ち・非表示）

中間JSONやHP全文のような長文・可変構造は、横持ちにせず縦持ちで保管する（Excelのセル32,767字制限があるため **32,000字ごとに分割し seq で連結**。modCaseStore が透過的に分割/結合する）。

| 列 | 型 | 必須 | 説明 |
|---|---|---|---|
| case_id | String | ○ | 案件一覧FK |
| data_key | String | ○ | enum: input_hp / input_yuho / input_memo / s1_json / s2_json / s3_json / s4_json / s1_edited / s2_edited / s3_edited / s4_edited |
| seq | Long | ○ | 分割連番(1..)。 |
| content | String | ○ | 最大32,000字 |
| saved_at | Date | ○ | |

- `sN_json` = LLMの生JSON（監査用・不変）。`sN_edited` = シート上で人が編集した結果を再シリアライズしたJSON（下流Stepへの入力は常に edited を優先、無ければ生JSON）
- 削除は case_id 単位（案件削除時）

### 2.4 ログ（PoC modLog 踏襲。非表示・ローテーション付き）

`err_log`: logged_at / err_code(E01xx=入力,E02xx=LLM,E03xx=JSON検証,E04xx=ナレッジ,E05xx=出力) / source(モジュール.関数) / detail(最大400字・入力本文は記録しない) / err_number / http_status
`usage_log`: logged_at / event(run_start/step_latency/fallback等) / case_id / detail
`run_log`（新設。1行=1 Step実行。監査と品質分析の主データ）:

| 列 | 説明 |
|---|---|
| run_at / case_id / step | step: s1/s2/s3/s4 |
| transport / model | 実際に使った経路とモデル |
| latency_ms / input_chars / output_chars | |
| injected_kb_ids | 注入したナレッジID列挙（"RL-09-001;M-0012;K-0003"） |
| validate_result | ok / repaired（修復リトライで成功） / failed |
| operator | 実行者 |

## 3. ナレッジブック `ナレッジブック.xlsx`

### 3.1 `業種マスタ`
| industry_code | industry_name | aliases（;区切り、入力補助用） |

初期データ: 日本標準産業分類 中分類のうち商品部の主要対象 30業種程度＋`00 共通`。

### 3.2 `リスクライブラリ`（Step2注入。1行=1知識）
| 列 | 説明 |
|---|---|
| risk_lib_id | `RL-<業種>-NNN`（共通は RL-00-NNN） |
| industry_code | 対象業種（00=全業種共通） |
| category | enum: property_natcat / product_liability / labor_hr / bcp_supplychain / cyber_info / management_strategy |
| risk_name | 例: アレルゲン表示誤り |
| typical_scenario | 典型シナリオ（200字以内） |
| typical_freq / typical_impact | enum: high/mid/low, large/mid/small |
| check_points | 現場確認ポイント（;区切り） |
| priority | 1(高)〜3(低)。注入行数超過時の切り捨て順 |
| source | 出典メモ（UWマニュアル名等。プロンプトには入れない） |

初期データ: 主要10業種 × 各6〜10行 ＋ 共通20行 = 約100行（ナレッジ管理者がUWマニュアル・過去提案から起こす。17章 T-90） |

### 3.3 `メニュー一覧`（Step3注入・実在チェックの正）
| 列 | 説明 |
|---|---|
| menu_id | M-NNNN 主キー |
| menu_name | 実在するサービス正式名 |
| summary | 100字要約（プロンプト注入用） |
| target_categories | 対応リスクカテゴリ（;区切り、上記enum） |
| target_industries | 対象業種コード（;区切り。空=全業種） |
| is_active | TRUE/FALSE（FALSEは注入も実在チェックも対象外） |

### 3.4 `種目マスタ` / `メニュー種目対応`
`種目マスタ`: line_id(L-NN) / line_name（火災/賠責/労災上乗せ/サイバー/取引信用/企業費用利益…）
`メニュー種目対応`: menu_id / line_id（多対多）

### 3.5 `成功事例`（Step3注入・80→100点の器）
| 列 | 説明 |
|---|---|
| case_lib_id | K-NNNN |
| industry_code | |
| customer_profile | 顧客の状況（匿名化: 社名を書かない。「静岡の菓子製造・従業員300名」程度） |
| risk_presented | 提示したリスク |
| proposal | 提案内容（メニューID併記可） |
| why_it_worked | **決め手**（なぜ刺さったか。本ライブラリの核心） |
| quote | 顧客/営業の生の声（任意） |
| registered_by / registered_at | |

初期データ: 内田部長の春華堂の経験＋ユーザー保有の三菱電機提案（ローカル保管）を管理者が登録する（17章 T-91）。

### 3.6 `新サービス候補`（本体からの自動追記先）
| logged_at / case_id / industry_code / unmatched_risk（該当メニューが無かったリスク名とシナリオ） / operator |

## 4. データ保全

- case_data の `sN_json`（LLM生出力）は不変。監査・プロンプト改善の一次データ
- 案件削除はHOMEからのみ（案件一覧+case_data+フィードバックを同時削除、確認ダイアログ必須）
- ナレッジブックは管理者が編集。編集中の排他は「管理者1名運用」を前提とし、本体からの追記（新サービス候補のみ）は開けない場合ローカル退避→次回起動時に再送（16章 E-13）
