#### セル格納規約（配列・入れ子）

画面シート（§2.12-§2.17）へJSONを展開する際、配列と入れ子オブジェクトは次の規約でセルに落とす。この規約は書き出し（JSON→シート）と逆シリアライズ（シート→JSON）で共通であり、**列名とスキーマプロパティの写像は各シート節の表が正**とする。

| 対象 | セル格納形式 | 逆シリアライズ |
|---|---|---|
| 文字列配列（main_products / processes / check_points / bullets / menu_ids / line_ids / aspirations / key_materials / segments / channels 等） | 要素を「; 」（半角セミコロン+半角スペース）で連結した1セル | 「; 」で分割し前後空白を除去。空セルは `[]` |
| 整数配列（target_risk_nos / target_gap_nos） | 10進整数を「; 」で連結（例 `2; 5`） | 「; 」で分割し整数化。数値化できない要素は破棄せず検証不合格として扱う |
| preventions（オブジェクト配列） | 1要素=`measure(related_menu_id)`（例 `原材料の二重調達(M-0012)`）、要素間は「; 」。related_menu_id が "" の要素は括弧ごと省き measure のみ | 「; 」で分割後、末尾が `)` でその直前の `(` 以降が `M-` +4桁数字に一致する場合のみ related_menu_id として切り出す。一致しなければ全体を measure とし related_menu_id="" |
| 入れ子オブジェクト（単数） | 親キーを畳んだ列に展開（evidence.quote→`evidence_quote`、evidence.source→`evidence_source`、supply_chain.notes→`supply_chain_notes`）。ただし insurability の3項目は列名が冗長になるため親名を省き `transferability` / `line_note` / `control_note` とする | 各シート節の表の「スキーマ写像」列に従って入れ子へ戻す |
| 空配列 | 空セル（空文字列 "" ではなく値なし） | 空セルは `[]`。15章の空配列規約（current_coverage / gaps / target_gap_nos）はここで担保する |
| 要素本文に「;」を含む場合 | 格納時に全角「，」へ置換する（**非可逆**。各シートの当該列見出しに「本文中の ; は ， に置換されます」の注記を常設） | 復元しない |
| 改行を含む文字列（scenario / pitch / prompt_text / notes 等） | セル内改行（vbLf）をそのまま保持 | JSON化時に `\n` へエスケープ（modJsonLite.EscapeJsonStr） |
| 日本語ラベルで表示するenum列 | 19章§3の日本語ラベルを表示（入力規則リスト） | modUICase の変換表でenum機械値へ戻す。表に無いラベルは検証不合格 |

**`EnumEn` の丸括弧フォールバック（v3.2.1・裁定書22 D13。この1件が唯一の例外）**: 上表の「表に無いラベルは検証不合格」＝**推測で近いものを返さない**は不変であるが、**完全一致で引けなかった場合に限り**、ラベル末尾の丸括弧（`（…）`）を落として**もう一度だけ**完全一致で引く。表示専用の欄に説明を足した「`しっかり調査（貼った内容から自動で決まります）`」のような**表示付加文**を読み戻すためであり、ラベル本体（`しっかり調査`）は19章§3から1字も変わっていない。完全一致で引けたときはこの経路を通らないため既存の変換結果は1つも変わらず、**部分一致・前方一致・正規表現による曖昧照合は依然として禁止**である。この例外を使ってよいのは「画面に出すためだけに丸括弧の補足を付けた書込専用セル」に限り、**利用者が入力する列・LLM出力の逆シリアライズには使わない**（そちらは従来どおり不合格にする）。
| 32,000字を超える文字列 | 表示セルは先頭2,000字＋注記、全文は case_data（16章 E-22） | 全文は case_data 側から復元する |

セルへの書込は全て `SetCellSafe` を経由する（16章 E-46・NFR-S7）。

**「;」置換の適用点（v2.5・裁定書9 B5）**: 上表の「要素本文に『;』を含む場合」は、**配列セルを組み立てる関数（`PathArrCell` / `PrevCell` / `IntArrCell`）が要素1本を書き出す直前**に `Replace(one, ";", ChrW(&HFF0C&))` を通すことで実現する。連結してからまとめて置換すると区切りの「; 」まで潰れるため、必ず要素単位で行う。復元はしない（非可逆）。この置換が無いと、LLMが返した1要素に「; 」が含まれるだけで読み戻し時に2要素へ分裂し、`sN_edited` の保存（下流Step実行のたびに自動で走る）で分裂後の配列が確定してしまう。

#### 逆シリアライズ規約（sN_edited の生成）

1. `modUICase.SerializeSheet(stepNo)` が対象シートの全テーブルをヘッダ名で読み、15章スキーマのプロパティ順にJSONを組み立てる。
2. 行順=配列順。各テーブルは順序列（`risk_no` / `gap_no` / `story_no` / `slide_no` / `seq` のうち当該表が持つもの）の昇順に並べ替えてから配列化する。
3. 表の「スキーマ写像」列が「（順序列・非スキーマ）」の列はJSONに書き戻さない。それ以外の全列は必ず書き戻す（15章スキーマは additionalProperties:false かつ全プロパティ required のため、欠落は不合格になる）。
4. 組み立てたJSONは保存前に必ず `modValidate.CheckSN` を通す。不合格なら `sN_edited` を保存せず、画面に不合格理由を表示し、下流は従前の参照優先（`sNr_json` / `sN_json`）を使い続ける。
5. 空行（全列が空）は無視する。ヘッダ行の直下から最初の空行までを表の範囲とする。

**投函下書き行**（v2.5.1・裁定書10 C1。旧 v2.5 の名前付きレンジ `ib_body_draft`〔N6〕は**廃止**）: [＋投函]の本文入力は VBA の `InputBox`（既定フォントでの入力上限が255字前後）ではなく、判断台帳の下書き行と同じ作法で、**受信箱テーブルの先頭データ行（ヘッダ直下）を投函下書き行**とする。規定は次のとおり。

- **id列（`inbox_id`）に固定マーカー「(下書き)」**を置く。この行は投函の入力欄であって受信箱のデータではない。
- 利用者は下書き行の `body` 列（必要なら `theme` / `source_kind` 等の入力列）に記入して[＋投函]を押す。`modUIInbox` は下書き行の `body` を読み、**空なら案内を出して中止**する。32,000字打切りと警告の規定は本節 `body` および16章 E-22 のとおり（打切り時は警告を出す）。
- **投函に成功したら下書き行の入力列をクリア**する（行は消さない。マーカーと下書き行そのものは常設）。
- **受信箱の件数・集計を行う全経路で下書き行を必ずスキップ**する（v2.5.2・裁定書11 Q2で `modInboxStore` 限定から拡大）: 未診断の抽出・一括診断・関心度集計・判定に加え、**HOMEの `hm_inbox_*` を数える `modUIInbox.CountByStatus`** も対象。`status` 列には入力規則もシート保護も無く下書き行に値が入りうるため、除外しないと「一括診断は0件なのにHOMEは1件」という食い違いが出る。判定基準は id列マーカー「(下書き)」の1点のみ。
- **`source_kind` は入力列**（v2.5.2・裁定書11 Q4）。`judge_to` と同作法で、19章§3の**日本語ラベル**（部内投稿／現場の声／ウォッチ）を入力規則で選ばせ、ui層が `modUICase.EnumEn("inbox_source_kind", ...)` で機械値へ戻してから `NewInboxItem` へ渡す。表に無いラベルは fail-closed で「発信元の種別は一覧から選んでください（部内投稿／現場の声／ウォッチ）」と案内して投函しない。空欄は既定 `member_post`。データ行の `source_kind` は従来どおり機械値（store が書く）**ビルド台帳（build/sheets_main.json）の静的DVも `judge_to` と同じく日本語enum（`source_kind_ja`）を焼く**（v2.5.3・裁定書12 V4）。起動時の `ApplyEnumValidation` が張り直すまでの間（マクロ無効で開いた状態・DV適用が失敗した起動）に機械値のドロップダウンが残ると、fail-closed の投函が全て止まるため。**入力列（DVは日本語）とデータ行（機械値）の非対称は本節の規定どおりであり、DVは既存セルの値を検査しないので確定行が赤くなることはない**。

#### ファイル名生成規則（`modUtilText.SanitizeFileName`）

company は案件入力の自由記述であり、生のままファイル名に使わない。企業ドシエファイル・`report_path`（HTMLレポート）・`ppt_path`（PPT）の3経路とも、以下の規則で生成した名前のみを使う（16章 E-21 と相互参照）。

`Public Function SanitizeFileName(ByVal name As String) As String`

1. Windowsファイル名の禁止文字 `\ / : * ? " < > |` と制御文字（Chr(0)-Chr(31)）を `_` に置換する。
2. 前後の空白を除去し、末尾のピリオドを除去する（末尾ピリオドはWindowsが黙って落とすため）。
3. 正規化後の文字列を先頭から32字で切り詰める。
4. 末尾に8桁のハッシュを `_` 区切りで付与し、同名社2件の衝突を避ける。**値源は対象で分ける**（v2.5・裁定書9 B7）: HTMLレポート・PPTは **case_id 由来**（case_id の `Fnv1a64Hex` 先頭8桁。1案件1出力なので案件ごとに違ってよい）、**企業ドシエファイルだけは company 由来**（`Left$(Fnv1a64Hex(NormalizeForHash(company)), 8)`。`dossier_meta.company_id` と同じ式）とする。企業ドシエで case_id 由来を使うと、同じ会社の2件目の案件が必ず別ファイルになり「1社1ファイル・追記して育てる」（FR-45・本節 運用）が成立しないため。
5. ディレクトリを含めた最終パス長が240字を超える場合は、company 部を丸ごと `Fnv1a64Hex`（16桁固定）に置換して再構成する（MAX_PATH 260 の手前で止める）。

命名テンプレート（拡張子を除く）:

| 対象 | テンプレート | 例 |
|---|---|---|
| 企業ドシエファイル | `<Sanitize(company)>_<8桁>_企業カルテ` | `A社_B社_1f3c9a02_企業カルテ.xlsx` |
| HTMLレポート | `<Sanitize(company)>_<8桁>_リスクレポート_<yyyymmdd>` | `A社_B社_1f3c9a02_リスクレポート_20260901.html` |
| PPT | `<Sanitize(company)>_<8桁>_提案骨子_<yyyymmdd>` | `A社_B社_1f3c9a02_提案骨子_20260901.pptx` |

`<yyyymmdd>` は `modUtilText.IsoDateCompact(Date)` の値であり、テンプレートの一部として**必ず付与する**（v2.5・裁定書9 B4。日付を落とすと同一案件の再生成が同名になる）。同名ファイルが既に存在する場合は上書きしない。末尾に `_2` `_3` の連番を付けて空きを探し、新規ファイルとして作成する（過去の出力を消さない。書出は `adSaveCreateOverWrite` 一択にせず、存在検査と連番探索を必ず通す）。ただし企業ドシエファイルは1社1ファイルであり、既存ファイルへの追記が正しい動作であるため連番を作らない（§2.8 運用）。ファイル名も外部由来テキストであるため、シート・CSVへ書き戻す際は `SetCellSafe` を通す（16章 E-46）。**連番サフィックスの字数**（v2.5.1・裁定書10 m2・注記のみ）: 手順5の240字判定は**連番を付ける前**の名前で行うため、連番（`_2`～`_9999`）で最終パスは最大+5字となりうる。240+5=245 字は MAX_PATH 260 未満に収まるため実害はなく、この挙動を仕様として容認する。

### 2.9 画面シートの型と参照規約

11章が「画面」として定義するシートのうち、§2.1-§2.7に列定義を持たない8シート（ナビ / 使い方 / S1-S4 / ヒアリングシート / 壁打ち）を、データとしては次の2型に分ける。T-02のシート雛形生成と照合スクリプト、および19章§5の「13章のシート・列と11章の画面項目が一致」の検査は、本節以降の定義を唯一の参照先とする。

|---|---|---|---|
| **帳票型** | `ナビ` / `使い方` | 1行目ヘッダを持たない。全ての値は**名前付きレンジ**で読み書きし、セル番地をコードに書かない | 11章§3のワイヤーフレーム（見た目の変更で名前付きレンジの名前は変えない） |

**ヘッダ行の位置**: テーブル型のうち**単一表のシート**（案件一覧・case_data・フィードバック・受信箱・判断台帳・ログ等）は**1行目=物理名ヘッダ**である。これに対し**複数ブロックのシート**（S1-S4）と**印刷見出しを持つシート**（ヒアリングシート・壁打ち）は、**各ブロックの先頭行=物理名ヘッダ**とし、位置はブロックアンカー（名前付きレンジ）で解決する（1行目にヘッダが来るとは限らない。実装・照合スクリプトとも行番号を仮定しない）。

テーブル型のうち S1-S4 の4シートは、15章スキーマが入れ子構造であるため**1シートに複数のテーブル（ブロック）を縦に並べる**。各ブロックは、ブロック名と同名の名前付きレンジ（ヘッダ行の左端セルを指す）をアンカーとして持ち、実装はこのアンカーからヘッダ行を特定する。ブロックとブロックの間には空行を1行以上置く（空行が表の終端。§2.2 逆シリアライズ規約5）。

名前付きレンジの命名規約: 帳票型は `hm_`（`ナビ`）/ `ci_`（`ナビ`）/ `dr_`（`ナビ`）/ `nv_`（`ナビ`）/ `gd_`（`使い方`。§2.18）を接頭辞とし、テーブル型のブロックアンカーはブロック名そのもの（例 `s2_risks`）を名前とする。加えて、テーブル型のうち**単票的な見出し・印刷用の固定セル**を持つ2シートは `hs_`（`ヒアリングシート`。§2.16）/ `sp_`（`壁打ち`。§2.17）を接頭辞とする名前付きレンジで参照する（列ではなくセル1点を指すため列物理名では照合できない。19章§5の照合手順もこの2接頭辞を名前付きレンジ側で突合する）。ブック内で一意。

#### (c) 保存経路（既存契約は不変）

- **保管**: `modUICase6.StoreArea(dataKey, content)` は `modCaseStore.SaveData` を呼ぶ。本文は `modUtil.SplitForCells(content, 32,000)` にかけて `case_data` の複数行へ入る（§2.2）。**`SplitForCells` の契約も 32,000 という値も変えない**。
- **読み出し**: `modUICase6.LoadArea(dataKey)` は `modCaseStore.LoadData`（区切りなし連結）で戻す。**区切りを `vbLf` へ変えてはならない**（機械切断との可逆性が壊れる。v2.5.1・裁定書10 M3）。
- **プレビュー**: `modNavText.PreviewLines(content, 5)` は先頭5行を返す純関数（各行は先頭120字で切り、切ったら末尾に `…` を付す）。**表示専用**であり、プレビューから本文を復元する経路は作らない。
- **直貼り枠の取り込み**: `modUICase6.ReadDirectPaste(rangeName)` は枠を上から走査し、最終の非空行までを `vbLf` で連結して返す。取り込んだら枠を空にする。**見張り行が空でなければ overflow** として呼出側へ返す（切り分けを求めず[ここに貼る]へ誘導する）。
- **既知フッターの除去**: `modNavText.StripDrFooter(text)` は 11章§3.3.5 の規則そのままの純関数（行頭一致の語の一覧・末尾から先頭へ走査・複数一致は先頭に近いものを採る・本文の先頭50%より前でしか一致しなければ切らない・それ以外の整形はしない）。**[ここに貼る]でも直貼りの取り込みでも同じ関数を通す**。語の一覧の正は 15章§2.0 である（本章と11章には一覧を置かない）。
- **撤回**: v3.1 の予約範囲への1行1セル展開（`ReadArea` / `WriteArea`）は**実装しない**。予約行という考え方ごと撤回した（11章§3.3.0）。

#### (d) 現場メモの分解規約（純関数・層(a)テスト対象）

画面の欄は1つだが、保存先の `data_key` は9本のままである。保存時に見出しで切り分ける（`modNavText.SplitFieldNotes` / `JoinFieldNotes`）。

| 切り分けた部分 | 保存先 data_key |
|---|---|
| `【営業メモ】`・`【前回更新メモ】`・`【付保の見立て】` の3つの節 | `input_memo` へ、見出しごと `vbLf` で連結して1本にする（節が空でも見出しは残す） |
| `【付保の見立て】` の節の本文（見出し行を除く） | **`input_coverage_note`**（v2.6・裁定書25 S1。節が空なら空文字）。上の行と**重複して保存する**（`input_memo` からは落とさない） |
| `【そのほか】` の節と、どの見出しにも属さない先頭部 | `input_field_notes` |

- **`「例: 」` で始まる行は、どの節でも保存しない**（先置きした例文がAIへ渡るのを防ぐ。判定は前後の空白を除いた行頭からの完全一致）。
- **見出しが1つも見つからないときは全文を `input_memo` へ入れる**（先頭に `【営業メモ】` を1行足す）。利用者が見出しを消しても壊れない。
- 見出しの判定は**行頭からの完全一致**（前後の空白を除去して比較）。部分一致・正規表現は使わない。
- **`input_coverage_note` の二重保存（v2.6・裁定書25 S1）**: 【付保の見立て】は `input_memo`（→ 15章 S1 user の `{{memoText}}`）と `input_coverage_note`（→ 同 `{{coverageNoteText}}`）の**両方**へ届く。**両方を連結して渡す**のが本裁定の解決であり、どちらか一方を落とす判断を実装に持たせない（S1 system 第9ルールが【付保の見立て】を「確度の低い伝聞」として一貫して扱うため、二重に届いても評価は変わらない。逆に片方を落とすと、現場メモの見出しを消した利用者の入力が丸ごと消える経路ができる）。`JoinFieldNotes` の可逆性は `input_memo` 側だけで成立させ、`input_coverage_note` は**派生（読み取り専用の写し）**として扱う。

#### (e) `ci_case_id` の3値判定（v2.5.3・裁定書12 V1 から不変）

**このセル1つが「どの案件の画面か」の唯一の根拠**である（`sN_case_id` と同作法。揮発性のモジュール変数は判定に使わない）。書き手は3つ: (1) ナビの描画（`modUINav.DrawNav`）は冒頭で空へ戻し、**描き切ったときだけ**案件IDを書く。(2) コーチ帯の案件プルダウンで先頭項目 `（新しい案件）` を選ぶと、**画面を全クリアしてから**固定マーカー **`(新規)`** を書く（`IsValidCaseId` は案件ID書式だけを通すのでこの値を有効IDと誤認しない。W1 の第1の壁）。(3) `CreateCaseFromSheet` は採番に成功した瞬間に新しい案件IDを本セルへ書き戻す。

[貼ったものを保存する]（`modUICase6.SaveNav`）は本セルの3値で分岐する: **`(新規)`**＝ここで採番 / **有効な案件ID**＝その案件へ保存 / **空・その他**＝**1欄も書かずにブロック**し、E0302 を記録して `hm_warning` へ「画面の案件と保存先が合いません。いちばん上の帯で、案件を選び直してください。」を出す（MsgBoxは使わない）。**[ここに貼る]も押した瞬間に同じ3値判定を通す**（保存まで待たない。一致しなければ1字も書かない＝第2の壁）。ただし画面が**新規モード（固定マーカー）**のときは、[ここに貼る]の中で採番してから保存する（書き手(3)）。先に[貼ったものを保存する]を押さないと1本目が貼れない、という順序の罠を作らないためである。

**個人情報の検査も[ここに貼る]の中で行う**（`ScanPasteFields`。16章 E-05）。検知したら1字も `case_data` へ書かず、11章§3.3.7 の文を出す。

#### (f) 削除（v3.2）

旧 `案件入力` シートの属性欄のうち画面から撤去した6本（取引・幹事・BID・再保／キャプティブ・他社付保メモ・提案書の種類）と、品質の上書き・匿名化トグル・収集レシピ14個・貼付欄17本（本欄9＋続き欄8）・字数カウンタ3本は**本章から削除した**（列と enum は案件一覧側に残る。撤去の一覧は 11章§3.3.9 が正）。ビルド台帳（`build/sheets_main.json`）からも同時に削除する。旧シートは**作って隠すのではなく、シートごと作らない**（11章§1.1）。

| category | **19章§3のリスクユニバース10分類**（S2出力の `category` と同一語彙）。`LoadKnowledge` の検査対象（16章 E-34 / E0402） |
| headline | 事故の見出し（1行・60字以内） |
| cause | 何がどうなって事故に至ったか（原因・経過） |
| loss_scale | 損害規模（公表値・概算。不明なら空欄） |
| lesson | この事例から引ける教訓・確認点（S2の `check_points` の材料） |
| source | 出所（公表記事・社内支払経験・報道等）。**顧客名・個人名は書かない**（§4の個人名の保存禁止と同じ規律。匿名化して登録する） |

- 注入時の1行書式は15章§3の整形例が正（`[IC-09-004] カテゴリ:… 見出し:… 原因:… 損害規模:… 教訓:… 出所:…`）。空欄の項目はその部分ごと省略する（空の項目名を出さない。`market_note` と同じ作法）。
- **解釈はKB側（月次編集会）が持つ**。`lesson` は人が書く欄であり、AIに埋めさせない。現場記録は事実のみ（FR-11）という規約は不変である。
- ビルド台帳 `build/sheets_kb.json` に同時に登録する。

## 4. データ保全・ライフサイクル

- `sN_json` は**当該ラウンドの検証合格済み生出力**であり、再実行・ラウンド確定で更新される（§2.2）。不変なのは `pf_json` と run_log の行のみ。プロンプト改善の一次データは run_log（メタ）＋現ラウンドの `sN_json`／`sN_json_failed` で構成する
- 起動時 `RepairStates` は、`sN_json`（合格済のみ）の実在キーと案件一覧 `last_ok_step` の突合で status を再導出する。`failed_step` は案件一覧の値をそのまま維持し、`ui_lock` は無条件で初期化する（16章 E-12）
- 案件削除はHOMEからのみ（案件一覧＋case_data＋フィードバックの同時削除・確認必須）。受信箱・判断台帳・run_logは削除しない（累積が資産）
- ナレッジブック編集は管理者1名運用。本体からの追記失敗時はローカル退避→次回起動時再送（16章 E-13）
- 個人名の保存禁止（owner/recorded_by はWindowsユーザー名までとし、顧客側個人名は全シートで入力禁止の注記＋E-05チェック）
