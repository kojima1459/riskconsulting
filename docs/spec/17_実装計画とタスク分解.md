# 17. 実装計画とタスク分解 v2.0

## 1. 開発体制（PoC「開発憲法」踏襲）

- 司令塔（Fable）: 仕様裁定・発注・検収。実装しない
- 実装: Opus（ゲートウェイ・検証・パイプライン・COM等の難所）／Sonnet（移植・シートI/O・UI・定数化・テスト）
- 検問方式: タスク着手時に空コミット→受入条件ごとに即コミット。停止時は最後の検問から再投入
- 各実装波の完了後に敵対的レビュー1周＋Fix後もう1周
- 実装エージェント必読: docs/spec/10〜17＋19、docs/06/07、PoCの移植元ファイル（12章の対応表）。**仕様との食い違いは勝手に直さず司令塔へ報告**（裁量は変数名・文言字数のみ）

## 2. フェーズ

```
W0 準備(雛形・シート) → W1 core移植 → W2 app層(知識・検証・プロンプト・パイプライン)
→ W3 UI・出力・受信箱 → W4 結合・実機・チューニング → リリース(Phase 1)
Phase 1.5(12月〜): PL-05/06ツール化・機構ライブラリ投入
Phase 2(来期): PL-07/08（判断台帳100件超が着手条件）
```
並行人間タスク（T-90系）はW1から開始。

## 4. テスト計画

1. **ユニット（modTestsPure）**: JSON抽出・検証（分岐網羅）・分割保存・整形・打切り・enum変換・採番。`run_excel_tests.ps1` で一括実行
2. **一致検査**: 15章⇔modPrompts*/modSchemas のdiffゼロ検査（T-23）。13章⇔シート実体の照合スクリプト（T-02/03）。19章⇔enum変換表の照合
3. **結合（mock）**: UC単位のシナリオ回帰。決定的応答のため毎リリース実施
4. **実機（ribbon）**: new/renewal各1社完走＋validate_result集計
5. **品質評価**: ベテラン3軸ルーブリック。評価入力セットで改訂時回帰

## 5. リリース・運用

1. lint緑→全テスト緑→ビルド→app_version更新→15分スモーク→署名(OQ-2)→共有フォルダ配置
2. 利用者は旧版を自分でコピー置換（Phase 1は「案件使い切り」運用。移行機能はv2.1検討）
3. ナレッジブック更新は管理者随時（本体再配布不要）
4. 月次運用: 編集会（受信箱・型候補の採択）／run_log集計（repaired・failed率、所要時間、警告率）／新サービス候補の商品部報告。四半期: 型生成バッチ＋勝ち筋仮説レビュー
