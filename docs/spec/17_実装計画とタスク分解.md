# 17. 実装計画とタスク分解

## 1. 開発体制と進め方（PoC「開発憲法」踏襲）

- 司令塔（Fable）: 仕様裁定・発注・検収・レビュー。実装はしない
- 実装: Opus（難所・COM連携・ゲートウェイ）/ Sonnet（定型・移植・シート I/O・テスト）
- **検問方式**: 各タスク着手時に空コミット→受入条件の項目ごとに即コミット。エージェント停止時は最後の検問から再投入
- 実装波の完了ごとに敵対的レビュー（PoCの adversarial-review 相当）を1周。指摘Fix後にもう1周
- 実装エージェントへの必読指示: `docs/spec/10〜16` 全部＋PoCリポジトリの該当移植元ファイル。**仕様と食い違いを見つけたら勝手に直さず司令塔へ報告**（軽微な裁量: 変数名・文言字数のみ）

## 2. 実装フェーズと順序

```
W0 準備          → W1 基盤移植      → W2 ドメイン層     → W3 UI・出力      → W4 結合・品質
(リポジトリ/雛形)   (core層+mock)      (KB/プロンプト/検証)  (画面/PPT/ヒアリング) (E2E/実機/配布)
```
並行可: W2のナレッジ初期データ作成（T-90/91、人間タスク）はW1から並行。

## 4. テスト計画

1. **ユニット（modTestsPure）**: 純ロジック（JSON抽出・検証・分割保存・整形・打切り）。Excelオブジェクト非依存で書き、`wintest/run_excel_tests.ps1`（PoC移植）で一括実行。目標: 検証系は分岐網羅
2. **結合（mock_ribbon）**: LLMなしで全画面フロー。決定的応答のため回帰テストとして毎リリース実施
3. **実機（ribbon）**: 実企業データでの完走・品質確認。run_log の validate_result 集計を品質メトリクスとする
4. **品質評価**: ベテラン採点ルーブリック（網羅性/具体性/実売性 各5点）。評価入力セット（PoC対象企業の入力テキスト）をリポジトリ外の共有フォルダに保存し、プロンプト改訂時の回帰評価に使う

## 5. リリース・運用手順

1. `tools/vba_lint.py` 緑 → ユニット・結合テスト緑 → ビルド（build/スクリプトでxlsm生成）→ 版番号更新（config app_version）
2. 実機スモーク（PoC docs/45 方式の15分チェックリストをRPN用に作成: T-44に含む）
3. 署名（OQ-2）→ 共有フォルダへ `リスク提案ナビ_vX.Y.Z.xlsm` 配置 → 利用者は旧版を自分でコピー置換（案件データは各自のブック内に残るため、**移行機能: 旧ブックから案件一覧+case_dataをインポートするボタンを v1.1 で追加検討**。v1.0 PoC期間は「案件は使い切り」運用と割り切る）
4. ナレッジブック更新は管理者が随時（本体の再配布不要な分離設計の利点）
5. 月次運用: フィードバック→成功事例昇格レビュー / run_log集計（repaired/failed率・所要時間）/ 新サービス候補の商品部への報告
