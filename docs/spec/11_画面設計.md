# 11. 画面設計（体験設計）v3.1

v3.1（裁定書19 裁定B: 実機第3報「タブが多くて迷子」への回答）: v3.0 は体験設計を書き起こしたうえで、利用者が見るタブを **HOME / 調査の指示文 / 案件入力 の3枚**に分けた。実機で返ってきた言葉は「タブが多くて迷子」「HOMEと案件入力の違いが分からない」「調査の指示文から入力するのか、案件入力が先か、HOMEが先か、開いた途端に迷子」だった。**分けたこと自体が原因**である。

v3.1 はこの3枚を **1枚のシート `ナビ` へ統合**し、利用者が既定で見るタブを **`ナビ` と `使い方` の2枚だけ**にする。`ナビ` は縦スクロール1画面で、上から **①会社のこと → ②貼る → ③作る → ④出す** の4区画が並ぶ。**上から下へ、①②③④の順に降りれば終わる**。どのタブから始めるかを選ぶ場面が無くなる。

v3.0 からの差分（本改訂で書き換えた節）:

| 節 | v3.0 | v3.1 |
|---|---|---|
| §0.2 | 初回に見せる3画面 | **利用者が見るタブは2枚**（ナビ／使い方）。他は既定で非表示 |
| §1 | 可視シート14枚 | **既定可視は `ナビ` と `使い方` の2枚**。`HOME` / `案件入力` / `調査の指示文` は**廃止（ナビへ統合）**。各シートの初期可視状態は13章§2.9の可視性表と同期する |
| §2 | 3画面をまたぐ1日 | ナビ1画面の4区画に沿った1日（トーストの逐語文は維持・宛先だけ更新） |
| §3.1 | HOMEのワイヤー | **ナビ1画面のワイヤー**（次の一手＋4区画） |
| §3.2・§3.3 | 独立タブ2枚のワイヤー | **ナビの区画①・区画②**の節へ書き直し。貼る欄は9欄から**6欄**へ（`data_key` 9本は不変。§3.3.2の連結規約で吸収する） |
| §3.6 | 操作ガイド（7章立て） | **使い方タブ**。実用文だけを書く（体験原則などの抽象語は載せない） |
| §3.8 | ― | **新設**。HTMLレポートの体裁は `docs/demo/確認用v2/出力サンプル⑤春華堂.html` を正とする |
| §8 | 影響モジュールと3弾の順序 | 中心を「**既存の名前付きレンジをナビシートへ付け替える**」案の実現性評価へ差し替え |

v3.0 で確定した中身（体験原則・トースト規約・貼付エリアの読み書き契約・自動化する判断・状態遷移・UI実装規約）は**そのまま生きている**。変わったのは**器の枚数**である。**13章参照による列定義の分業**（本章＝配置と操作の正／13章＝列の物理名・物理順の正／19章＝enumの正）も不変である。

UserFormは使わない。シート上の図形ボタン＋セル表示で構成する（PoC流儀・32bit互換・保守性）。

旧版の改訂履歴（v2.4〜v2.5.1）は docs/20 と各裁定書に残す。

## 0. 体験原則（この章のすべてがここに従属する）

**この節は設計者のための節である**。ここに書いた言葉（原則・体験・導線・区画）を**利用者の目に触れる面へ書き写してはならない**。実機で「ガイドが抽象的で実用的でない」と言われた原因はこれである。利用者が読む面（ナビの案内文・使い方タブ・トースト）は、§3.6 の作法で**やることだけ**を書く。

### 0.1 六原則（裁定書17 裁定B①〜⑥。姉妹製品の憲章§3を採用）

| # | 原則 | 本製品での意味 |
|---|---|---|
| ① | **押せるものは必ず反応する** | 無反応は故障と同義。押した結果が画面外・スクロール外にしか出ないものは「反応していない」と数える。**セルがA1へ動くだけ**は反応ではない |
| ② | **待ち時間は進捗を見せる** | 「止まっているのか動いているのか分からない」状態を作らない。LLM呼び出しは最長20分あるため、呼び出しの**前に**進捗4行を書き切る（E-50a） |
| ③ | **失敗は「何が起きたか。次に何をするか。」の2文** | エラーコードだけの表示・専門用語だけの案内は失敗の隠蔽と同じ。利用者向けの文にコード（E0302等）を出さない。コードは err_log にだけ残す |
| ④ | **OS/Officeの生ダイアログに晒さない** | VBAの実行時エラーダイアログ・OLE待ちダイアログ・「〜が応答していません」に到達させない。どうしても出るものは事前に説明を出す |
| ⑤ | **データは失わせない** | 貼った文章・手で直した下書きを、失敗や再実行で黙って消さない。消える可能性のある操作は必ず事前に告げる |
| ⑥ | **開いた瞬間に、次の一手が1つだけ見える** | `ナビ` の最上段は**次にすることを名指しする1行**（`hm_next_action`）で始まり、**ウィンドウ枠固定（`FreezePanes`）でスクロールしても消えない**。この1行を読めば、他を何も知らなくても前へ進める |
| ⑦ | **選ぶ場面を作らない（v3.1で追加）** | 「どのタブから始めるか」も選択である。**画面が複数あること自体が判断を強いる**。利用者が能動的に選ぶのは「どの案件か」だけにし、それ以外は上から下へ降りるだけにする |

原則⑦は本改訂で足した。v2.5.1 のHOMEは「案件」「進捗」「状態表示」「受信箱」「主要動線4本」「くわしい操作18本」を**同時に**見せていた。v3.0 はそれを整理したが、代わりに**3枚のタブへ横に分けた**。情報量は減っても、**入口が3つある**かぎり「どれから」という判断が残る。v3.1 は入口を1つにして、この判断ごと消す。

### 0.2 利用者が見るタブは2枚（これ以外は既定で非表示）

| タブ | 利用者の言葉での役割 |
|---|---|
| **`ナビ`** | ここだけで仕事が終わる画面。上から**①会社のこと → ②貼る → ③作る → ④出す**の順に降りる。最上段のコーチ帯が「いま何をするか」を1文で言い続ける |
| **`使い方`** | 困ったときに読む説明。ナビの①〜④と同じ順で「何をどこへ・押すと何が起きる・うまくいかないとき」だけを書く（旧 `操作ガイド`） |

**他のシートは既定で非表示**にし、必要になった瞬間だけ出す。出し方の規則は下表が正であり、13章§2.9 の可視性表と**一字一句同期する**（片方だけ直さない）。

| シート | いつ見えるようになるか | 誰が可視にするか |
|---|---|---|
| `AIの下書き① 会社の理解`〜`④ 提案の骨子` | ナビ区画④の**[下書きを見る]を押したとき**（4枚まとめて可視にし、①へ移る） | `modUINav.ShowDrafts` |
| `ヒアリングシート` | ナビ区画④の**[ヒアリングシートを出す]で作成に成功したとき** | `modUIHome.HomeBuildHearing` の成功分岐 |
| `err_log` / `run_log` / `usage_log` | 使い方タブの「困ったとき」の**[記録を見る]を押したとき**（3枚まとめて可視にし、`err_log` へ移る） | `modUIGuide.ShowLogs` |
| `壁打ち` / `受信箱` / `商談の記録` / `判断台帳` | 使い方タブ末尾「上級」の各行の**[表示する]を押したとき**（押した1枚だけ） | `modUIGuide.ShowAdvanced(sheetKey)` |

| `case_data` / `config` / `vba_src` | 出さない（管理者がタブの再表示で開く） | ― |

- **一度出したシートは、そのブックでは出したままにする**（出したり隠したりを繰り返すと、利用者は「さっき見たタブが消えた」と感じる）。次にブックを開いたときは既定の2枚へ戻る。
- **可視にしたシートには必ず1行目に `[ナビへ戻る]` ボタンを置く**（§3.4）。行き止まりを作らない。
- **タブを非表示にすることは、機能を消すことではない**。上級機能の公開Subは可視状態に関係なく動く（§7.2c）。

### 0.3 利用者像（これを外すと設計が壊れる）

- **ITに詳しくない営業所員**（50代を含む）。エラーコードもフォルダ構成も知らない。**「わけの分からない表示」が一度出たら、その機能は二度と使われない**。
- 自分のPCではなく**会社の管理端末**（Excel 32bit・EDR・ネットワーク共有・ダウンロード制限）。開発者が横にいない。
- 社内ディープリサーチは**直列でしか使えない**（1本が終わるまで次を投げられない・1本あたり約10分）。「まとめて投げて放置」は**誤り**であり、この表現を製品と文書から除去する（裁定書17 裁定A H5）。
- 期待している成果は1つだけ:「**調べたことを貼る → ボタンを押す → お客様に見せられるレポートと、訪問で聞くことの紙が出る**」。
- 判断を求められると止まる。**選択肢は「意味が分かるもの」だけを残し、残りは製品が決める**（§5）。
- **いま自分がどこにいるのかが見えないと不安になる**（実機第3報「ステップで今の作業位置が分かるのが良い」）。ナビは常に「STEP n/6」と「いま何をするか」を最上段に出し続ける（§3.1）。

## 2. 利用者の1日（ユーザージャーニー）

対象: 更新案件1件の準備。**人が手を動かすのは合計30分ほど**、待ち時間を含めて半日。時刻は目安である。

**v3.1 では画面の移動が無い**。1日を通じて利用者が見るのは `ナビ` の1枚だけであり、変わるのは**ナビのどこにいるか**（区画①→②→③→④）と、**最上段のコーチ帯が何と言っているか**である。

各ステップは「**区画 / 押すもの / 見えるフィードバック / 失敗したときの案内**」の4点で書く。フィードバック欄の文はトースト（§4）とコーチ帯の**逐語の完成文**である。

### 2.1 全体像

1. **どこか1つでも「押しても何も見えない」ボタンがあると、そこで一日が止まる**（§4 のトースト必須はこのため）。
2. **待ち時間に画面が固まったように見えると、二度と押されない**（§4.2 の進捗4行）。
3. **貼る作業に「分ける」判断が入ると止まる**（§3.3 の貼付エリア方式＝続き欄の撤去）。
4. **意味の分からない選択肢が1つでもあると、その画面全体が「難しい画面」に見える**（§5 の自動化）。
5. **「いま自分がどこにいるか」が見えなくなると止まる**（v3.1で追加）。コーチ帯は**常にウィンドウ枠固定で見えていること**。スクロールで帯が消える実装は本章違反である（§3.1.1）。
6. **画面が2枚以上になると、どこから始めるかで止まる**（v3.1で追加）。作業用のシートを1枚増やす提案は、本節の事実に照らして却下されるべき既定を持つ。

#### 3.3.1 6つの欄（v3.0 の9欄から統合。`data_key` 9本は不変）

**貼る欄を6つに絞る**。9つ並べたことが「どこへ貼るのか分からない」の一因だった（実機第3報）。**並び順は「利用者が実際に手を動かす順」**であり、15章 `BuildS1User` の9ブロック出現順とは**一致させない**（出現順は §3.3.2 の保存規約が保証する）。

| 表示順 | 画面ラベル（逐語） | 名前付きレンジ | 予約行 | 見張り行 | 保存先 data_key | 出る条件 |
|---|---|---|---|---|---|---|
| 1 | `調べた結果` | `ci_area_dossier` | 800 | `ci_sent_dossier` | `input_dossier` | 常に |
| 2 | `会社のホームページ` | `ci_area_hp` | 400 | `ci_sent_hp` | `input_hp` | 常に |
| 3 | `有価証券報告書のリスクの章` | `ci_area_yuho` | 800 | `ci_sent_yuho` | `input_yuho` | 常に |
| 4 | `現場メモ（手で書く欄）` | `ci_area_field_notes` | 400 | `ci_sent_field_notes` | `input_memo` ＋ `input_field_notes`（§3.3.2） | 常に |

予約行の合計は **2,800行**。①`調べた結果` が800行なのは、ディープリサーチ3本ぶんを1欄で受けるためである。

> **予約行は仮置きである**（v3.1）。社内DRの返答1本を **3,000〜8,000字** と想定し、3本で最大24,000字、1行あたり40字として600行。余裕を見て800行を置いた。**実物の字数を受け取ったら本表を確定する**（§10 #5）。

**出る条件が偽の欄は、行ごと非表示にする**（`Rows.Hidden = True`）。**セルの中身は消さない**（原則⑤。種別を「新規」へ戻しても、いまの契約に貼った文章は保持され、保存もされる）。**図形ボタン `ci_btn_paste_*` は非表示行の上に置かない**（隠れた図形が残ると誤クリックの元になる。行を隠す前に当該欄のボタンを削除し、出すときに作り直す）。

**貼付エリアの構造**（v3.0 から不変）:

- **1欄＝1本の縦長レンジ**（1列 × 予約行数）。利用者は**いちばん上のセルをクリックして Ctrl+V を1回押すだけ**。Excelはクリップボードの改行を行に割り、上から順に埋める。**利用者は「分ける」判断をしない**。
- セルの物理上限32,767字にぶつかるのは「**改行の無い1段落が32,767字を超えるとき**」だけになる。起きたときは §3.3.4 の1件だけを案内する。
- **列幅は広く（既定100）・折り返しはOFF（`WrapText = False`）・行高は15pt固定**。折り返しをONにすると800行が縦に伸びて画面が使い物にならない。セルの表示が途中で切れても、中身は全部入っている。
- 欄と欄のあいだに**境界行**「▲ ここまでが「〈欄名〉」です」を1行置く（灰色地・`Locked = True`）。その下に**見張り行（sentinel）を1行**置く。ここは常に空でなければならない。

#### 3.3.2 読み書きの規約（§7.2(a) へ規約本文、ここは要点）

- **読み（画面→保存）**: 予約範囲を上から走査し、末尾の空行を落として、**行を `vbLf` で連結**して1本のテキストにする。
- **書き（保存→画面）**: 保存されたテキストを `vbLf` で分割し、上から1行1セルへ書く。**読み→書き→読みで1字も変わらない**。
- **`case_data` への保存は既存契約のまま**（`modUtil.SplitForCells(content, U3_CHUNK=32,000)`）。**貼付エリアは画面側の入力方式であって、保存形式は一切変えない**。

**現場メモ欄の分解規約（v3.1の新規定）**: 画面の欄は1つだが、**保存先の `data_key` は9本のまま**である。`ci_area_field_notes` は次の4つの見出しをあらかじめ書いた状態で描画され（利用者は見出しの下に書き足すだけ）、保存時に見出しで切り分ける。

```
【営業メモ】
【前回更新メモ】
【付保の見立て】
【そのほか気づいたこと】
```

| 切り分けた部分 | 保存先 `data_key` |
|---|---|
| `【営業メモ】`・`【前回更新メモ】`・`【付保の見立て】` の3つの節 | **`input_memo` へ、見出しごと `vbLf` で連結して1本にする**（節が空でも見出しは残す） |
| `【そのほか気づいたこと】` の節と、どの見出しにも属さない先頭部 | `input_field_notes` |
| ― | `input_prev_renewal` と `input_coverage_note` は**常に空文字**で保存する |

- **見出しが1つも見つからないときは、全文を `input_memo` へ入れる**（先頭に `【営業メモ】` を1行足す）。利用者が見出しを消しても壊れない。
- 見出しの判定は**行頭からの完全一致**（前後の空白を除去して比較）。部分一致・正規表現は使わない。
- **15章 `BuildS1User` の9ブロックの出現順・ブロック見出しは不変**である。`input_prev_renewal` / `input_coverage_note` は空になるため、既存規約どおり **`なし` を差し込んだ空ブロックとしてプロンプトへ渡る**。**`prompt_diff` には触れない**（15章のテンプレート文字列を1字も変えない。空ブロックは既存の空欄処理がそのまま担う）。
- この分解と再結合は**純関数**（`SplitFieldNotes(text) → (memo, others)` / `JoinFieldNotes(memo, others) → text`）として core へ置き、層(a)の可逆性テストで検査する（§8.3）。

**そのほかの規約**（v3.0 から不変）:

- 旧 `ci_paste_*` に入っている既存案件も、読み出し側（`JoinField` の区切りなし連結）を残せばそのまま読める（§8.3 移行）。
- **1セルが32,000字を超えていたら**、その欄は保存をブロックする（§3.3.4）。
- **`=` `+` `-` `@` で始まる行**は、書き戻し時に必ず `SetCellSafe` を通す（16章 E-46）。`ci_count_*` も数式にしない。

#### 3.3.3 [ここに貼る]ボタンと字数の表示（裁定書18 で確定・v3.1で6本へ）

**貼る手段を2本立てにする**。第一の手段は各欄の見出し右に置く図形ボタン、第二の手段は従来どおりの Ctrl+V 直貼りである。**常駐タイマーは作らない**。

##### (1) [ここに貼る] ボタン（第一の手段・推奨）

| 図形キー | 置き場所 | キャプション | OnAction |
|---|---|---|---|
| `ci_btn_paste_dossier` / `_hp` / `_yuho` / `_field_notes` / `_contract` / `_hearing_answers`（**6本**） | 各欄の見出し行の右端 | `ここに貼る` | `modUICase6.PasteInto<欄>`（6本。実体は共通の `PasteIntoArea(areaKey)`） |

押したときの処理（順序が正）:

1. クリップボードから**テキストだけ**を取り出す（**書式は読まない**）。経路は既存の `modUICase4.CopyResearchRow` と同系（`DataObject` の遅延バインド。事前参照設定はしない＝32bit/64bit・参照設定なしで動く形）。
2. 取り出したテキストを改行（`vbCrLf` / `vbCr` / `vbLf` のいずれも1つの改行として扱う）で分割し、**予約範囲へ上から1行1セル**で `SetCellSafe` 経由で書く。書く前に予約範囲と見張り行をクリアする。
3. **その場ではみ出しを見る**（分割後の行数が予約行数を超えたか／1行が32,000字を超えたか）。超えていたら §3.3.4 の該当文をトーストで出し、その欄に overflow を立てる。
4. **その場で字数を数え直す**（当該欄と合計）。
5. 成功トースト（逐語）: 「〈欄名〉に 8,234字 入りました。次の欄へ進んでください。」

**現場メモ欄だけは扱いが違う**: [ここに貼る]は**見出しを消さずに、いま選んでいる見出しの下へ差し込む**（4つの見出しのどれも選んでいなければ `【そのほか気づいたこと】` の下）。予約範囲を丸ごとクリアしない（原則⑤。手で書いた他の節を消さない）。

このボタンで貼ることの効き目は、字数の即時更新だけではない:

- **書式を持ち込まない**。ブラウザからの Ctrl+V は HTML の表・罫線・画像・背景色・**結合セル**をシートへ持ち込み、貼付エリアの構造を壊す。テキストだけを読む経路なら、これが**構造的に起きない**。
- **はみ出しをその場で検知できる**（保存まで待たない）。
- **貼り先を間違えない**（押したボタンの欄へ必ず入る）。

見出しの下に灰色の小さな案内文を常設する（逐語）:

> 「[ここに貼る]を押すと、表の線や画像が入らずに文だけが入ります。Ctrl+V で直接貼ってもかまいません。」

##### (2) Ctrl+V 直貼り（第二の手段・許容する）

- 従来どおり、枠のいちばん上のセルをクリックして Ctrl+V でも貼れる。**この経路を塞がない**（利用者の手癖を否定しない）。
- ただし直貼りでは VBA が動かないため、**字数は自動では更新されない**。字数は次の2点で数え直す:
  1. **ナビを描いたとき**（`DrawNav` の末尾）
  2. **[貼ったものを保存する]を押したとき**（`SaveCaseInput` の冒頭）
- そのため字数表示には**数えた時刻を必ず添える**（逐語）: 「会社のホームページ 8,234字（14:03時点）」。時刻がないと、利用者は古い数字を今の数字だと信じてしまう。
- 直貼りで持ち込まれた結合セル・画像は、**保存時に検知**して §3.3.4 の該当文を出す（[ここに貼る]で貼り直せば消える）。

##### (3) 上限の色分け（両方の手段に共通）

- 目安以内＝黒／目安の9割超＝橙「もう少しで目安です」／目安超＝赤「目安を超えています。作るときに後ろが切られることがあります」。
- 目安は `dossier_tier` から決まる（`max_context_chars` 40,000 / `t2_max_context_chars` 100,000。§5）。
- **超えていても保存も実行も止めない**（打切り規則は16章 E-03 のまま）。

## 4. フィードバック規約（原則①〜④の実装規約）

### 4.1 全ボタンにトーストを出す（例外なし）

- **押した図形ボタンは、必ず 0.5秒以内に何かを画面へ返す**。返し方はトースト（`modUIToast`。図形カード＋`Application.OnTime` 自動消去・Shape接頭辞 `ts_`）。姉妹製品の技法を移植する（裁定書17 裁定A H2）。
- **セルを移動させるだけ・シートを切り替えるだけは「反応」に数えない**。シート切替でもトーストを出す（「〈画面名〉を開きました。〈次にやること〉。」）。
- **文の型**:
  - 成功: 「**〈何が起きたか〉。次は〈次の一手〉。**」 例:「案件 C-20260901-001 を保存しました。次は③の[まとめて作る]を押してください。」
  - 失敗: 「**〈何が起きたか〉。〈次に何をするか〉。**」 例:「ヒアリングシートを作れませんでした。先に③の[まとめて作る]を押してください。」
- **禁止**: エラーコード（E0302 等）・英語・`enum` の機械値・モジュール名・「ドシエ」「ティア」「プレイ」「プリフライト」等の開発語を**利用者向けの文へ書かない**。コードとモジュール名は `err_log` にだけ残す（原則③・§7）。
- トーストは**成功＝緑・注意＝橙・失敗＝赤**の3色。文字量に応じて表示時間を伸ばす（短文3秒〜長文9秒）。**トーストの失敗が業務処理を壊してはならない**（`modUIToast` の全公開入口は `On Error Resume Next` で包み、失敗しても「トーストが出ない」に留める）。
- **`hm_warning`（ナビ区画④の「お知らせ」）は残す**。トーストは消えるが、`hm_warning` は残って読み返せる。**警告は必ず両方に出す**（実機で「hm_warning が視認されない」事象が起きたため、片方だけにしない）。

### 4.2 待ち時間の見せ方（3段構え）

**事実の確認**: 社内リボンの呼び出しは**同期**である（`Wait` はタイムアウト秒であって、非同期モードは無い）。呼出中はVBAが制御を返さないため、**呼んだあとに画面へ書き足すことはできない**（16章 E-50a）。したがって「待っているあいだ動く進捗」は、**呼ぶ前に描き切る**か、**別のプロセスに呼ばせる**かのどちらかしかない。

本章は3段構えで書く。**(1)(2) は第1弾で必ず実装する**。**(3) は実験であり、成否で採否を決める**（手順と判定基準は §8.7）。

#### (1) ステータスバー（いちばん確実・ゴースト化しても読める）

Windowsが「応答していません」と判断してウィンドウを白く塗りつぶしても（ゴースト化）、**タイトルバーとステータスバーの文字は残る**。ここに1行だけ状況を書く。

```
呼出の直前:
  Application.DisplayStatusBar = True            ' 非表示設定の端末があるため必ず立てる
  Application.StatusBar = "考え中… ② リスクの洗い出し（開始 14:03・最大20分）"
呼出のあと（成功・失敗のどちらでも必ず）:
  Application.StatusBar = False                  ' Excelへ返す（空文字ではなく False）
  Application.DisplayStatusBar = <元の値>
```

- **`DisplayStatusBar` は呼出の前に必ず `True` にする**。会社の端末ではステータスバーが非表示に設定されていることがあり、そこへ書いた文字は誰にも届かない（姉妹製品での実例: `notebook/src/ui/modWorkExcel.bas:35` 付近の記録「ステータスバーは非表示設定のためそこに書いた文字は誰にも届いていなかった」）。
- **元の値を退避し、必ず戻す**（他人の設定を書き換えたままにしない）。退避と復帰は `ExitUiLock`（E-50d）と同じ場所に置き、**失敗経路でも必ず通す**。
- 文（逐語）: `考え中… 〈段の名前〉（開始 hh:mm・最大N分）`。**「考え中…」で始める**（利用者が読んで意味の分かる語。「実行中」「処理中」より状況が伝わる）。
- `Application.StatusBar = False` で Excel の既定表示（「準備完了」）へ返す。**空文字を代入しない**（空のバーが残る）。

#### (2) 事前描画オーバーレイ（呼ぶ前に描き切る大きなカード）

呼出の**前に**、画面の中央へ大きな図形カードを1枚描き切る。呼出が返ったら消してトーストを出す。

```
┌────────────────────────────────────────┐
│  いま作っています。                                │
│                                                    │
│  ② リスクの洗い出し                                │
│  開始 14:03 ／ 最大 20分                           │
│                                                    │
│  ○ ● ○ ○   （4段のうち2段目）                     │
│                                                    │
│  画面が白くなっても、止まっていません。            │
│  そのままお待ちください。                          │
└────────────────────────────────────────┘
```

実装規約（順序が正・1つでも入れ替えない）:

1. 既存の `nv_wait*` の図形を全て削除する（名前を配列へ集めてから削除。§8.6 禁忌3）。
2. `ActiveWindow.VisibleRange` から中央を求めてカードを置く（列幅・行高・DPIを仮定しない。`modUIToast` と同じ作法）。**大きさは幅420pt・高さは文字量から実測**。
3. 段の進捗ドットは**セルではなく図形の中の文字**で `○ ● ○ ○` と書く（4段のうち何段目か）。**アニメーションさせない**（呼出中は動かせない）。
4. **`Application.ScreenUpdating = True` を明示してから `DoEvents` を1回**入れ、**描画が画面に出たことを確定させてから**リボンを呼ぶ。ここを飛ばすと、描いたつもりのカードが1度も表示されないまま固まる。
5. 呼出が返ったら（成功・失敗のどちらでも）カードを削除し、トーストを出す。**削除は `On Error Resume Next` で包む**（カードが消せないことで業務を止めない）。
6. 一括実行では**段が変わるたびに 1〜4 を繰り返す**（段の名前とドットを書き換えて描き直す）。Step間には必ず `DoEvents` を挟む（E-50c）。

- **カードはクリックできない**（`OnAction` を付けない）。押しても何も起きないボタンを作らない（原則①）。
- **進捗4行（`hm_progress_*`）はこれまでどおり残す**（§3.1.3）。カードは待っているあいだの視認性のため、進捗4行は**あとから読み返すため**にある。両者の文は同一にする。
- カードの下端に灰色の小さな1行を常設する（逐語）: 「この画面は20分ほど固まったように見えることがあります。閉じずにお待ちください。」

#### (3) ワーカー方式（実験枠・第1弾で実機実験する）

**第2のExcelインスタンス**（`CreateObject("Excel.Application")`・非表示）に呼出を実行させ、**親のインスタンスは `Application.OnTime` で進捗バーの図形を動かしながら結果セルをポーリングする**。成功すれば (2) のカードが**本物の動く進捗バー**になる。

- **前提（どれか1つでも崩れたら不採用）**: ①社内リボン（`.xlam`）が第2インスタンスにも自動ロードされること ②`CreateObject` によるCOM生成がEDRに止められないこと ③第2インスタンスの終了が確実にできること（ゾンビプロセスを残さない）。
- **望みがある理由**: 姉妹製品は管理端末で `Shell` による外部プログラムの実行に成功している。COMの生成が一律に禁止されているわけではない可能性がある。
- **実験の手順と判定基準は §8.7**。**実験が終わるまで、本方式を前提にした設計を他の節へ書かない**（(1)(2) だけで成立する設計にしておく）。
- **採用する場合でも `Application.OnTime` の常駐は「実行中だけ」**とし、終了時に必ず予約を取り消す（§7.2d の「常駐タイマーはトーストの自動消去1本だけ」に、**実行中に限った2本目**として例外を1つ足すことになる。例外を足すこと自体が §7.2(d) の改訂であり、実験が成功したときに明記して改訂する）。

#### (4) 3段構えに共通する規約

- `modUIProgress.SetStage` が**リボン呼出の前に**進捗4行を書き切る（いま動いている段／始めた時刻／最大の待ち時間／「画面が白くなっても処理は続いています」）。**(1)(2) の書き込みもこの中で行う**（呼出前の1箇所に集約し、書き忘れの経路を作らない）。
- **押した直後のトースト**は進捗の書き込みと同時に出す（「下書きを作りはじめました。10〜20分かかります。画面が白くなっても動いていますので、そのままお待ちください。」）。
- **段の名前を平易語にする**: 「Step2 リスク仮説を生成中」→「② リスクの洗い出しを作っています」。ステータスバー・カード・進捗4行・トーストの4箇所で**同じ段名を使う**（4箇所で違う呼び方をしない）。
- **`Application.Interactive = False` を使わない**（キーボード入力を奪ったまま固まると、利用者はExcelを強制終了するしかなくなる）。

### 4.3 生ダイアログを出さない

- `MsgBox` / `InputBox` を**案内の目的で使わない**。案内はトーストと `hm_warning` に一元化する。
- **例外は「押すと消えるもの」の確認2種だけ**（原則⑤のため、消える前に必ず止める）:
  1. 下流Stepの無効化を伴う再実行（16章 E-10）
  2. ヒアリングシートの上書き（手書きの回答が消える）
  加えて第2ラウンド開始の確認を残す。**これら3つの `vbYesNo` はダイアログの題名を日本語にし、本文も §4.1 の2文型で書く**。
- VBAの実行時エラーダイアログに到達させない: `modBoot.Boot` の各手順を個別のエラーハンドラで包む（B21）／全ての図形の `OnAction` 先の公開Subは冒頭に `On Error GoTo` を持つ／`ExitUiLock` で `ScreenUpdating = True` を必ず戻す（E-50d）。
- 「Excellent メッセージ E284」のような**社内の別アドインのダイアログ**は本製品と無関係である。区別できるように、**本製品が出すダイアログの題名は「リスク提案ナビ」で始める**（利用者が「これはこのアプリか」を題名で判別できる）。

### 4.4 失敗したら err_log の最後の行

- 全ての失敗経路は `err_log` へ痕跡を残す（工学原則）。**利用者に見せる文は §4.1 の2文のまま**で、コードは書かない。
- 直らないときの最終案内は**この1文に統一する**（画面・使い方タブ⑤・docs/24/25/26 で同一文）:
  > 「err_log タブのいちばん下の行をコピーして、開発担当へ送ってください。」
- そのために `err_log` / `run_log` / `usage_log` は**使い方タブ⑤の[記録を見る]で可視になる**（v3.1。裁定書17 裁定A H4 の「利用者が自分で送れる」要請は満たしたまま、既定の可視シートは2枚に保つ。13章§2.9の可視性同期・`tools/sheet_check.py` 緑）。可視になったシートには §1.1 の1行目の説明文と `[ナビへ戻る]` を書く。

### 6.2 状態遷移（旧§4。内容は維持）

#### 案件（`案件一覧.status`）

`draft → s1_done → s2_done → s3_done → s4_done → exported → feedback_done`、任意時点から `error`。

- `error` からの復帰は **`failed_step` の再実行**が原則（完了済みStepの結果は保持する。10章NFR-R3）。`draft` へ戻すのはナビ区画②の貼付内容そのものを変更したときだけであり、`error` になっただけで自動的に `draft` へ落とさない。
- 起動時の `RepairStates` は `sN_json`（検証合格済みのみ）と `last_ok_step` の突合で status を再導出し、`failed_step` が非空の案件は `error` を維持する（16章 E-12）。
- ルール: Step N 再実行時は N+1 以降の結果・状態を必ず無効化（確認ダイアログつき。16章 E-10。§4.3 の例外1）。
- **後半2状態の結線**（v2.5・裁定書9 B16(b)）: `exported` は**リスクレポートHTMLの生成成功時**（`modUIHome.HomeExportHtml` の成功分岐）、`feedback_done` は**商談の記録の保存成功時**（`modUICase4.FeedbackSave` の成功分岐）に `modCaseStore.SetStatus` で立てる。
- **遷移検査の担い手**（同 B16(a)）: `SetStatus` は enum 検査のみを行い `CanTransition` を通さない（修復系が自由書込を要するため）。本図の整合は起動時の `RepairStates` が担い、`CanTransition` は遷移表の宣言＝層(a)から検査できる純核として置く（14章§6）。
- **v3の追加**: `status` は `hm_next_action` と `nv_step_no`（§3.1.1）の入力である。**状態を1つ増やすたびに §3.1.1 の優先順位表へ1行足すこと**（状態が増えたのに次の一手が出ない画面を作らない）。**STEPは6つのまま増やさない**（状態が増えても、利用者に見せる段は6つに写像する）。

#### 受信箱（`受信箱.status`）

`undiagnosed → diagnosed → (adopted | conditional_hold | rejected | merged)`。`conditional_hold` は `revive_tag` ＋見直し期日必須。年次棚卸しで再診断キューへ。

## 7. UI実装規約

v2.5.1 の規約を全て維持し、v3で追加した4件を末尾に足す。

### 7.1 維持する規約（v2.5.1 から不変）

- ボタンは**図形＋OnAction**。UI操作コードは ui 層のみ（R4）。**`Hyperlinks.Add` は使わない**。図形にハイパーリンクを付けると `OnAction` が働かなくなる（同じ図形に両方は載らない）。シート内の移動は `Application.Goto` を呼ぶ図形ボタンで行う。
- **本章ワイヤー中の記号（▶▲●等）は視覚的な意図表示であり、`.bas` ソースに絵文字リテラルを書いてはならない**（VBEはCP932保持のため `?` 化する）。ボタンキャプション等でアイコンが必要な場合は ui 層で `ChrW` 組立か代替テキストを使う（15章§0原則7と同旨）。**丸数字①〜⑳は CP932 に存在するのでリテラルで書いてよい**（既存のボタン・ツアーカードで実証済み）。
- 実行中: `modUIProgress.SetStage` は**リボン呼出の前に**4行を書き切る（E-50a）。一括実行はStep間で必ず `DoEvents` を挟む（E-50c）。
- `ui_lock` で多重実行と案件切替をブロックし、完了/失敗で必ず解除する。**`ui_lock` はシート・configへ永続化しない**（`modUIProgress` のモジュール変数。Excelプロセスの終了で自然消滅）。`llm_wait_sec + 120` 秒を超えた保持は失効として自動解除する（E-11）。解除は `ExitUiLock` に一元化し、`Application.ScreenUpdating` の `True` 復帰もここで必ず行う（E-50d）。
- enum列はデータの入力規則（リスト）。源泉はナレッジブック/19章レジストリから起動時にコピーした隠しレンジ（ナレッジ未接続でも開ける）。
- 日本語ラベル⇔enumの変換は `modUICase` の共通変換表（19章と一致必須）のみで行う。
- **シート保護（`Worksheet.Protect`）は使わない**（16章 E-51）。代わりに**入力対象外セルの `Locked = True` ＋ `ws.EnableSelection = xlUnlockedCells` ＋ 全アクション完了時の `ParkFocus`**で構成する。実行開始時にも `ParkFocus` を通してから処理に入る。**残余リスクの注記**（M8）: `Locked` / `EnableSelection` は**誤操作低減であり強制ではない**。`sN_case_id` 等の表示セルは `DrawStep` が描画のたびに毎回上書きする自己修復方式で成立させている。
- 長文セルは先頭2,000字表示＋全文は `case_data`（E-22）。
- **クロス案件汚染を構造で塞ぐ**（B1）: 下書き①〜④は読取専用の案件ID表示セル `sN_case_id` を持ち、`DrawStep` が描画のたびに書く。`SaveEditedStep` は冒頭で引数の caseId と表示 case_id を突き合わせ、不一致なら**1セルも保存せず**中止する。`RefreshHome` は `hm_case_id` の変更を検知したら必ず `DrawAllSteps`（または全ブロックの `ClearBlock`）を通す。
- **切り捨てたまま保存しない**（B6・m3）: ブロックの `reserve_rows` を超える配列要素は描画できない。超過が起きたら案内し、**切捨てフラグが立っている間は当該Stepの `sN_edited` 保存をブロックする**（err_log は E0604）。保存ブロックの実体はセル状態で持つ（切捨てが発生した描画では `DrawStep` が `sN_case_id` を書かず空のままにする）。
- **描画に失敗した画面から保存しない**（B15）: ナビの描画（`DrawNav`。第1弾までは `DrawCaseInput`）の成否をモジュール変数で保持し、失敗直後の保存をブロックする。
- **下書き行は成功してから消す**（B3）: 判断台帳の起票は `modJudgeStore.NewJudgement` を**先に**呼び、`judge_id` が非空のときだけ下書き行を `Delete` する。
- **二次照合の警告**（B14）: `ValidateEdited` の後段でナレッジ本体との突合を行い、不一致は知らせる（保存は止めない）。
- **起動シーケンスは1手順の失敗で止めない**（B21）: `modBoot.Boot` の各手順を個別のエラーハンドラで包む（12章§2.1）。
- 外部由来テキスト（貼付・LLM出力）をセルへ書くのは `SetCellSafe` 経由のみ。**文字数カウンタ等も数式を書かずVBAが値で書く**（数式は16章 E-46 の対象になるため画面側に作らない）。

### 7.2 v3で追加する規約

#### (a) 貼付エリアの結合規約（§3.3.2 の実装契約）

- **読み**: `ReadArea(areaName)` は予約範囲を上から走査し、最終の非空行までを取り、**行を `vbLf` で連結**して返す。行の中の値は `CStr(cell.Value)` そのまま（トリムしない。原文を変えない）。
- **書き**: `WriteArea(areaName, content)` は `Split(content, vbLf)` の各要素を上から1セルずつ `SetCellSafe` で書き、予約範囲の残りをクリアする。**予約行数を超える分は書かず、見張り行へマーカーを書いて overflow を立てる**。
- **`ReadArea` → `WriteArea` → `ReadArea` は完全可逆**（1字も変わらない）。これは層(a)の純関数テストで検査できる形に切り出す（`JoinLines` / `SplitLines` を core へ置く）。
- **`case_data` への保存経路は不変**: `ReadArea` の結果を、既存どおり `modUtil.SplitForCells(content, U3_CHUNK = 32,000)` にかけて `case_data` の複数行へ入れる。**`U3_CHUNK` の値も、`SplitForCells` の契約も変えない**。
- **旧 `ci_paste_*` からの読み出し（`JoinField` の区切りなし連結）は当面残す**（§8.3 移行）。`JoinField` と `ReadArea` は**別の関数**であり、`JoinField` の「区切りなし連結」規約（M3）を `vbLf` へ変えてはならない（機械切断との可逆性が壊れる）。
- **1セル32,000字超の検出**は `ReadArea` の中で行い、欄名つきで呼出側へ返す（§3.3.4）。

#### (b) トーストの規約（`modUIToast`・接頭辞 `ts_`）

- 図形名は全て `ts_` 接頭辞。**描く前に既存の `ts_*` を全削除**する（孤児防止。名前を配列へ集めてから削除する）。
- **自ブックがアクティブなときだけ描く**（他の業務Excelを見ている間にShapeを生成して他人のブックを汚さない）。
- 位置は `ActiveWindow.VisibleRange` から中央上に寄せる（列幅・行高・DPIを仮定しない）。高さは文字量から実測して合わせる。
- 消去は `Application.OnTime` の予約。**予約時刻を必ず変数に保持し、Cancel は同時刻指定で行う**（Excel仕様）。ブックを閉じるときは予約を全て取り消す。
- **全公開入口の最上部に `On Error Resume Next`**（サーキットブレーカー）。トーストの失敗は「トーストが出ない」に留め、保存・実行へ絶対に波及させない。
- `modUIToast` は **ui層の他モジュールから一方向にだけ呼ばれる**（`modUIToast` からは業務モジュールを呼ばない。R1循環禁止）。

#### (c) 上級区画の feature flag

- config キー `ui_advanced`（既定 `FALSE`）。`FALSE` のとき、**上級側の図形を生成しない**（隠すのではなく作らない）。
- 上級側の公開Subは flag が `FALSE` でも**呼ばれれば動く**（マクロを直接呼べる人の保険を残す）。flag は導線の有無だけを制御する。
- **v3.1**: flag を切り替える口は**画面に置かない**（`config` を管理者が直接書く）。ナビに「開くと何かが増えるボタン」を置かないため（§3.7）。

#### (d) OnTime タイマーの衛生（**トーストの自動消去のみ**）

**本製品が持つ常駐タイマーはトーストの自動消去1本だけである**（裁定書18: 字数の3秒ポーリングは不採用）。**画面の状態を定期的に見に行くタイマーを新設してはならない**。

**唯一の例外候補**（v3.1）: §4.2(3) のワーカー方式を実験して採用したときに限り、**実行中だけ動く2本目**（進捗バーの更新と結果セルのポーリング）を認める。**実験が成功して採用が決まった時点で本節を改訂すること**（黙って2本目を足さない）。実行が終わったら必ず予約を取り消す。

- 予約は**必ず予約時刻を変数に保持**し、Cancel は同時刻指定で行う（Excel仕様）。予約は常に1本（表示のたびに前の予約を取り消してから張り直す）。
- 自動消去の手続きは、**対象の図形が無ければ何もしないで戻る**（ブックを閉じたあとに予約が発火しても、Excelが本ブックを開き直す経路を作らない）。
- タイマーの本体は `On Error Resume Next` で包む。
- **タイマーはセルを書かない**（書くのは図形の削除だけ）。利用者が編集中のセルを奪う経路を作らない。

#### (e) クリップボードからの取り出し（[ここに貼る]）

- 経路は既存の `modUICase4.CopyResearchRow` と**同系**（`DataObject` の遅延バインド）。**事前参照設定を足さない**（32bit端末・参照設定なしで動くことが生命線）。
- **取り出すのはテキストだけ**。`Worksheet.Paste` / `PasteSpecial` を使わない（書式・結合セル・画像がシートへ入る）。
- 取り出しの全体を `On Error GoTo` で包み、失敗したら**枠に一切触らずに**失敗の2文を出す（§3.3.4）。**読めなかったときに既存の中身を消してはならない**（原則⑤）。
- 書き込みは `SetCellSafe` 経由（16章 E-46）。書く前に予約範囲と見張り行をクリアする。


## 8. W6実装への申し送り

### 8.1 最重要の評価: 既存の名前付きレンジをナビシートへ付け替える案

**案**: `HOME` / `案件入力` を廃止してナビ1枚にするにあたり、**既存の `hm_*` / `ci_*` の名前付きレンジを1つも改名せず、参照先セルだけをナビシートへ付け替える**。VBA側は `U3_SHEET` / `U4_CASEIN` の定数値と、シート名リテラルを使っている数箇所を差し替えるだけにする。

#### (a) 実測（grep による直接参照の数）

**シート名に依存する箇所は、本体で合計12箇所（うち定数定義5・実使用7）、テストで1箇所しかない。**

#### (b) なぜ「付け替え」が成立するのか（構造的な理由）

`modUISheet.NamedCell` は次の1行で解決している（`src/ui/modUISheet.bas:76`）:

```
Set NamedCell = ThisWorkbook.Names(rangeName).RefersToRange.Cells(1, 1)
```

**`ThisWorkbook.Names` はブック・スコープ**である。名前がどのシートのセルを指していようと、この呼び方は変わらない。したがって:

- `ReadNamed` / `WriteNamed` / `MarkNamed` / `ClearNamed` を通す**すべての読み書きは、シート名を1文字も知らない**。
- `modUICase3` の名前付きレンジ経由の呼び出しは**36箇所**あるが、**そのすべてが無改造で動く**（`modUICase.bas` 1／`modUICase2.bas` 8／`modUICase3.bas` 36／`modUICase4.bas` 8／`modUIHome.bas` 23／`modUIInbox.bas` 1／`modUIProgress.bas` 6／`modUISparring.bas` 7／`modUIToast.bas` 1 の計91箇所）。
- **`ws.Range("ci_...")` のようなシート修飾つきの直接参照は、本体に1箇所も無い**（唯一の直接 `Names(...)` は `modBoot.bas:505` の `ThisWorkbook.Names("hm_warning")` で、これもブック・スコープである）。
- `RowOfNamed`（`modUICase3.bas:116` / `modUIHome.bas:203`）も `NamedCell` 経由で行番号を取る。**行番号はセルから実測する**ので、レンジがナビシートの別の行へ移っても正しく動く。

**結論: 名前付きレンジの付け替えは、ビルド側（`build/sheets_main.json`）だけで完結する。VBA側で必要なのは、上表12箇所のうち「シートを引く」5箇所の値の差し替えだけである。**

#### (c) `modUICase3`（残153字）を触らずに済むか

**済まない。ただし字数は増えない。** 必要な変更は次の3点で、**いずれも文字数が減るか、ほぼ同じである**:

| 変更 | 前 | 後 | 増減 |
|---|---|---|---|
| `modUICase3.bas:28` | `Private Const U3_SHEET As String = "案件入力"` | `Private Const U3_SHEET As String = "ナビ"` | **−2字** |
| `modUICase3.bas:462`・`470` | `modUISheet.ShowSheet "HOME"` | `modUISheet.ShowSheet U3_SHEET` ※ナビへ戻るだけなので同一シート。**行ごと削除できる**（すでにナビにいる） | **−58字**（2行削除） |
| `btn_ci_save` のキャプション（`EnsureCaseButtons` 内、`modUICase3.bas:105` 付近） | `"保存して戻る"` | `"貼ったものを保存する"` | **＋8字** |
| `btn_ci_count`（[字数を数える]）の生成2行 | ― | **削除**（v3.0 で撤去済みの機能） | **−120字ほど** |

**差引きで `modUICase3` は約170字減る**（残153字 → 約320字）。よって **Z-5 分割を待たずに、シート統合そのものは着手できる**。

**ただし貼付エリアの実装（`ReadArea` / `WriteArea` / `PasteIntoArea` / 現場メモの分解）は `modUICase3` に置けない**。これらは v3.0 の申し送りどおり**新設 `modUICase6` に置く**（`modUICase3` の `PasteTable` / `SplitPaste` / `DrawPasteField` / `JoinField` の呼び出し口を `modUICase6` の関数へ差し替える。差し替えは1行の置換なので字数はほぼ変わらない）。

**Z-5（`modUICase3` 分割）が先か**: **先ではない**。第1弾（ナビ新設＋既存ハンドラ結線＋レポート体裁）は `modUICase3` を上表の4点しか触らないため、**Z-5 を後ろへ回せる**。Z-5 が必須になるのは第2弾（貼付エリアの本実装）で `DrawCaseInput` を6欄の描画へ書き換えるときであり、**そのときは分割が前提**である。

**`modUIHome` は先に分割が要る（Z-13）**。実測で **29,002字・残998字**（v3.0 記載の27,632字から1,370字増えている。W5.2 の作業による）。ナビの描画（コーチ帯・4区画・黄色い枠）を足す余地が無い。**`modUIHome` の HOME描画部分を新設 `modUINavDraw` へ切り出してから着手する**。

| 第1弾に入れる | 理由 |

## 9. 代案・懸念（設計班から司令塔へ）

### 9-1. ボタンから番号（①〜⑤）を外し、区画が番号を持つことにしたこと（v3.1で変更）

**裁定書18 で採用した「HOMEのボタンを①〜⑤へ振り直す」は、v3.1 で置き換わった**。ボタンのキャプションから番号を外し、**番号は区画の見出しが持つ**（[③ まとめて作る] → 「③ 作る」区画の中の[まとめて作る]）。

- **理由**: 1画面に統合すると、番号つきのボタンが縦に5本並ぶことになる。**番号は「押す順」ではなく「画面のどこか」を指したほうが強い**（利用者は「③のところ」と口で言える）。加えて①が「調べる指示文を出す」というボタンでなくなった（文がその場にあるため）ので、番号のふり直しがもう一度必要になった。**2度目の番号変更を避けるには、ボタンから番号を外すのが最も安い**。
- **懸念**: 利用者は W5.2 で①〜⑤の番号を一度見ている。**3週間ほどで「番号つきボタン → 番号なしボタン＋番号つき区画」の変更を経験する**。トーストと帯の文はすべて「③の[まとめて作る]」の形で書き、**番号と場所が一体であることを言葉で補う**。
- **確認事項へ**（§10 #1）。

### 9-2. シート名の変更を第3弾へ後置したこと（v3.0 から継続）

- **理由**: シート名は 13章・19章・build・tools・層(b)テスト・docs 4本を横断する**最も広い影響**を持つのに、利用者に効く度合いは第1弾（1画面になる）・第2弾（貼るのが楽になる）より小さい。
- **懸念**: 第1弾・第2弾のあいだ、下書きのタブは「S1」「S2」のままである。ただし **v3.1 では下書きタブが既定で非表示になった**ため、利用者が「S1」を見る場面そのものが減る（[下書きを見る]を押したときだけ）。**v3.0 のときより実害は小さい**。

### 9-3. 字数の自動表示を常駐タイマーで行わないこと（裁定書18で決着・不採用）

**裁定**: `Application.OnTime` による3秒ポーリングは**不採用**。代わりに各貼付欄の見出し右へ **[ここに貼る]**（6本）を置き、押した時点で「クリップボードのテキストを行に展開して枠へ書く／はみ出しをその場で検知／字数をその場で更新」を一度に行う（§3.3.3）。

- **不採用の理由**: ①開いている間ずっとタイマーが回る（常駐は事故の温床）。②セル編集モード中は Excel が OnTime を保留するため、貼った直後の反映がどのみち遅れる。③強制終了で予約が残ると次回起動時に存在しない手続きを呼ぼうとする。
- **残る懸念**: クリップボードの遅延バインド取り出しは会社の管理端末（EDR）でブロックされうる。**失敗しても枠に一切触らず**、失敗の2文（§3.3.4）を出して Ctrl+V 直貼りへ誘導する設計にしてあるため、ブロックされても機能は死なない（字数の即時性だけを失う）。**実機での最優先の確認項目**である。
- **v3.1 での追加懸念**: §4.2(3) のワーカー方式を採用すると、**実行中に限った2本目の常駐タイマー**ができる。§7.2(d) の「常駐は1本だけ」は、そのとき明示的に改訂すること（黙って2本目を足さない）。

### 9-4. 予約行の固定（合計2,800行）と、Ctrl+V 直貼りのときだけ検知が遅れること

- **[ここに貼る]で貼るぶんには、はみ出しはその場で検知できる**。残る穴は **Ctrl+V 直貼り**である。シート保護を使わない方針（E-51）のため `Locked` は物理的な障壁にならず、直貼りは境界行を越えて次の欄へ流れ込みうる。検知は見張り行の走査＝**保存時**まで遅れる。
- **緩和**: ①予約行を想定の2倍以上に取った。②境界行を灰色地で明示した。③[ここに貼る]がその場で見張り行と行数を見る。④見出し下の常設案内文で[ここに貼る]へ誘導する。
- **v3.1 で悪化した点**: 欄が9つから6つに減ったため、**1つの欄がより長い文章を受ける**（とくに「調べた結果」は DR 3本ぶん）。**予約行はDR1本 3,000〜8,000字の想定での仮置き**であり、実物を測るまで確定できない（§10 #5）。
- **代案**: 6欄を**縦ではなく横（6列）に並べる**と、はみ出しは構造的に起きない（列が違えば衝突しない）。ただし横スクロールの必要な帳票は、想定利用者にとって縦スクロールより難しい。本章は縦を採った。**実機で「はみ出しが頻発する」なら横並びへの転換を再検討すべき**である。

### 9-5. 「調査の深さ」を「調べた結果」の有無だけで決めること

- §5 #1 は単純規則である。**「調べた結果」が空でもHP・有報を大量に貼った案件は `t1_quick` 扱いになり、上限が 40,000字のまま**になる（超過分は E-03 で打切られる）。
- **代案**: 合計字数が `max_context_chars` を超えたら自動で `t2_full` へ上げる。ただし「深さ」の意味が2つ（材料の量／調査の手厚さ）に割れる。
- **推奨**: 本章の規則で第2弾を出し、**打切りが実機で起きるかを `run_log` で観測してから**決める。

### 9-6. 「協業提案書（alliance）」を Phase 1.5 まで隠すこと（採用済み・裁定書18）

- §5 #3 のとおり `proposal` 固定とし、画面の入力口を Phase 1.5 まで隠す。**データ列と enum は消さない**（消すのは画面の入力口だけ）。**この線引きを実装で守ること**（列ごと消すと復活が高くつく）。

### 9-7. トーストと `hm_warning` の二重表示

- §4.1 は「警告は必ずトーストと `hm_warning` の両方へ出す」と定めた。**実装規則**: トーストは**押した直後の1回だけ**、`hm_warning` は**次の操作まで残る**。両者の文は同一にする。`hm_warning` を空へ戻すのは、次の操作の冒頭（既存の作法）だけ。
- **v3.1 で緩和された点**: 1画面になったため、**トーストが消えても `hm_warning`（区画④の「お知らせ」）が同じ画面の中にある**。v3.0 では別のタブにあった。

### 9-8. 現場メモ欄の「見出しで切り分ける」規約（v3.1で新規）

- **懸念**: 利用者が見出しを消したり、見出しの下ではなく上に書いたりしうる。そのとき `input_memo` と `input_field_notes` の振り分けが設計どおりにならない。
- **緩和**: (1) 見出しが1つも見つからなければ全文を `input_memo` へ入れる（壊れない）。(2) 判定は行頭からの完全一致に限る（部分一致で誤爆させない）。(3) 分解と再結合は純関数にして層(a)でテストする（§8.3）。
- **代案A（より単純）**: 見出しで切らず、**現場メモ欄の全文をそのまま `input_memo` へ入れ、`input_field_notes` も空にする**。実装は最小だが、**S1の `field_insights`（現場メモの原文をタグ付きで下流へパススルーする仕組み）が働かなくなる**。出力見本の「現場メモが提案に効いている」という価値の実演（`docs/design/出力見本` の企業理解と提案ストーリー）が弱まるため、本章は採らなかった。
- **代案B（より安全）**: 見出しごとに**別々の小さな貼付エリア**を置く（＝v3.0 の9欄へ戻る）。欄が増えるので採らなかった。
- **司令塔への確認**: 代案Aで足りるかどうかは、**`field_insights` を実際どれだけ使っているか**による。15章の担当と突き合わせて決めたい。

### 9-9. 見本の「攻めの保険活用（SEC-17）」に対応するJSONが無いこと（v3.1で新規）

- `docs/design/出力見本` の 07節（A〜Hの8アイデア）は、**現在の S1〜S3 スキーマのどこからも作れない**。「保険を本業拡大の装置に変える」という発想は S3 の `stories[]` とは目的が違う（stories は目の前のリスクへの打ち手、07節は事業機会）。
- **選択肢**: (a) 15章の S3 スキーマへ `growth_ideas[]` を足す（LLMの出力が1本増える＝プロンプトと検証の改訂が要る）。(b) S3 の `stories[]` のうち `proposal_kind` が新種目のものを流用して描く（**中身が違うものを同じ枠に入れる**ので誤解を生む）。(c) **Phase 1.5 まで描かない**。
- **推奨**: **(c)** で第1弾を出す。18章の登録表には `SEC-17` を予約だけして「Phase 1.5」と書き、描かない（§8.4 の改訂方針2）。**空のセクションを出さない**という現行規約に従う。
- **懸念**: 利用者は見本の07節を見ている。**「見本にあった節が実物に無い」ことを、先に伝えておく必要がある**（§10 #7）。

### 9-10. 第1弾の中間状態（区画②が旧9欄のまま）を利用者に見せること（v3.1で新規）

- §8.1(d) のとおり、第1弾では区画②に**旧 `ci_paste_*` の9欄**をそのまま置く。1画面にはなるが、貼る欄は6つに減っていない。
- **懸念**: 利用者は「タブは減ったが、貼る欄は9つのまま」という**中途半端な状態**を数週間見ることになる。実機第3報の不満（欄が多い）が一部だけ解消される。
- **代案**: 第1弾と第2弾をまとめて1回で出す。ただし `modUICase3` の Z-5 分割と貼付エリアの本実装が入るため、**出るのが数週間遅れる**。
- **推奨**: **分けて出す**。「タブが3枚→1枚」は実機の不満の中心であり、**先に効かせる価値が大きい**。第1弾を渡すときに「貼る欄を6つにまとめるのは次回です」と**先に告げる**こと（黙って中間状態を渡さない）。

### 9-11. コーチ帯を画面の上に置いたこと（モックは下）（v3.1で新規）

- モックのコーチ帯は**画面の下**に貼り付いている（`position:sticky; bottom`）。Excelには下に貼り付く帯が無いため、**上に固定した**（§8.5 #1）。
- **懸念**: モックを見た利用者が「下にあったものが上にある」と感じる。**位置は変わるが役割は同じ**であることを、第1弾を渡すときに1文で伝える。
- **代案**: 図形をウィンドウの下端へ毎回描き直す（`ActiveWindow.VisibleRange` の下端に合わせる）。**スクロールのたびに描き直しが要る＝スクロールを検知するタイマーが要る**ため、§7.2(d) に違反する。採らない。
