# 18. v1.1 差分仕様（構想v2への追随）

10〜17章のv1.0仕様に対する追加・変更。矛盾時は本書が優先。基盤（LLM3経路・JSON防衛線・PPT生成・ナレッジ注入方式・コーディング規約）は**無変更**。

## D-1. 更新診断プレイの追加（最優先の追加機能）

- 案件入力シートに追加: `現契約サマリ貼付欄`（種目・限度額・主要特約・保険料。社内帳票/Excelからの貼付前提、書式自由）、`前回更新メモ`（任意）
- 案件種別 `case_type` enum: `new`（新規）/ `renewal`（更新）を案件一覧に追加。renewal時のStep2/3は専用プロンプト（S2R/S3R）に切替:
  - S2R: リスク仮説に加えて**付保ギャップ分析**（現契約とリスクの突合。無保険・過小・重複の3分類）を出力
  - S3R: 提案を `upsell`（既存種目の拡張）/ `cross_sell`（未付保種目）/ `scheme`（型適用）にタグ分けして3本
- スキーマは S2/S3 を拡張（gaps[], proposal_kind を追加。strict準拠は維持）

## D-2. 案件コンテキストの構造化

案件一覧に選択式カラムを追加（プロンプトにも注入し、run_log分析の層別軸になる）:
`channel`(ホール/リテール) / `kanji`(幹事/非幹事/共保) / `bid`(BID有無) / `reinsurance`(再保/キャプティブ関与) / `other_insurers`(他社付保状況メモ)

## D-3. フィードバックの事実化（13章 §2.5 を置換）

「刺さった/刺さらなかった」の主観enumを廃止し、事実列に変更:
`event`(次アポ/見積依頼/成約/失注/継続/事故発生) / `customer_quote`(顧客の実際の発言・そのまま) / `terms_summary`(成約条件) / `loss_note`(その後のロス)。
解釈列（なぜ刺さったか）は**設けない**。四半期のAI横断分析（型生成プレイ）が仮説を出し、商品部が裁定する。

## D-4. 受信箱＋プリフライト診断（docs/05 §2 の実装仕様）

- 新シート `受信箱`: `idea_id / 起案者G / テーマ / 本文 / 出所`(商品部投稿/営業の声/情報ウォッチ) `/ 診断JSON / 予測drop_type / 状態`(未診断/診断済/採択/条件付き保留/却下/統合)
- 新プレイ「プリフライト」: 1コールで ①保険原理5問判定 ②生存文法(a)〜(d)適合 ③カタログ・型・研究中テーマとの重複照合 ④予測棄却類型と3手（経路/給付/主体）による回避案 を返す（スキーマ新設: Schema-PF）
- 統制語彙: `drop_type` enum = T1〜T10, T0（docs/05 §1）。`化ける条件`タグ enum = tech/regulation/partner/data/market ＋ 見直し期日

## D-5. 案件判断台帳（Phase 2への仕込み。今から記録）

新シート `judgement_log`（UW判断の事実記録。1案件5分・選択式中心）:
`case_ref / 種目 / 状況要約 / 選んだ対応`(増率/クローズ/縮小特約/条件維持/ロス改善伴走) `/ 適用係数・安全率メモ / 判断の決め手(自由記述1行) / 結果`(成約/失注) `/ 事後ロス`。
※ツール外の案件も記録可（台帳が主、ツールは従）。BID・高ロスプレイはこの台帳が100件を超えた時点で設計着手。

## D-6. 情報ウォッチプレイ（構想v2 §5）

- ナレッジブックに新シート `情報ウォッチ`: `watch_id / 日付 / 出所`(自社PR/グループ/他社/法改正) `/ 要約 / 仕分け`(新アセット/型実例/適用先候補/判断基準変化) `/ 反映先ID`
- 収集は3経路（外部検索可能なAIを前提にしない）:
  1. **ディープリサーチ社内アプリの月次バッチ利用（主経路）**: 固定の「月次ウォッチプロンプト」（過去1ヶ月の自社・グループ・主要他社PR、保険×サービス新スキーム、関連法改正の列挙・要約）を投げて放置→結果を受信箱へ貼付。遅さ・コード実行不可・顧客情報不可の制約はバッチ調査用途では無効（公開情報のみ・月1回・対話不要）
  2. **巡回リスト＋全員投函**: ナレッジブックに巡回先URL一覧を保持し月次当番が15分でコピペ。受信箱への随時投函（URL＋一言）も可＝分散クロール
  3. （要検証）VBAによる巡回リストの半自動取得: 社内プロキシが外部GETを通すか要確認（OQ-5として16章に追加）。Phase 1では実施しない
- 本文貼付後はAIリボンで要約・仕分け（Schema-WT新設）→ 月次編集会で採択
- **他社実績の型化**: 他社リリース由来のスキームは型ライブラリに `状態=他社実績` として登録可。型生成プレイの掛け合わせ対象に含め、「他社が業種Xでやった座組を自社アセットで業種Yへ」の応用候補を機械的に探索する

## D-7. 型生成プレイ（生むエンジンの月次バッチ）

- 入力: 受信箱の未採択群＋案件ログ（事実）＋機構ライブラリ＋型ライブラリ
- 処理: 第3弾分析の掛け合わせ手順をプロンプト化——「機構 × 未解決リスク × 器（加入経路・被保険者の置き方）」の組合せ候補を生成し、生存文法4条件と判断基準でセルフ審査させてから提示
- 出力: 型候補（S/A/B格付・成立条件・最初に検証すべき仮説つき）→ 商品部が裁定 → 型ライブラリへ
- 実行者: 当面は開発者が月次で実行（中央処理）。1回あたり数〜十数コール
