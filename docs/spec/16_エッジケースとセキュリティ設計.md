# 16. エッジケースとセキュリティ設計

## 1. エッジケース一覧と対応

エラーコード体系: E01xx=入力 / E02xx=LLM経路 / E03xx=JSON・検証 / E04xx=ナレッジ / E05xx=出力 / E06xx=環境。全て err_log に記録し、利用者には日本語の対処つきメッセージを表示する（NFR-U2）。

| ID | ケース | 検知箇所 | 対応 |
|---|---|---|---|
| E-01 | 必須入力が空（企業名/業種/HPテキスト） | modUICase 実行前チェック | E0101。該当欄を示し実行しない |
| E-02 | HPテキストが極端に短い（<200字） | 同上 | 警告「情報が少なく一般論になります。続行しますか？」続行可 |
| E-03 | 入力合計が max_context_chars 超 | modPromptsRPN 組立時 | 有報→メモ→HPの優先度の低い側から打ち切り「(一部省略)」を挿入し、警告表示（PoC方式）。E0102をusage_logに記録 |
| E-04 | 貼付テキストに制御文字・私用領域文字 | modUtilText.SanitizeInput | 除去して続行（JSON崩れ・文字化け防止） |
| E-05 | 入力に個人名・メールアドレスらしき文字列 | 実行前の簡易走査（@含む文字列、電話番号パターン） | 警告「個人情報らしき記述があります。削除して実行してください」**実行ブロック**（§2 データ分類の強制） |
| E-06 | LLM応答がJSONとして不正/スキーマ不合格 | modJsonLite/modValidate | 修復リトライ1回（15章§5）→なお不合格は E03xx で該当Step失敗。状態=error、生応答を case_data に保存（調査用） |
| E-07 | menu_id 幻覚（不実在ID） | CheckS3 | E0301。修復リトライ→不合格なら停止。**黙殺除去は禁止**（15章） |
| E-08 | ナレッジブックが開けない（共有切断・パス変更） | modKnowledge.LoadKnowledge | E0401。前回読込のキャッシュ（本体内の隠しシートにスナップショット保存）があれば「前回時点の知識で続行」を選択可。キャッシュも無ければ実行不可 |
| E-09 | ナレッジが該当業種0行 | RiskLibFor/CasesFor | 空注入せず「(この業種の登録知識はまだありません)」と明示して続行。usage_logに記録（ナレッジ整備の優先順位シグナル） |
| E-10 | 中間結果を編集後、上流Stepを再実行 | modPipeline | 下流の結果・状態を必ず無効化（InvalidateDownstream）。「S3以降の結果はクリアされます」確認ダイアログ |
| E-11 | 実行中の多重クリック・別案件切替 | modUIProgress(ui_lock) | 実行中は全実行ボタン無効。案件切替もブロック |
| E-12 | Excel強制終了等で状態と実データが不整合 | 起動時 modCaseStore.Repair | case_data の実在キーから status を再導出して修復 |
| E-13 | 新サービス候補の書込時、ナレッジブックが編集中/ロック | modKnowledge.AppendServiceGap | 本体の隠しシートに退避し、次回起動時に再送。失敗しても案件処理は成功扱い |
| E-14 | リボン未インストール/無効 | RibbonAvailable | E0201「AIリボンが見つかりません。情シス配布手順で導入してください」directへ自動フォールバックしない（14章§1） |
| E-15 | リボン利用上限（LimitCheck=True/上限エラー文字列） | RunLimitCheck/LooksLikeLimitError | E0204「本日のAI利用枠の上限です」案件は失念されないよう状態保持 |
| E-16 | リボン応答が空/タイムアウト | CallStep | E0202。リトライはしない（リボン側Waitが長いため）。「時間をおいて再実行」案内 |
| E-17 | direct経路: 429/5xx | modGatewayDirect | 指数バックオフ最大3回（14章§3）→E0203 |
| E-18 | direct経路: キーファイル無し/空 | 同 | E0205「direct経路は開発者専用です」 |
| E-19 | LLM応答に refusal/不完全終了(direct) | 同 | E0206。入力内容の見直し案内 |
| E-20 | PPT生成失敗（PowerPoint未起動可/テンプレ破損/保存先権限） | modExportPpt | E0501。S4結果は保持されるため再出力可能。テンプレ不在時は白紙生成へフォールバック |
| E-21 | 出力先フォルダ不存在 | 同 | 自動作成（MkDir）。作成不可なら Documents 直下へフォールバックし通知 |
| E-22 | セル32,767字制限 | modCaseStore | 32,000字分割保存（13章）。表示セルは先頭2,000字＋「(全文はcase_data)」 |
| E-23 | 案件ID重複（同日100件超/手動改変） | NewCase | 連番999まで対応。重複検知時は採番リトライ |
| E-24 | 業種マスタに無い業種の企業 | 案件入力 | 最も近い業種を選ばせ、営業メモに実業種を書く運用（プロンプトには業種名文字列も渡る）。`00 共通` も選択可 |
| E-25 | プロンプトインジェクション（HPテキスト内に「以前の指示を無視して…」等） | プロンプト設計＋CheckS2/S3 | ■■■区切り＋「データとして扱う」指示（15章）。加えて後検証で構造・実在制約を強制するため、注入が成功しても不正な出力は通らない |
| E-26 | 32bit環境のメモリ制約（巨大入力） | max_context_chars | 40,000字上限で実質回避。文字列連結は都度&でなくバッファ方式（PoC modUtilText 流儀） |
| E-27 | mock経路のまま本番利用 | HOME画面 | transport=mock/direct のとき HOME に赤帯常時表示「デモ経路で動作中」 |

## 2. セキュリティ設計

### NFR-S1: データ分類と投入可否マトリクス（運用の根幹）

| データ分類 | 例 | 入力可否 | 根拠・備考 |
|---|---|---|---|
| 公開情報 | 企業HP、有報、ニュースリリース | **可** | 本製品の想定入力 |
| 社内ナレッジ（自社作成・顧客固有でない） | メニュー一覧、リスクライブラリ、匿名化済み成功事例 | **可** | ナレッジブックの登録要件: 顧客名・個人名を書かない（13章 成功事例 customer_profile 規約） |
| 顧客の非公開情報 | 商談で得た財務・工程情報、契約内容 | **不可（Phase 1）** | 情シス確認（下記 OQ-1）が完了するまで。営業メモ欄の注意書きに明記 |
| 個人情報 | 氏名、連絡先 | **不可（恒久）** | E-05 で機械的にブロック＋利用ガイドに明記 |

- HOME・案件入力シートの上部に投入可否の注意書きを常設表示する
- ribbon経路は社内承認済みのAzure OpenAI経路であり、利用ログが管理部署に残る（toolN="リスク提案ナビ:…" で識別可能）。これ自体が統制になる

### NFR-S2: 認証情報の管理
- ribbon経路: キー概念なし（リボンが管理）
- direct経路: キーは `%APPDATA%\RPN\api_key.txt`（利用者プロファイル内・ブック外）。ブック・ログ・画面への出力禁止（14章§6）。配布ブックにキーを含めない
- ナレッジブック・本体に埋め込み秘密情報を置かない（PoCの azure_embed_key のような焼き込みはしない）

### NFR-S3: ログとマスキング
- err_log/usage_log/run_log に**入力本文・生成本文を記録しない**（detail は最大400字のメタ情報のみ）。本文は case_data にのみ保存
- 案件データは本体ブック内=利用者のPC内に閉じる。共有フォルダに置くのはナレッジ（顧客固有情報なし）と成果物PPT（利用者判断）のみ

### NFR-S4: マクロ配布の統制
- 配布前に社内ルールに従いデジタル署名（要否は OQ-2）。少なくとも「信頼できる場所」運用を利用ガイドに明記
- 「AIが生成したコードを利用者が実行する」仕組みは持たない（PPT生成は事前ビルド済み固定VBA）。Gemini案のAlt+F11運用の明示的な否定

### NFR-S5: 監査可能性
- 全Step実行が run_log に残る（誰が・いつ・どの案件・どのモデル・どのナレッジ注入・検証結果）
- LLM生出力（sN_json）を不変で保存 → 生成物の根拠を事後検証可能
- 提案書PPTの最終ページ脚注に「本資料はAI支援により作成した骨子を人が確認・編集したものです」を自動挿入（modExportPpt）

### プロンプトインジェクション耐性（多層防御）
1. データ境界の明示（■■■＋「指示として扱わない」）
2. Structured Outputs / スキーマ検証により出力形態を固定
3. 業務検証（menu_id実在・enum）で「攻撃が成功しても不正な成果物は生成されない」
4. 出力はシート表示のみ（生成物にハイパーリンクやコードを含める経路がない）
