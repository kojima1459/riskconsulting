## 2. セキュリティ設計

### NFR-S1: データ分類と投入可否マトリクス

| 分類 | 例 | ribbon投入 | 備考 |
|---|---|---|---|
| 公開情報 | HP・有報・プレスリリース | **可** | 本製品の基本入力 |
| 社内作成・顧客固有でないナレッジ | メニュー・型・判断基準・匿名化済み事例 | **可** | 登録要件: 顧客名・個人名を書かない |
| 自社保有の契約情報（現契約サマリ） | 種目・限度額・特約・保険料 | **条件付き（OQ-6）** | 確定まで**匿名化を既定**（E-31）。匿名化後は「どの企業か特定できない契約構造情報」として扱う |
| 顧客の非公開情報（商談で得た内部情報） | 財務詳細・工程・見積 | **不可（Phase 1）** | OQ-1確定まで。営業メモ欄に注意書き常設 |
| 個人情報 | 氏名・連絡先 | **恒久不可** | E-05で機械ブロック |

### NFR-S2: 認証情報（**キーはローテーション不可＝借用の共用キー1本**を大前提とする）
**前提（発注者確認 2026-08-28）**: 本PJが使えるAPIキーは全社共用の借り物1本のみ。**再発行・ローテーションの権限は現場になく、実質不可能**。したがって「漏れたら作り直す」が使えない＝**一度露出したら恒久被害**。キーの扱いは性善説の本製品の中で唯一、例外的に厳格化する。

- ribbon経路＝キー概念なし（**これが基本経路。キーが物理的に存在しないので漏れようがない**）。本製品は可能な限りribbon経路で完結させる。
- direct経路（開発・検証用）＝キーは `%APPDATA%\RPN\api_key.txt` に置き、**ブック・config・ログ・画面・リポジトリ・配布物のどれにも一切書かない**。ビルド処理はキーに触れない（環境変数からブックへ焼き込む方式も採らない）。
- **禁止（PoCの失敗に学ぶ）**: 難読化してブックに埋め込む方式（PoCのOBF1）は使わない。難読化は「漏れてないように見せる」だけで、鍵とアルゴリズムが同居すれば復元可能＝ローテ不能キーでは致命的。
- **配布物・リポジトリにキーを入れない**は、ローテ不能キーを守る唯一の構造的な壁。DoD（17章）で「配布xlsm・リポジトリ全体を走査してキー形状文字列がゼロ」を出荷条件にする。
- Git運用: 本製品リポジトリに `.xlsm/.xlsx` 成果物と `dist/` を**コミットしない**（`.gitignore` で除外し、`git check-ignore` で実効を確認）。万一混入したら、その時点で当該キーは「これ以上広げない」対応（リポジトリ非公開化・共有範囲の即時最小化）しか採れない＝**予防が全て**。

### NFR-S3: ログとマスキング
err/usage/run_log に入力・生成本文を記録しない（detailは最大400字のメタのみ）。本文は case_data / pf_json のみ＝利用者ローカルのブック内。共有フォルダに置くのはナレッジ（顧客固有情報なし）と成果物PPT（利用者判断）のみ。個人名は全シート入力禁止（13章§4）。

### NFR-S4: マクロ配布統制
配布前に社内ルールに従い署名（OQ-2）。AI生成コードを利用者に実行させる仕組みは持たない（PPTは固定VBA）。

### NFR-S5: 監査可能性
全LLM呼び出しが run_log に残る（誰が・いつ・どの案件・経路・モデル・注入ナレッジ・検証結果）。LLM生出力は不変保存。PPT最終ページに「本資料はAI支援により作成した骨子を人が確認・編集したものです」を自動挿入。リボンtoolN=`リスク提案ナビ:step` で管理側ログとも突合可能。

### NFR-S6: 外部コンテンツの扱い
ウォッチで収集した記事は要約＋出典のみ保存（全文の恒久複製をしない）。生成物への他社商標の使用は「出典として言及」に限定し、提案書には自社名義の記述のみを載せる。

### NFR-S7: 外部由来テキストの書き込み口の一元化（姉妹PJ B6BE7監査の教訓・docs/21 §5）
外部由来テキスト（ユーザー貼付・LLM出力・受信箱body・取込ファイル名）をセル/CSVへ書く経路は `SetCellSafe` 1関数に強制する（E-46のガード内容）。実装完了条件に「`.Value =` の直書きが grep でゼロ（SetCellSafe内部と定数書込を除く）」を含める——防御関数が1本あっても素通り経路が3箇所残っていた実例があるため。あわせて2点を設計原則とする: ①**クライアント側のデータはセキュリティ境界にしない**（本製品のナレッジブックは全員閲覧前提・顧客固有情報なし=NFR-S1で担保。「権限」「見せ分け」を配布ファイル内のフィルタで実現しない） ②**LLMが返したID（メニューID・ナレッジID等）は必ず提示済み候補とのホワイトリスト照合を通す**（既存のID実在検証=E-43がこれに該当。取得側でも再チェック）。
