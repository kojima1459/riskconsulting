# 16. エッジケースとセキュリティ設計 v2.5

v2.5変更概要（裁定書9: W4.1 最終修正ウェーブ）: E-15 の警告文を実装の逐語（「本日のAI利用枠の上限です」）へ揃え、E-35/E-36 の `hm_warning` 表示経路を `modPipeline2.LastDeepOutcome()` 経由と明記、E-22（E0604）へブロック超過の切捨てと貼付欄の枠溢れの2件を追加して**警告のうえ保存をブロックする**規定を加え、E-24 に業種欄の入力規則（ナレッジ未接続時は手入力で続行）、E-08 に0行読込でスナップショットへ触れない規定、E-13 に書込0件で退避キューを消さない規定、E-41 に判定入力列 `judge_to` の規定、NFR-S7 設計原則(2) に二次照合の呼出点を追記した。

v2.4.2変更概要（W3.1裁定）: E-47(1) の `JsStringSafe` のエスケープ集合を「`</` → `<\/`」から「**すべての `<` → `\u003C`**」へ改訂した（18章§5.3(1) v1.1 と同時改訂）。旧集合では `<!--<script>`（`-->` を伴わない形）を含むLLM出力でHTMLトークナイザが script data double escaped 状態へ入り、生成HTMLが実ブラウザ上で白紙化する経路が残っていた。

v2.4.1変更概要（裁定書5: W1整合）: NFR-S7①のガード適用順を固定した（NULバイト除去 -> 32,000字切詰め -> 先頭式記号の `'` 前置。`Chr(0) & "=1"` の期待値は `'=1`、戻り値は最大32,001字）。純変換部は `modUtilText.SanitizeForCell`（14章§6）。

v2.4変更概要: 実装前監査72件の裁定を反映。§1の全表に code 列を追加して未採番行を採番し、E-03（入力打切り）・E-06/E-12（データ体制）・E-11（ui_lock）を全面改訂、E-04/E-05/E-22の範囲を拡張、E-35/E-36/E-47/E-48/E-49/E-50/E-51 を新設、NFR-S2の走査仕様とNFR-S7の3書き込み口を明文化した。（検証指摘の修正）E-05の走査対象にHTMLレポート出力と企業ドシエ書出を追加し企業ドシエ共有前の確認必須を規定、E-52（config読込失敗・E0608）を新設、CP932外文字（U+2014）を除去した。

エラーコード体系: E01xx=入力／E02xx=LLM経路／E03xx=JSON・検証／E04xx=ナレッジ／E05xx=出力／E06xx=環境・状態／E07xx=受信箱・ウォッチ。全て err_log 記録＋非エンジニア向け日本語メッセージ（対処つき）。
個別コードの正は §1 各表の `code` 列であり、19章§4のエラーコード表と一字一句一致させる（矛盾時は本章が正）。`code` 列が `(なし)` の行は、利用者への案内・run_log/usage_log 記録のみで err_log にコード付きの行を立てないケースである。

#### E-03 入力打切りの詳細規則（実装はこの順序どおりに行う）

1. **上限の選択**: 案件一覧の `dossier_tier` で決める。`t1_quick` → config `max_context_chars`（既定40,000字）。`t2_full` / `t3_sparring` → config `t2_max_context_chars`（既定100,000字）。判定単位は「1回のLLM呼び出しに載せる貼付テキストの合計字数」であり、ナレッジ注入分は別枠（下記5）で数える。**上限そのものの配分は 15章§0.7 が正**（貼付＝上限の7割／ナレッジ＝上限の3割。裁定書7 B-9）。本項の「別枠」は「貼付の合計字数にナレッジを混ぜて数えない」の意であって、貼付が上限の全量を使えるという意味ではない（両者を足すと上限の1.3倍になり破綻するため）。実装では `modPipeline.BudgetOf(limitChars, 7)` / `BudgetOf(limitChars, 3)` が唯一の配分点である。
2. **打切り対象と優先順**（先に切るものから順に。1つ切るごとに再計測し、上限を下回った時点で停止する）: **追加ドシエ（input_dossier）→ 前回更新メモ（input_prev_renewal）→ 有報リスク章（input_yuho）→ 営業メモ（input_memo）→ HPテキスト（input_hp）**。
3. **打切らない4欄**: **現契約サマリ（input_contract）・現場メモ（input_field_notes）・付保の見立て（input_coverage_note）・ヒアリング回答（input_hearing_answers）**。いずれも他で代替できない一次情報であり、FR-34（現場メモの原文パススルー）・FR-35（ヒアリング回答=第2ラウンドの主入力）が原文性を要件にしているため、機械的に削らない。
4. **この4欄だけで上限を超える場合**: 打切らず、実行**前**に E0102 を警告として出し（「入力が上限を超えています。現場メモ・ヒアリング回答は自動では削れません。要点を残して短くしてください」＋各欄の現在字数）、利用者に削減を求める。利用者が続行を選んだ場合のみ、4欄を後ろから順に切り「(一部省略)」を挿入する（この経路もE0102をusage_logへ記録）。
5. **ナレッジ側の切詰め**: 貼付テキストの打切りとは別に、注入ナレッジは 15章§0.7 の順（成功事例→型→メニュー→種目→リスクライブラリ）で行数を削る。切詰めが発生したら run_log の detail に `truncated:<欄名>` を列挙して記録する（黙って削らない）。
6. 切詰めた欄には必ず末尾に `（一部省略）` を挿入し、E0102 を usage_log へ記録する。記録するのは欄名と削減後字数のみで、本文は記録しない（NFR-S3）。

### NFR-S2: 認証情報（**キーはローテーション不可＝借用の共用キー1本**を大前提とする）
**前提（発注者確認 2026-08-28）**: 本PJが使えるAPIキーは全社共用の借り物1本のみ。**再発行・ローテーションの権限は現場になく、実質不可能**。したがって「漏れたら作り直す」が使えない＝**一度露出したら恒久被害**。キーの扱いは性善説の本製品の中で唯一、例外的に厳格化する。

- ribbon経路＝キー概念なし（**これが基本経路。キーが物理的に存在しないので漏れようがない**）。本製品は可能な限りribbon経路で完結させる。
- direct経路（開発・検証用）＝キーは `%APPDATA%\RPN\api_key.txt` に置き、**ブック・config・ログ・画面・リポジトリ・配布物のどれにも一切書かない**。ビルド処理はキーに触れない（環境変数からブックへ焼き込む方式も採らない）。
- **禁止（PoCの失敗に学ぶ）**: 難読化してブックに埋め込む方式（PoCのOBF1）は使わない。難読化は「漏れてないように見せる」だけで、鍵とアルゴリズムが同居すれば復元可能＝ローテ不能キーでは致命的。
- **配布物・リポジトリにキーを入れない**は、ローテ不能キーを守る唯一の構造的な壁。走査仕様は次の4項目を正とし、17章 T-46② はこれを参照して実装する（姉妹PJの実漏洩は「難読化blobが xlsm 内の sheet23.xml に埋まっていた」形であり、平文のキー形状文字列を素のgrepで探すだけでは原理的に検出できない）。
  1. **対象**: リポジトリの全trackedファイル ＋ ビルド成果物 `*.xlsm` / `*.xlsx` を `unzip -p` で**全パート展開したテキスト**（xlsx/xlsmはZIPであり、素のgrepではXMLパート内が見えないため展開が必須）。
  2. **検出パターン**: `sk-[A-Za-z0-9_-]{20,}` ／ 連続32文字以上の `[0-9a-f]` ／ 連続40文字以上のBase64様文字列 ／ 文字列リテラルに `OBF`・`難読`・`_KEY` を含む定数定義。
  3. **buildスクリプト検査**: `build/` 配下のスクリプトが `api_key.txt` または環境変数からキーを読む行が存在しないことを grep で確認する（「ビルド処理はキーに触れない」の機械的担保）。
  4. **検出時の出力**: ファイル名と行番号のみを出し、**キー値そのものは出力しない**（検問ログ自体が漏洩経路にならないようにする）。
- Git運用: 本製品リポジトリに `.xlsm/.xlsx` 成果物と `dist/` を**コミットしない**（`.gitignore` で除外し、`git check-ignore` で実効を確認）。万一混入したら、その時点で当該キーは「これ以上広げない」対応（リポジトリ非公開化・共有範囲の即時最小化）しか採れない＝**予防が全て**。

### NFR-S3: ログとマスキング
err/usage/run_log に入力・生成本文を記録しない（detailは最大400字のメタのみ）。本文は case_data / pf_json のみ＝利用者ローカルのブック内。共有フォルダに置くのはナレッジ（顧客固有情報なし）と成果物（Phase 1はHTMLリスクレポート、Phase 1.5以降はPPTも。いずれも利用者判断）のみ。個人名は全シート入力禁止（13章§4）。

**社内AIリボンの社内ログ（事実の明記。裁定書24 A-4）**: リボンちゃん ver.202606 の実ソース（`log.bas`）を読むと、リボン経由の呼び出しでは**プロンプト全文と回答（各先頭4,096字）が、実行者の氏名・役職・メールアドレスと共に社内のログサーバへHTTPで送られる**。**オプトアウトの手段は利用者側に無い**（`toolN` の末尾に `_ss` を付けるとログ本文がマスクされる隠し仕様が実ソースに存在するが、**本製品はこれを使わず、社内ログの抑止を一切行わない**＝会社の監査設計を迂回しうるため。裁定書24 A-4）。したがって「**リボンへ顧客の非公開情報を入れない**」という NFR-S1 のルールは、本製品の運用上の建前ではなく**前提条件**である。ここでいう非記録（NFR-S3 の本文非記録）は本製品が持つ err/usage/run_log の話であり、**リボン側の社内ログには本製品の関与なく本文が残る**。

### NFR-S4: マクロ配布統制

### NFR-S5: 監査可能性
全LLM呼び出しが run_log に残る（誰が・いつ・どの案件・経路・モデル・注入ナレッジ・検証結果）。LLM生出力は当該ラウンドの検証合格版を `sN_json` に、不合格版を `sN_json_failed` に保存する（E-06。完全な実行履歴はrun_log側で追う）。**HTMLリスクレポートの末尾**（Phase 1.5以降はPPT最終ページにも）に「本資料はAI支援により作成した骨子を人が確認・編集したものです」を自動挿入。リボンtoolN=`<config app_tool_prefix><step>`（既定 `リスク提案ナビ:step`）で管理側ログとも突合可能。

### NFR-S7: 外部由来テキストの書き込み口の一元化（姉妹PJ B6BE7監査の教訓・docs/21 §5）
外部由来テキスト（ユーザー貼付・LLM出力・受信箱body・取込ファイル名）が外へ出る口は**3つ**あり、そのすべてを専用関数に強制する。防御関数が1本あっても素通り経路が3箇所残っていた実例があるため、「口ごとに1関数」を機械検査で担保する。

| # | 書き込み口 | 強制する関数 | ガード内容 | 参照 |
|---|---|---|---|---|
| ① | **セル**（シートへの書込） | `modUtilText.SetCellSafe` | 先頭式記号（`=` `+` `-` `@`）の `'` 前置・NULバイト除去・32,000字切詰め。**適用順は下記に固定** | E-46 |
| ② | **CSV**（ログ・集計の書出） | `modUtilText.SetCellSafe` と同一ガードを通す | 同上（集計CSVを開いた管理者側のExcelで発火するため） | E-46 |
| ③ | **HTML/JS**（HTMLレポート生成） | `modUtilText.HtmlSafe`（HTML本文・属性値）／ `modUtilText.JsStringSafe`（JS文字列リテラル） | `& < > " '` のエンティティ化／`</`→`<\/`・U+2028・U+2029・制御文字のエスケープ。JSONは「1本のJS文字列リテラル＋`JSON.parse`」形式でのみ埋める | E-47 |

**①のガードの適用順（固定。純変換部 `modUtilText.SanitizeForCell` が担い、`SetCellSafe` はこれを通してからセルへ書く）**:

1. **NULバイト（`Chr(0)`）を除去する**。セルの値にNULが混ざるとExcelは以降の文字を黙って捨てることがあり、「保存はできたのに中身が切れている」という気付けない欠損になる
2. **32,000字で切り詰める**（サロゲートペアを割らない切詰めを使う）
3. **先頭が `=` `+` `-` `@` なら `'` を前置する**

順序の根拠: 3を最後に置くのは、切詰めで先頭文字が変わることはない一方、前置してから切ると `'` の分だけ本文が1字失われるため。したがって**戻り値は最大32,001字**（`'` を含む）となり、セルの物理上限32,767字を超えない。1を最初に置くのは、先頭のNULを残したまま3を判定すると `Chr(0) & "=1"` が「先頭は式記号でない」と誤判定され、NULを捨てるExcel側で `=1` が数式として復活するため。**`Chr(0) & "=1"` の期待値は `'=1`** である（この1ケースが順序の三点すべてを固定する）。

**実装完了条件（17章 T-46① の検問と同一の定義。両章で一致させる）**: 検査対象は `src/**/*.bas` から `modUtilText`（防御関数の定義本体）を除外したもの。検出パターンは `\.Value2?\s*=` ／ `\.Formula\w*\s*=` ／ `(Cells|Range|Offset)\([^)]*\)\s*=`（VBAで最頻の既定プロパティ代入 `ws.Cells(r,c) = s` を取りこぼさないため）。定数・ヘッダの書込は行末に `' SAFE:const` の注記を必須とし、**注記の無いヒットのみをFAIL**とする（除外が実装者の裁量ではなく差分レビュー可能な痕跡として残る）。③については「HTMLへ差し込む値が `HtmlSafe` / `JsStringSafe` を経由しない埋め込みが grep でゼロ」を同じ検問に含める。

あわせて2点を設計原則とする: ①**クライアント側のデータはセキュリティ境界にしない**（本製品のナレッジブックは全員閲覧前提・顧客固有情報なし=NFR-S1で担保。「権限」「見せ分け」を配布ファイル内のフィルタで実現しない） ②**LLMが返したID（メニューID・ナレッジID等）は必ず提示済み候補とのホワイトリスト照合を通す**（既存のID実在検証=E-43がこれに該当。取得側でも再チェック）。**二次照合の呼出点**（v2.5・裁定書9 B14）: 「取得側でも再チェック」の実体は `modKnowledge.MenuIdExists` / `LineIdExists` / `SchemeIdExists` / `CaseLibIdExists` / `PatternIdExists` の5本であり、`modUICase2.ValidateEdited` の後段でナレッジブック本体と突き合わせる。不一致は保存をブロックせず `hm_warning` へ出す（一次側の fail-closed はそのまま残す）。宣言だけして呼び出しが0件の状態は本原則を満たさない。
