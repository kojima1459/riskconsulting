# 04. シードナレッジ調達計画（PoC立ち上げに必要なデータの種類・量・粒度・集め方）

**前提**: プロダクトの最終形は「二方向のナレッジエンジン」（使うエンジン=型・カタログを全員の提案力に変換 / 生むエンジン=案件事実と会社の実績から新しい型を生成）。本書はその**初期装填（シード）に何がどれだけ要るか**の調達計画。

## 0. 先に結論

- **集めるのは「文書」ではなく「行」**。マニュアル・約款の全文は集めない（それはMyBookshelfの領分）
- シードの大半は**既にある**。投稿ボックス約1,900件、各Gのパンフ、インターリスク総研レポート、会社の実績（ヤモリ/WOTA/セレンディ/じゃぱん21/セーフタウン…）。無いのは「構造化された形」だけで、構造化はAIの得意技
- 開発者の正味作業は **AI併用で1～1.5週間**。各Gの負担は **ヒアリング60分＋レビュー30分の計1回**（9月の課題ヒアリングと抱き合わせで1回で済ませる）
- ゼロから人が書き起こす資産はほぼ無い。**人の役割は「書く」ではなく「AIの下書きを裁く」**

## 2. 「作れるのか・データ量は爆発しないか」への回答

### 作れる。理由は3つ
1. **ナレッジは行であり、注入は選択的**。LLMに渡すのは案件ごとに業種・文脈でフィルタした数十行だけ。ライブラリ全体が1万行になっても、1回の生成に使うのは常に一部
2. **会社は既にこのスケールをExcelで回している**。投稿ボックス1,900件がExcel 1ファイルで運用されている現実が証拠。型25件・カタログ150行は誤差
3. 基盤（リボン経由LLM・VBA・共有フォルダ）はNotebookLM PoCで実証済み

### Excelで破綻する境界も明示しておく
- 同時編集・権限管理・1万行超の検索性・全社展開の配布統制 → **Phase 3のIT基盤（Webアプリ/DB）の仕事**。ただしナレッジが最初から構造化された行なら、移行はコピーで済む。「Excelで始めてDBに引っ越す」は構造化されていない場合にだけ痛い

### 「日々分析・日々更新」はしない設計にする
君の懸念どおり、日々人手でキュレーションする運用は必ず死ぬ。投稿ボックスがうまく回りきらない一因も、1,900件を人手で仕分けする構造にある。だからこうする:

```
受信箱方式（人の作業を月1に固定）
  日々:   誰でも「受信箱」シートに放り込むだけ（アイデア・事例・記事URL・一言）
          案件の事実記録はツールが自動で貯める（人は選択式5分）
  月1:    AIが受信箱＋案件ログを一括処理して「型候補・カタログ追加候補・
          判断基準候補」の下書きを生成 → 管理者＋各G代表が30分で採択/却下
  四半期: AIが全案件事実を横断分析して「勝ち筋仮説」を提出 → 商品部が裁定
```

**人間は「入力係」でも「分析係」でもなく「編集長」**。書くのも分析するのもAI、裁くのが人。これなら蓄積が増えるほど人の負担が増える構造にならない。

## 3. 投稿ボックスの位置づけ（なぜうまくいかないか、との接続）

添付の投稿ボックスは、実は「生むエンジン」の手動版を既にやろうとした痕跡と読める。うまく回らない構造的理由（別スレ分析とも整合するはず）:
- **白紙で発想を求めている**: 「アイデアください」は出ない。出ても粒度がバラバラで、仕分けが人手に落ちて詰まる
- **ドロップの学びが捨てられている**: 理由列に貴重な判断基準が書かれているのに、次の起案に還流しない
- **採択後の受け皿がない**: 「テーマ研究」止まりで、型→提案→案件への導線がない

本プロダクトはこの3つを機械で埋める: 型ライブラリと適用シグナルが「白紙」をなくし（AIが型×企業の組合せ候補を先に出し、人は裁く側に回る）、ドロップ理由は判断基準スターター（資産6）として再利用され、採択された型はそのまま全員の提案生成に載る。**投稿ボックスは廃止ではなく、受信箱としてこのループに接続する。**

## 4. 「営業もグループも全商品を知らない」への回答

覚えなくていい、が設計思想。カタログ（資産2）が入った時点で、Step3の提案マッチングは**費用利益も工業中止もGLTDも常に検討台に載せる**。ノリで営業してる人の生成結果にも、理論武装派と同じ弾が装填される。グループ間の相互不理解も同じで、カタログと型ライブラリは「他Gが何をどう売っていて、どんなUWの勘所があるか」の初めての共通台帳になる——**ツールの副産物として部内の相互理解が生まれる**構造。だから各Gヒアリング（1回60分）は「協力のお願い」ではなく「おたくのGの売り物を全員が売れるようになる登録会」として設計する。

## 5. 収集の段取り（9月に1回で済ませる）

各G 60分ヒアリング（9月の課題収集と同席で実施）のアジェンダ:
1. カタログ下書きのレビュー（AIがパンフから作成済みのものを直す）: 20分
2. 最近の成約/失注 各1件の事実インタビュー: 15分
3. 変わった座組・面白い特約構成はあるか: 10分
4. 「これは引き受けない/縮小する」判断基準を3つ: 10分
5. 困りごと（PJ本来の課題収集）: 5分

これで資産2・3・5・6が一度に埋まる。事前準備は開発者側のAI下書きのみ。
