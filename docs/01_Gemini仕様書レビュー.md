# Gemini仕様書レビュー — FDE視点での評価

**対象**: 「超セキュア環境向け：AIリスク分析・提案書作成ツールの設計」（Gemini作成）
**目的**: 内田部長のアイデア（企業名・業種を入力→潜在リスク分析→リスクコンサル提案書骨子の自動生成）を具現化する手段として、本仕様書が最適かを評価する。
**結論**: **9月キックオフの「30秒デモ」素材としては有効。プロジェクトの成果物（プロダクト）としては不採用とし、多段パイプライン型の設計（docs/02）に差し替えることを推奨。**

## 2. 残す価値がある部分（デモ用に転用）

1. **出力フォーマットの骨格**: 企業サマリー → 4大リスクカテゴリ → 提案の切り口3点 → スライド骨子、という流れは方向性として正しい。
2. **「HPテキストのコピペを入力にする」発想**: APIがWeb検索不可の環境における現実的なグラウンディング手段。本設計でも入力手段として継承する。
3. **キックオフで春華堂のライブデモを見せる展開案**: 正しい。改良版プロンプト（docs/03）で実施する。

## 3. 根本的な問題点（7点）

### (1) 前提事実の誤り — 最強の資産を使わない設計になっている
Gemini案は「Web検索不可・**API不可**・Python/開発環境なし」を前提としているが、実際には:
- **OpenAI APIキーが開発者に付与済みで、コール制限なし**
- **VBAによる開発が可能**で、すでにVBA×OpenAI APIによるNotebookLM風ツールが社内PoC段階にある（技術スタックは実証済み）

つまり「開発できない前提のノーコード運用設計」は、当環境では制約回避ではなく**資産の放棄**である。

### (2) プロダクトではなく「プロンプト配布」
テキストファイルでプロンプトを配って各自コピペ、という運用には以下が欠落する:
- バージョン管理（誰がどの版のプロンプトを使っているか不明になる）
- 品質管理（出力のばらつきを検知・改善する仕組みがない）
- 改善ループ（現場の学びがプロンプトに還流しない）

結果として「プロンプトを使いこなせる人／使いこなせない人」という**新しい属人化**を生む。PJ目的（属人化解消・業務変革）と構造的に矛盾する。

### (3) 社内ナレッジが「添え物」扱い
仕様書では「2. さらに精度を上げるテクニック」として後付けされているが、実際には**ここが提案品質の本体**である。
- 社内には約款・アンダーライティングマニュアル・過去提案書など「80点まで」の電子データが多数存在する
- ナレッジなしの単発プロンプトは、一般論のリスク列挙と、**実在しないコンサルメニューを幻覚した提案**を返すリスクがある
- 「営業が現場で使える提案」= 実在の自社サービス・保険種目に紐づいた提案。ここへの接続が仕様の中心になければならない

### (4) 社内AI（ディープリサーチ）前提の危うさ
- 動作が遅く、現場は使わなくなる（ツール定着の最大の敵は待ち時間）
- 「個人情報・お客様情報は入力不可」の制約と、営業の実利用（顧客企業の情報を貼り付ける運用）が衝突しやすい。公開情報のみと言っても現場での線引きは曖昧になりがちで、コンプライアンス事故の温床になる
- アーキテクチャ不明のツールに業務プロセスを依存させるのは中期的にリスク

### (5) 「AIにVBAコードを都度生成させ、Alt+F11で貼り付け実行」は運用として破綻
- 非開発者に毎回マクロコードの貼り付け・実行をさせるのは、社内のセキュリティ教育（不明なマクロを実行しない）と真っ向から矛盾する
- 生成コードは毎回微妙に異なり、エラー時に現場で誰も直せない
- 正解は**事前ビルド・検証済みの固定VBA**を配布し、AIには構成データ（JSON）だけを返させる構造（docs/02参照）

### (6) 「80点→100点」の属人ナレッジを取り込む仕組みがゼロ
部内の実感として、80点までは電子データで揃うが、**提案のセンス・成功事例（何が刺さったか）は共有されておらず属人化している**。これが内田部長の課題意識（属人化解消・提案レベルの底上げ）の核心である。Gemini案にはこの暗黙知を採取・蓄積・再利用する仕組みが一切ない。ツールを配っても「ベテランの提案は上手く、若手の提案は一般論」という構図は変わらない。

### (7) ワンショット生成の限界
企業理解 → リスク仮説 → 提案マッチング → 骨子生成、という認知的に異なる4つの工程を1プロンプトに詰めると:
- どの工程で品質が落ちたのか検証できない（改善が回らない）
- 中間結果に人（ベテラン）が介入できない
- 出力形式が安定せず、後工程（PPT化）の自動化が壊れやすい

多段パイプライン化し、各段の中間出力を構造化データとして残すべき（docs/02参照）。

## 4. 判定

| 用途 | 判定 |
|---|---|
| 9月キックオフのデモ素材 | **採用**（docs/03の改良版プロンプトを使用） |
| PJの成果物・展開するプロダクト | **不採用** → docs/02「リスク提案ナビ」構想に差し替え |

Gemini案の本質的な価値は「開発ゼロでも明日デモができる」ことであり、それはPhase 0（キックオフ）で使い切る。10月以降のPoC・開発期は、実在する資産（OpenAI API＋VBA＋社内ナレッジ）を前提とした設計で進める。
